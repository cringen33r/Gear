## 1. Как оценивать временную сложность алгоритма на практике? Покажите на примерах кода, как определить O(n), O(n²), O(log n) и O(n log n)

**Что измеряем**
- Рост числа элементарных операций при росте n, не время в миллисекундах
- Константы и младшие члены отбрасываются: `3n + 100` → O(n)
- O — верхняя граница, Ω — нижняя, Θ — точная
- Различать лучший, средний, худший случай

**Метод оценки**
1. Вложенность циклов по данным
2. Как меняется счётчик: `i++` → линейно, `i *= 2` → логарифм
3. Сложность вызываемых внутри функций
4. Для рекурсии — рекуррентное соотношение

**O(1)** — доступ по индексу, `push`/`pop`, чтение из хеш-таблицы

**O(log n)** — размер задачи делится пополам на каждом шаге
```js
while (lo <= hi) { const mid = (lo + hi) >> 1; /* ... */ }
```
- n/2^k = 1 → k = log₂n; для n = 10⁶ это ~20 итераций

**O(n)** — один проход
```js
for (let i = 0; i < arr.length; i++) s += arr[i];
```
- Сюда же `map`, `filter`, `reduce`, `indexOf`; два последовательных цикла — тоже O(n)

**O(n log n)** — либо n операций по log n, либо divide-and-conquer
```js
mergeSort(left); mergeSort(right); merge(...); // T(n) = 2T(n/2) + O(n)
```
- Второй вид: цикл по n с бинарным поиском внутри

**O(n²)** — вложенный цикл по тем же данным
```js
for (let i = 0; i < n; i++)
  for (let j = i + 1; j < n; j++) /* ~n²/2 сравнений */
```

**Скрытый квадрат — где ошибаются**
- `a.filter(x => b.includes(x))` → O(n·m); лечится `Set` → O(n + m)
- `array.shift()` в цикле → O(n²), потому что shift сдвигает все элементы
- Конкатенация строк в цикле

**Ориентиры при ~10⁸ операций/сек**
- n ≤ 10⁶ → нужен O(n) или O(n log n)
- n ≤ 10⁴ → допустим O(n²)
- n ≤ 20 → допустим O(2ⁿ)

## 2. Как работает бинарный поиск? При каких условиях он применим и какие типичные ошибки встречаются на практике?

**Принцип**
- Сравниваем с элементом в середине, отбрасываем половину диапазона
- Инвариант: если элемент есть, он в [lo, hi]
- O(log n) по времени, O(1) по памяти (итеративно)

```js
let lo = 0, hi = a.length - 1;
while (lo <= hi) {
  const mid = lo + ((hi - lo) >> 1);
  if (a[mid] === target) return mid;
  if (a[mid] < target) lo = mid + 1; else hi = mid - 1;
}
return -1;
```

**Условия применимости**
1. Данные отсортированы по тому же ключу, по которому ищем
2. Произвольный доступ за O(1) — массив, строка; по связному списку бессмыслен
3. Предикат монотонен: ищем границу перехода false → true (отсюда «бинарный поиск по ответу»)

**Когда не окупается**
- Сортировка ради одного поиска: O(n log n) против O(n) линейного просмотра
- Если порядок не нужен вообще — хеш-таблица за O(1)

**Типичные ошибки**
- `(lo + hi) / 2` — переполнение в языках с фиксированной разрядностью → `lo + ((hi - lo) >> 1)`
- Забытое округление: в JS без `>> 1` или `Math.floor` индекс дробный → `undefined`
- `lo = mid` вместо `lo = mid + 1` → бесконечный цикл, границы не сужаются
- Смешение шаблонов: `hi = length - 1` требует `lo <= hi`, `hi = length` требует `lo < hi` и `hi = mid`
- Дубликаты: обычный поиск даёт произвольное вхождение, для первого нужен lower_bound
- Массив отсортирован не так: `[1,2,10].sort()` → `[1,10,2]`, сортировка лексикографическая
- Сортировка по одному ключу, поиск по другому
- Вещественный диапазон: `lo <= hi` не завершится, нужно фиксированное число итераций

## 3. Чем отличаются стек и очередь? Приведите примеры задач и объясните связь стека с рекурсией

**Различие**
- Стек — LIFO, добавление и удаление с одного конца: `push`, `pop`, `peek`
- Очередь — FIFO, добавление в хвост, удаление из головы: `enqueue`, `dequeue`
- Обе — O(1) на все операции при корректной реализации

**Реализация в JS**
- Стек — массив с `push`/`pop`
- Очередь **нельзя** через `push`/`shift`: shift сдвигает все элементы → O(n), цикл становится O(n²)
- Корректно: кольцевой буфер, связный список с head/tail, два индекса, очередь на двух стеках

**Задачи для стека**
- Сбалансированность скобок, парсинг, вычисление выражений
- Undo/redo, история навигации
- DFS без рекурсии
- Монотонный стек — ближайший больший элемент за O(n)
- Стек вызовов в движке

**Задачи для очереди**
- BFS и кратчайший путь в невзвешенном графе
- Планировщики, очереди сообщений, буферизация, rate limiting
- Task queue и microtask queue в event loop

**Связь стека с рекурсией**
- Каждый вызов создаёт фрейм стека вызовов: аргументы, локальные, адрес возврата
- Вход — фрейм кладётся, `return` — снимается
- Глубина рекурсии = высота стека; переполнение → `RangeError: Maximum call stack size exceeded` (в JS ~10⁴ фреймов)
- Любая рекурсия переписывается в цикл с явным стеком
- Смена контейнера меняет алгоритм: `stack.pop()` → DFS, `queue.dequeue()` → BFS при одном и том же коде
- Хвостовая рекурсия: оптимизация в спецификации ES2015 есть, в V8 не реализована

**Подробнее:** [[Стек и очередь]], [[Рекурсия]], [[DFS и BFS]]

## 4. Как работает хеш-таблица? Что такое коллизии и когда Map предпочтительнее обычного объекта в JavaScript?

**Устройство**
- Массив корзин, индекс = `hash(key) mod capacity`
- Требования к хеш-функции: быстрая, детерминированная, равномерная
- Вставка, поиск, удаление — O(1) в среднем

**Коллизии**
- Разные ключи дают один индекс; неизбежны — ключей больше, чем корзин
- Цепочки: в корзине список; в Java длинные цепочки → красно-чёрное дерево
- Открытая адресация: линейное, квадратичное пробирование, двойное хеширование; страдает от кластеризации, удаление через tombstones
- Load factor > 0.75 → рехеширование всей таблицы за O(n), вставка остаётся амортизированно O(1)
- Худший случай O(n); hash-flooding атака → защита рандомизированным зерном (SipHash)

**Object vs Map**

| | Object | Map |
|---|---|---|
| Ключи | строки и символы | любое значение |
| Прототип | наследует `Object.prototype` | нет |
| Размер | `Object.keys().length` — O(n) | `size` — O(1) |
| Порядок | целочисленные ключи сортируются | строго вставка |
| Итерация | через `Object.keys/entries` | итерируема по умолчанию |
| Частые вставки/удаления | хуже, возможен dictionary mode | оптимизирована |
| JSON | сериализуется | нет |

**Когда Map**
- Ключи не строки: объекты, DOM-узлы, функции
- Ключи приходят от пользователя — `__proto__` ломает объект (prototype pollution)
- Частые добавления и удаления
- Нужны порядок вставки, размер, регулярная итерация

**Когда Object**
- Фиксированный набор известных строковых ключей
- Нужна сериализация в JSON и деструктуризация
- Компромисс для словаря: `Object.create(null)`

**Смежное**
- `Set` — то же без значений, принадлежность за O(1)
- `WeakMap`/`WeakSet` — ключи-объекты удерживаются слабо, не мешают сборке мусора
- Ключи Map сравниваются по SameValueZero: `NaN` равен `NaN`

**Подробнее:** [[Хеш-таблица и коллизии]], [[Map, Set и WeakMap против объекта]]

## 5. Как работает приоритетная очередь на основе кучи? Какие операции эффективны и чем куча отличается от сортированного массива?

**Приоритетная очередь**
- Элементы извлекаются по приоритету, а не по порядку поступления
- Операции: `insert`, `extractMin`, `peek`

**Двоичная куча**
- Почти полное двоичное дерево в массиве
- Свойство min-кучи: узел ≤ потомков; корень — минимум
- Полного порядка нет — между братьями отношение не определено
- Индексы: потомки `2i+1`, `2i+2`; родитель `(i-1) >> 1`
- Высота log n, массив без дыр → хорошая локальность кеша

**Операции**
- `insert` — в конец и sift-up: O(log n)
- `extractMin` — корень как ответ, последний элемент в корень и sift-down: O(log n)
- `peek` — `heap[0]`: O(1)
- `build-heap` из готового массива: **O(n)**, а не O(n log n)
- `decrease-key` — O(log n), нужна карта «элемент → индекс»

**Куча vs сортированный массив**

| Операция | Куча | Сортированный массив |
|---|---|---|
| Вставка | **O(log n)** | O(n) — сдвиг |
| Извлечь минимум | O(log n) | **O(1)** |
| Просмотр минимума | O(1) | O(1) |
| Поиск произвольного | O(n) | **O(log n)** |
| k-й по порядку | O(n) | **O(1)** |
| Построение | **O(n)** | O(n log n) |
| Обход по возрастанию | O(n log n) | **O(n)** |

- Вывод: куча не тратит работу на полный порядок → выигрывает при динамическом потоке
- Сортированный массив выигрывает при редких изменениях и частом чтении

**Применение**
- Дейкстра, A\*, Прим
- Кодирование Хаффмана
- Top-K из потока: O(n log k) времени, O(k) памяти
- Планировщики задач и таймеры
- Скользящая медиана на двух кучах
- Heapsort

**Подробнее:** [[Двоичная куча и приоритетная очередь]]

## 6. Что такое бинарное дерево поиска? Какие ограничения оно накладывает и какие операции поддерживает?

**Определение**
- Для каждого узла: левое поддерево строго меньше, правое строго больше, оба — тоже BST
- Следствие: in-order обход даёт отсортированную последовательность

**Ограничения**
1. Ключи должны быть сравнимы — нужен линейный порядок
2. Классическое BST не хранит дубликаты (счётчик в узле или соглашение)
3. Все операции — O(h), где h — высота
4. Вставка отсортированных данных вырождает дерево в список → O(n)

**Операции**
- Поиск, вставка, min, max, предшественник, преемник — O(h)
- Удаление: лист — убрать; один потомок — заменить потомком; два потомка — заменить преемником (минимум правого поддерева), затем удалить его
- Обходы: in-order — сортировка, pre-order — сериализация, post-order — освобождение, level-order — по уровням
- Диапазонный запрос — O(h + k)
- k-й по порядку — O(h), если хранить размеры поддеревьев

**Балансировка**
- AVL — строгий баланс, быстрее поиск, дороже вставка
- Красно-чёрное — меньше поворотов; `std::map`, `TreeMap`, планировщик Linux
- B/B+-дерево — узел = страница диска; индексы СУБД, файловые системы
- Treap, splay, skip list

**BST vs хеш-таблица**
- Хеш: O(1) в среднем, но нет порядка, диапазонов, соседей
- BST: O(log n) гарантированно + порядок, диапазоны, min/max
- В JS встроенного BST нет: `Map` и `Set` — хеш-таблицы

**Подробнее:** [[Бинарное дерево поиска]], [[Сбалансированные деревья]]

## 7. Чем отличаются обход в глубину (DFS) и обход в ширину (BFS)? В каких задачах один предпочтительнее другого?

**Различие**
- DFS — стек (или рекурсия): вглубь до упора, затем откат
- BFS — очередь: по уровням
- Оба — O(V + E) при списках смежности

**Память**
- DFS — O(глубины)
- BFS — O(ширины), в худшем O(V)
- Широкий граф → DFS экономнее; глубокий → BFS безопаснее (стек не переполнится)

**Только BFS**
- Кратчайший путь в невзвешенном графе — вершина впервые достигается по кратчайшему пути
- Обход по уровням, поиск ближайшего с ранним выходом
- Multi-source BFS; обобщения — 0-1 BFS на деке, Дейкстра на куче

**Естественно через DFS**
- Топологическая сортировка (post-order + разворот)
- Обнаружение циклов через цвета вершин
- Компоненты связности, компоненты сильной связности, мосты и точки сочленения
- Backtracking: судоку, N ферзей, перестановки
- Рекурсивные обходы деревьев: AST, DOM, файловая система

**Веб-практика**
- `querySelector` — обход в глубину
- Реконсиляция React, резолвинг зависимостей сборщика — DFS
- Краулер — обычно BFS

**Компромисс**
- Iterative deepening DFS: оптимальность BFS при памяти DFS

## 8. Какие алгоритмы сортировки вы знаете? Сравните O(n²) и O(n log n) по сложности, памяти и устойчивости

**Устойчивость**
- Элементы с равными ключами сохраняют относительный порядок
- Нужна для многоключевой сортировки: сначала по имени, потом устойчиво по отделу

**Квадратичные**
- Bubble — O(n²), устойчива, O(1); практической ценности нет
- Selection — всегда Θ(n²) сравнений, но n−1 обменов; неустойчива; выгодна, когда запись дорога
- Insertion — O(n²) в худшем, **O(n) на почти отсортированных**, устойчива, O(1), малая константа → используется для подмассивов до 10–32 элементов

**O(n log n)**
- Merge — Θ(n log n) всегда, **устойчива**, O(n) памяти; связные списки, внешняя сортировка
- Quick — в среднем O(n log n) с лучшей константой (in-place, локальность), **худший O(n²)**, O(log n) стек, **неустойчива**; смягчение — случайный опорный, медиана из трёх, introsort
- Heap — гарантированные O(n log n), **O(1) памяти**, неустойчива, плохая локальность
- Timsort — гибрид merge и insertion, O(n) на отсортированном, устойчив; Python, Java, V8

**Сводка**

| Алгоритм | Средний | Худший | Память | Устойчив |
|---|---|---|---|---|
| Insertion | O(n²) | O(n²) | O(1) | да |
| Selection | O(n²) | O(n²) | O(1) | нет |
| Merge | O(n log n) | O(n log n) | O(n) | да |
| Quick | O(n log n) | **O(n²)** | O(log n) | нет |
| Heap | O(n log n) | O(n log n) | **O(1)** | нет |
| Timsort | O(n log n) | O(n log n) | O(n) | да |

**Нижняя граница**
- Любая сортировка на сравнениях — Ω(n log n): дерево решений с n! листьями, высота ≥ log₂(n!)
- Обход только без сравнений: counting O(n + k), radix O(d(n + k)), bucket O(n); все устойчивы

**Критерии выбора**
- Общий случай — встроенная сортировка языка
- Нужна устойчивость — merge/Timsort
- Лимит памяти — heapsort
- Гарантия по времени, защита от подобранного входа — introsort/heapsort
- Данные не влезают в память — внешняя сортировка слиянием
- Малые целые ключи — counting/radix

**JavaScript**
- `sort()` без компаратора сортирует как строки: `[10,9,1]` → `[1,10,9]`
- С V8 7.0 устойчива по спецификации; мутирует массив, иммутабельный вариант — `toSorted()`

**Подробнее:** [[Квадратичные сортировки]], [[Сортировки за O(n log n)]], [[Линейные сортировки и нижняя граница]], [[Выбор алгоритма сортировки]]

## 9. Что такое рекурсия? Как определить базовый случай и когда итеративный подход практичнее?

**Определение**
- Функция решает задачу, вызывая себя на подзадаче меньшего размера
- Две части: базовый случай (ответ без рекурсии) и рекурсивный случай (сведение + комбинация)

**Как определять базовый случай**
1. Взять наименьший осмысленный вход: пустой массив, пустая строка, `null`-узел, n = 0 или 1
2. Проверить, что аргумент **строго убывает** и не может перепрыгнуть базу (база `n === 0` при шаге `n - 2` → бесконечная рекурсия)
3. Проверить границы: длина 0 и 1, узел без потомков
4. При нескольких рекурсивных ветвях база должна покрывать все выходы
5. Учесть невалидный вход: отрицательное n, циклический граф → множество посещённых

**Плюсы**
- Код повторяет определение задачи
- Естественна для рекурсивных структур: деревья, JSON, DOM, AST, файловая система

**Минусы**
- Память на стек вызовов, в JS предел ~10⁴ вложений
- Накладные расходы на вызов
- Экспоненциальное дублирование при перекрывающихся подзадачах: наивный `fib` — O(2ⁿ) → мемоизация O(n) или итеративная динамика O(1) памяти

**Когда итеративный подход практичнее**
- Большая или непредсказуемая глубина — цикл с явным стеком не падает
- Линейные задачи: сумма, подсчёт, поиск
- Горячий код
- В JS: рекурсия, эквивалентная циклу, — TCO в V8 нет
- Нужен контроль обхода: пауза, лимит времени, прогресс

**Когда рекурсия практичнее**
- Обход дерева небольшой глубины, backtracking с откатом, парсинг, divide-and-conquer

**Преобразование в итерацию**
- Хвостовая → `while` с аккумулятором
- Нехвостовая → явный стек с сохранением состояния возврата
- Перекрывающиеся подзадачи → таблица динамического программирования

## 10. Как выбрать подходящую структуру данных для задачи? Сравните массив, связный список, хеш-таблицу, кучу и дерево поиска

**Вопросы для выбора**
1. Какие операции доминируют
2. Нужен ли порядок и какой
3. Соотношение чтений и записей
4. Нужна ли гарантия худшего случая
5. Помещаются ли данные в память

**Сравнение**

| Операция | Массив | Связный список | Хеш-таблица | Куча | Сбаланс. BST |
|---|---|---|---|---|---|
| По индексу | **O(1)** | O(n) | — | — | O(log n)\* |
| По ключу | O(n) | O(n) | **O(1)** сред. | O(n) | O(log n) |
| Вставка в конец | O(1) аморт. | O(1) | O(1) сред. | O(log n) | O(log n) |
| Вставка в середину | O(n) | **O(1)**\*\* | — | — | O(log n) |
| Минимум | O(n) | O(n) | O(n) | **O(1)** | O(log n) |
| Извлечь минимум | O(n) | O(n) | O(n) | **O(log n)** | O(log n) |
| Диапазон | O(n) | O(n) | O(n) | O(n) | **O(log n + k)** |
| Обход по возрастанию | O(n log n) | O(n log n) | O(n log n) | O(n log n) | **O(n)** |

\* при хранении размеров поддеревьев \*\* при наличии ссылки на узел

**Ниши**
- **Массив** — индекс, перебор, минимум накладных расходов, локальность кеша; дефолт в вебе
- **Связный список** — стабильные ссылки при частых модификациях; двусвязный внутри LRU, деки
- **Хеш-таблица** — индекс по id, дедупликация, подсчёт частот, кеш, принадлежность
- **Куча** — приоритетная очередь, Дейкстра, top-K, планировщики
- **BST** — порядок, диапазоны, ближайший ключ, k-й по порядку

**Специализированные**
- Trie — префиксный поиск; дек — скользящее окно; union-find — компоненты связности; bloom filter — дешёвый фильтр; LRU = хеш + двусвязный список; дерево отрезков — запросы на диапазоне

**Типичные ошибки**
- Линейный поиск в цикле вместо `Set` → скрытый O(n²)
- `shift()` как очередь → O(n²)
- Полная сортировка ради top-K вместо кучи
- Хеш-таблица там, где нужны диапазоны
- Связный список «ради асимптотики» на малых объёмах
- Преждевременная оптимизация при малом n

**Эвристика**
- Порядок и индекс → массив
- Доступ по ключу → хеш-таблица
- Самый приоритетный → куча
- Порядок по значению и диапазоны → дерево
- Уникальность → Set
- Префиксы → trie
