## 1. Что происходит, когда пользователь вводит URL в браузере? Опишите путь от DNS до начала рендеринга HTML

**1. Разбор строки**
- URL или поисковый запрос; разбор на схему, хост, порт, путь, query, фрагмент
- Проверка HSTS → принудительная замена `http` на `https` до отправки
- Нормализация хоста, Punycode

**2. DNS**
- Поиск по кешам: браузер → ОС и `hosts` → резолвер провайдера
- Если нет — рекурсивный обход: корневые серверы → TLD → авторитативный сервер зоны
- Запись A/AAAA, у каждой TTL; возможен CNAME
- UDP 53; современные варианты — DoH, DoT
- Оптимизация: `dns-prefetch`, `preconnect`

**3. Соединение**
- TCP-хендшейк SYN → SYN-ACK → ACK = 1 RTT
- TLS: шифронабор, проверка сертификата до корневого CA, срок, домен, ECDHE (forward secrecy)
- TLS 1.3 — 1 RTT, при возобновлении 0 RTT
- ALPN — согласование h2 / h3 / http/1.1; SNI — какой домен
- HTTP/3: QUIC поверх UDP, транспорт и криптография в одном рукопожатии

**4. Запрос**
- Сначала Service Worker, затем HTTP-кеш: свежий → сети нет; протух → условный запрос
- Фрагмент `#...` на сервер **не отправляется**
- Возможны редиректы 301/302/307 → процесс повторяется

**5. Ответ**
- Приходит потоково; тип по `Content-Type`, не по расширению
- Парсер стартует, **не дожидаясь конца ответа**

**6. Критический путь рендеринга**
- HTML → DOM, CSS → CSSOM
- CSS блокирует отрисовку (иначе FOUC)
- Обычный `<script>` блокирует **парсер** (может вызвать `document.write`) и ждёт CSSOM; лечится `defer`, `async`, `type="module"`
- Preload scanner качает ресурсы, пока парсер заблокирован
- DOM + CSSOM → render tree → layout → paint → composite
- `transform` и `opacity` — только композиция, поэтому дёшевы

**После первой отрисовки**
- Подресурсы, `DOMContentLoaded`, `load`, гидратация, регистрация SW
- Метрики: TTFB, FCP, LCP, CLS, INP

**Подробнее:** [[Путь запроса от URL до ответа]], [[Критический путь рендеринга]]

## 2. Из чего состоят HTTP-запрос и HTTP-ответ? Чем отличаются методы GET, POST, PUT, PATCH, DELETE? Какие идемпотентны и почему это важно?

**Структура запроса**
- Стартовая строка: метод, target (путь + query), версия
- Заголовки
- Пустая строка
- Тело (опционально)

**Структура ответа**
- Статусная строка: версия, код, фраза
- Заголовки, пустая строка, тело

**Ключевые заголовки**
- Запроса: `Host` (обязателен в 1.1), `Accept`, `Accept-Encoding`, `Content-Type`, `Content-Length`, `Authorization`, `Cookie`, `Origin`, `If-None-Match`, `If-Modified-Since`, `Range`
- Ответа: `Content-Type`, `Cache-Control`, `ETag`, `Last-Modified`, `Location`, `Set-Cookie`, `Access-Control-Allow-Origin`, `Vary`

**HTTP/2–3**
- Стартовая строка → псевдозаголовки `:method`, `:path`, `:scheme`, `:authority`
- Сжатие HPACK/QPACK, бинарные мультиплексированные потоки; семантика та же

**Свойства методов**

| Метод | Тело | Safe | Идемпотентен | Кешируем |
|---|---|---|---|---|
| GET | нет | да | **да** | да |
| HEAD | нет | да | **да** | да |
| POST | да | нет | **нет** | редко |
| PUT | да | нет | **да** | нет |
| PATCH | да | нет | **не гарантирован** | нет |
| DELETE | обычно нет | нет | **да** | нет |

**Различия**
- GET — параметры в URL: закладки, ссылки, кеш; ограничение длины, видно в логах и истории
- POST — тело: изменяющие операции, большие объёмы, чувствительные данные
- PUT vs POST — кто назначает URI: PUT клиент знает адрес, POST адрес возвращает сервер в `Location`
- PUT заменяет ресурс целиком (отсутствующие поля сброшены), PATCH описывает изменение
- PATCH не идемпотентен в общем случае: merge patch `{"age":31}` — да, «добавить в массив» — нет
- DELETE идемпотентен: коды различаются (204, затем 404), но **состояние сервера** одно

**Почему идемпотентность важна**
1. Таймаут — клиент не знает, дошёл ли запрос; идемпотентный можно повторить
2. Автоматические ретраи в библиотеках, прокси, service mesh — только идемпотентные методы
3. Кеширование и спекулятивная предзагрузка GET → **GET не должен менять состояние** (`GET /delete?id=5` выполнит краулер)
4. Гарантия «at least once» в очередях требует идемпотентных обработчиков

**Idempotency-Key**
- Для POST, который должен переживать повтор (платежи): клиент шлёт UUID, сервер сохраняет результат первой обработки и возвращает его на повтор

**Подробнее:** [[HTTP-методы и идемпотентность]], [[Структура HTTP-запроса и ответа]], [[HTTP (HyperText Transfer Protocol)]]

## 3. Как выбирать HTTP-статусы для REST API? Объясните разницу между 200, 201, 204, 400, 401, 403, 404, 409, 422, 500

**Принцип**
- 2xx успех, 3xx перенаправление, **4xx — вина клиента**, **5xx — вина сервера**
- От разделения 4xx/5xx зависят алертинг, SLA и логика ретраев

**Разбор кодов**
- **200 OK** — успех с телом
- **201 Created** — создан ресурс; обязателен `Location`; типично для `POST /users`
- **204 No Content** — успех, тела нет; DELETE, PUT без ответа, «сохранить настройки»
- **400 Bad Request** — **синтаксис**: битый JSON, нет обязательного параметра, неверный тип
- **401 Unauthorized** — «не аутентифицирован»: нет/недействительны/истекли credentials; обязателен `WWW-Authenticate`; имеет смысл обновить токен и повторить
- **403 Forbidden** — аутентифицирован, но прав нет; повтор бессмыслен
- **404 Not Found** — ресурса нет либо сервер не раскрывает его существование
- **409 Conflict** — конфликт с **текущим состоянием**: email занят, есть ссылки на сущность, устаревший ETag
- **422 Unprocessable Content** — синтаксис верен, нарушена **семантика**: невалидный email, отрицательный возраст, дата окончания раньше начала
- **500 Internal Server Error** — необработанное исключение; не для ошибок ввода; без stack trace; в мониторинг

**Разграничение**

| Ситуация | Код |
|---|---|
| Сломанный JSON | 400 |
| Нет обязательного поля | 400 или 422 |
| Поле не проходит валидацию | 422 |
| Значение конфликтует с состоянием | 409 |

- Спецификация не предписывает жёстко; важна последовательность внутри API

**Другие полезные**
- 202 Accepted — асинхронная обработка
- 206 Partial Content — Range
- 304 Not Modified — валидация кеша
- 405 Method Not Allowed — обязателен `Allow`
- 410 Gone — удалён навсегда
- 415 Unsupported Media Type
- 429 Too Many Requests — с `Retry-After`
- 502 / 503 / 504

**Формат ошибки**
- RFC 9457 Problem Details: `type`, `title`, `status`, `detail`, `instance` + машиночитаемый код
- Не раскрывать SQL, пути, версии

**Частые ошибки**
- Всегда 200 с `{"success": false}` — ломает кеш, мониторинг, клиентские библиотеки
- 500 при ошибке ввода — искажает метрики надёжности
- 200 вместо 201 без `Location`; тело с 204

**Подробнее:** [[HTTP-статусы]]

## 4. Как устроена реляционная база данных и зачем нужны индексы? Объясните таблицу, ключи, связи. Как индекс ускоряет чтение и замедляет запись?

**Модель**
- Данные в отношениях (таблицах): строка = объект, столбец = атрибут с типом и ограничениями
- Порядок строк не определён, задаётся только `ORDER BY`
- SQL декларативен: что нужно — описывает разработчик, как получить — решает планировщик

**Ключи**
- PRIMARY KEY — уникален, NOT NULL; естественный или суррогатный (предпочтительнее — естественные меняются)
- UNIQUE — уникальность, NULL допустим
- FOREIGN KEY — ссылочная целостность; `ON DELETE`: CASCADE, SET NULL, RESTRICT
- Составной ключ — для таблиц-связок

**Связи**
- 1:1 — FK + UNIQUE
- 1:N — FK хранится **на стороне «многих»**
- M:N — промежуточная таблица с двумя FK и составным PK

**Нормализация**
- 1НФ атомарность, 2НФ зависимость от всего ключа, 3НФ нет транзитивных зависимостей
- Убирает аномалии вставки, обновления, удаления
- Денормализация — дублирование ради чтения, ценой согласованности

**Зачем индекс**
- Без индекса — seq scan, O(n); с индексом — O(log n)
- Аналогия: алфавитный указатель в книге

**B+-дерево**
- Узел = страница диска (4–8 КБ), сотни ключей → высота 3–4 уровня на миллионах строк
- Листья связаны в список → диапазоны и `ORDER BY`
- Работает: `=`, `<`, `>`, `BETWEEN`, `LIKE 'abc%'`, сортировка, MIN/MAX
- Не работает: `LIKE '%abc'`, вычисление над столбцом (`YEAR(created_at)`), неявное приведение типов

**Другие типы**
- Hash — только равенство; GiST/GIN — полнотекст, JSONB, гео; BRIN — большие упорядоченные таблицы; bitmap — низкая кардинальность

**Составные и покрывающие**
- Составной `(a,b,c)` работает по левому префиксу: `a`, `(a,b)`, `(a,b,c)`; не для `b` отдельно
- Порядок: сначала равенство, потом диапазон
- Покрывающий индекс → index-only scan без обращения к таблице
- Кластеризованный (InnoDB) хранит строки в порядке PK

**Почему замедляется запись**
1. Найти место в дереве — O(log n)
2. Вставка, при переполнении — расщепление узла, возможно каскадное
3. Запись в WAL — дополнительный I/O
4. Удаление — tombstone + последующая очистка (VACUUM)
5. Всё под блокировками → падает параллелизм
- Итог: 8 индексов = 9 операций записи вместо одной; плюс место на диске и вытеснение данных из кеша

**Что индексировать**
- PK (автоматически), **FK** (JOIN и проверки при удалении), столбцы в WHERE / JOIN / ORDER BY / GROUP BY
- Только высокоселективные: индекс по полю с двумя значениями бесполезен
- Неиспользуемые индексы удалять (`pg_stat_user_indexes`, `idx_scan = 0`)
- Диагностика — `EXPLAIN ANALYZE`; смежная проблема — N+1

**Подробнее:** [[Индексы в базе данных]], [[Реляционная модель — таблицы, ключи, связи]]

## 5. Что такое транзакция в базе данных? Какие проблемы согласованности она решает и когда необходима?

**Определение**
- Последовательность операций как неделимое целое: COMMIT или ROLLBACK
- Пример: перевод денег двумя UPDATE

**ACID**
- **Atomicity** — всё или ничего; undo-журнал
- **Consistency** — все ограничения и инварианты соблюдены
- **Isolation** — параллельные транзакции не видят промежуточных состояний
- **Durability** — после COMMIT данные переживут сбой; WAL + fsync до подтверждения

**Проблемы параллельного доступа**
- Грязное чтение — читаем незакоммиченное
- Неповторяющееся чтение — та же строка при двух чтениях различается
- Фантомное чтение — тот же запрос возвращает новые строки
- Потерянное обновление — read-modify-write: 100 → оба пишут 150 вместо 200
- Write skew — обе читают согласованное состояние, пишут в разные строки, ломая инвариант

**Уровни изоляции**

| Уровень | Dirty | Non-repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | + | + | + |
| READ COMMITTED | − | + | + |
| REPEATABLE READ | − | − | +\* |
| SERIALIZABLE | − | − | − |

\* в PostgreSQL snapshot isolation фантомы не допускает
- Умолчания: PostgreSQL, Oracle, SQL Server — READ COMMITTED; MySQL InnoDB — REPEATABLE READ
- Строже изоляция → ниже параллелизм и больше откатов по конфликту

**Механизмы**
- Блокировки (2PL): S и X, возможны deadlock — СУБД обнаруживает и откатывает одну
- MVCC: версии строк, читатели не блокируют писателей; плата — мёртвые версии и VACUUM
- Пессимистическая — `SELECT ... FOR UPDATE`; оптимистическая — версия строки в `WHERE`, при 0 строк повтор

**Когда необходима**
- Меняются несколько строк или таблиц, которые должны меняться вместе
- Read-modify-write: списание баланса, декремент остатка
- Согласованная выборка для отчёта
- Пакетная обработка, где частичное применение недопустимо

**Когда не нужна и вредна**
- Одиночные INSERT/UPDATE — уже атомарны в autocommit
- Внутри транзакции нельзя: HTTP-вызовы, отправка почты, обработка файлов — удерживаются блокировки, блокируется VACUUM
- Правило: транзакция короткая, внешние эффекты через outbox

**Распределённые**
- 2PC — блокирующий, применяется редко
- Saga — локальные транзакции + компенсирующие действия
- Transactional outbox — событие в той же транзакции, публикация асинхронно; «at least once» → идемпотентные потребители
- Теория: CAP, модель BASE

**Подробнее:** [[Транзакции и ACID]], [[Уровни изоляции и аномалии параллельного доступа]], [[Распределённые транзакции]]

## 6. Как выполняется JavaScript-код в браузере? Объясните call stack, task queue, microtask queue и event loop. Почему setTimeout(fn, 0) не мгновенен?

**Модель**
- Один поток: в каждый момент выполняется ровно один фрагмент кода
- Асинхронность даёт не параллелизм JS, а среда исполнения, возвращающая результат через очереди

**Компоненты**
- **Call stack** — фреймы вызовов; переполнение → `RangeError`
- **Heap** — объекты, управляются GC
- **Web APIs** — `setTimeout`, `fetch`, DOM-события; реализованы вне движка
- **Task queue (макрозадачи)** — таймеры, события ввода, `MessageChannel`, загрузка ресурсов
- **Microtask queue** — `.then`/`.catch`/`.finally`, `queueMicrotask`, `MutationObserver`, продолжение после `await`

**Алгоритм цикла**
1. Стек пуст → взять **одну** задачу из task queue, выполнить до конца
2. Выполнить **все** микрозадачи, включая появившиеся по ходу
3. При необходимости — рендеринг: `requestAnimationFrame` → стили → layout → paint
4. Повтор

**Следствия**
- За тик: одна макрозадача, все микрозадачи
- Рендеринг невозможен, пока стек не пуст и микрозадачи не исчерпаны
- Тело async-функции **до первого `await`** выполняется синхронно

**Порядок на примере**
```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
(async () => { console.log('4'); await null; console.log('5'); })();
console.log('6');
// 1, 4, 6, 3, 5, 2
```

**Почему `setTimeout(fn, 0)` не мгновенен — три причины**
1. Это постановка в очередь **макрозадач**: колбэк ждёт конца синхронного кода и опустошения очереди микрозадач
2. Clamping по спецификации: при вложенности > 5 минимум 4 мс; в фоновых вкладках до 1000 мс и реже
3. В очереди перед ним могут стоять другие задачи — гарантия «не раньше чем», не «ровно через»

**Практика**
- Бесконечная цепочка микрозадач блокирует рендеринг, `setTimeout` — нет
- `setTimeout(fn, 0)` — законный способ отдать управление браузеру и разбить тяжёлую работу
- Современные альтернативы: `scheduler.yield()`, `scheduler.postTask()`, `requestIdleCallback`, Web Workers

**Node.js**
- Фазы libuv: timers → pending → poll → check (`setImmediate`) → close
- `process.nextTick` приоритетнее микрозадач промисов

**Подробнее:** [[Event loop, задачи и микрозадачи]], [[Таски, микротаски, очередь и прочие ублюдки]]

## 7. Сравните cookies, localStorage и sessionStorage. Чем отличаются по времени жизни, области действия, взаимодействию с сервером?

**Сравнение**

| | Cookies | localStorage | sessionStorage |
|---|---|---|---|
| Объём | ~4 КБ | 5–10 МБ | 5–10 МБ |
| Время жизни | до `Expires`/`Max-Age`, иначе до закрытия браузера | бессрочно | до закрытия **вкладки** |
| Область | домен + путь, при `Domain` — поддомены | origin | origin **в одной вкладке** |
| Отправка на сервер | **автоматически с каждым запросом** | нет | нет |
| Доступ с сервера | да, заголовок `Cookie` | нет | нет |
| Доступ из JS | `document.cookie`, кроме `HttpOnly` | да | да |
| Событие | нет | `storage` в других вкладках | нет |

**Cookies**
- Устанавливаются через `Set-Cookie` или из JS
- Атрибуты: `Expires`/`Max-Age`, `Domain`, `Path`, `Secure`, **`HttpOnly`** (недоступна JS — защита от XSS), **`SameSite`** (Strict / Lax по умолчанию / None+Secure — защита от CSRF), `Partitioned`
- Главный недостаток: едут с **каждым** запросом, включая картинки и стили → лишние килобайты замедляют весь сайт

**localStorage**
- Синхронный key-value, только строки, объекты через `JSON.stringify`
- Общий для всех вкладок origin
- Событие `storage` в других вкладках — синхронизация темы, разлогин везде
- Минусы: синхронный API блокирует поток, доступен любому скрипту (XSS), в приватном режиме может бросать

**sessionStorage**
- Тот же API, своя копия у каждой вкладки; переживает перезагрузку, не переживает закрытие
- Для состояния мастера, фильтров, позиции скролла

**Что где хранить**
- Cookies — сессия и токены (HttpOnly + Secure + SameSite), данные для SSR: локаль, A/B-группа
- localStorage — настройки UI, черновики, флаги «онбординг показан»
- sessionStorage — временное состояние вкладки

**JWT: cookie или localStorage**
- localStorage — уязвим к XSS, не уязвим к CSRF
- HttpOnly cookie — не уязвим к XSS, уязвим к CSRF → нужен SameSite + CSRF-токен
- Консенсус: HttpOnly cookie при наличии CSRF-защиты; универсального ответа нет

**Другие механизмы**
- IndexedDB — асинхронная транзакционная база, сотни МБ, офлайн
- Cache API — для Service Worker; OPFS — файлы; переменная в памяти — самое безопасное для короткого access-токена

## 8. Чем Docker-контейнер отличается от виртуальной машины? Какие задачи решает контейнеризация в разработке и развёртывании?

**Уровень виртуализации**
- ВМ: гипервизор виртуализирует **аппаратуру**, у каждой гостевой ОС **своё ядро**
- Контейнер: виртуализируется ОС, процессы изолируются средствами **ядра хоста**, ядро общее

**Механизмы контейнера в Linux**
- namespaces — изоляция видимости: PID, NET, MNT, UTS, IPC, USER
- cgroups — лимиты CPU, памяти, I/O
- OverlayFS — послойный образ: слои read-only + записываемый слой
- capabilities, seccomp, AppArmor/SELinux

**Сравнение**

| | ВМ | Контейнер |
|---|---|---|
| Ядро | своё | **общее с хостом** |
| Размер | гигабайты | мегабайты |
| Старт | десятки секунд | миллисекунды–секунды |
| Плотность | десятки | сотни |
| Другая ОС на хосте | да | нет |
| Граница безопасности | сильная (гипервизор) | слабее |
| Снапшоты, живая миграция | зрелые | ограниченно |

- Docker на macOS/Windows поднимает лёгкую Linux-ВМ
- Гибриды для сильной изоляции: Firecracker, gVisor, Kata Containers

**Какие задачи решает**
1. «Работает у меня» — образ содержит рантайм, библиотеки, конфигурацию; одинаковое окружение на ноутбуке, в CI, в проде
2. Воспроизводимость — Dockerfile в репозитории, ревьюится как код
3. Онбординг — `docker compose up` поднимает приложение, БД, кеш, очередь
4. Изоляция зависимостей — разные версии Node/Python без конфликтов
5. Плотность и утилизация железа
6. Единица оркестрации — Kubernetes: масштабирование, самовосстановление, rolling update, health checks, service discovery
7. Деплой = запуск нового образа, откат = запуск предыдущего тега
8. CI/CD — артефакт сборки один и тот же на всех стадиях

**Ключевые понятия**
- Образ, контейнер, Dockerfile, registry, volume, сеть, Compose

**Практики**
- Многостадийная сборка; порядок инструкций от редко меняющихся к часто; `.dockerignore`
- Минимальные базовые образы (alpine, distroless), регулярное обновление
- **Не root**, секреты не в образе
- Один процесс на контейнер, логи в stdout
- Явные теги вместо `latest`, сканирование уязвимостей
- Лимиты ресурсов, health check

**Ограничения**
- Не заменяют ВМ при недоверенных арендаторах, другом ядре или ОС, специфических драйверах
- Оркестрация добавляет операционную сложность
