## 1. Как работают HTML-формы? Объясните роль form, input, label, button и атрибутов name, value, method, action

**`<form>`**
- Собирает ввод и отправляет на сервер; единственный способ отправки без JS
- `action` — URL назначения; пустой = текущий URL
- `method` — нативно **только GET и POST** (плюс `dialog`); PUT/PATCH/DELETE только через `fetch` или method override
- `enctype` — `application/x-www-form-urlencoded` по умолчанию, **`multipart/form-data` обязателен для файлов**
- `novalidate`, `target`

**GET vs POST в форме**
- GET — данные в query: закладки, ссылки, обновление без предупреждения; ограничение длины, видно в истории и логах
- POST — данные в теле: изменяющие операции, большие объёмы, чувствительные данные

**`<input>`**
- Тип задаёт поведение: `text`, `email`, `password`, `number`, `tel`, `date`, `file`, `checkbox`, `radio`, `hidden`
- Правильный `type` даёт: клавиатуру на мобильных, встроенную валидацию, нативный виджет, автозаполнение
- Другие элементы: `<textarea>`, `<select>`, `<fieldset>`+`<legend>`, `<datalist>`, `<output>`

**`name`**
- Ключ данных; **без него поле не отправляется вообще**
- Одинаковый `name` у радиокнопок = группа с взаимоисключающим выбором
- Одинаковый `name` у чекбоксов = массив значений
- **Неотмеченные чекбоксы/радио не отправляются** — на сервере `undefined`, а не `false`
- `disabled` не отправляется, `readonly` отправляется

**`value`**
- Начальное значение и то, что уйдёт на сервер
- Для checkbox/radio — значение при выборе; без `value` отмеченный чекбокс шлёт `on`
- Для `<button name="action" value="save">` — какой кнопкой отправили
- У `<textarea>` значение — содержимое тега
- Различать атрибут `value` (начальное, `defaultValue`) и свойство `input.value` (текущее)

**`<label>`**
- Связь: `for` + `id` либо вложение поля внутрь
- Даёт: объявление подписи скринридером, клик по подписи = фокус/переключение, доступное имя
- **`placeholder` не заменяет label**: исчезает при вводе, низкий контраст, теряется при автозаполнении

**`<button>`**
- `submit` (по умолчанию в форме), `reset`, `button`
- Частая ошибка: забытый `type="button"` у вспомогательной кнопки → отправка формы
- `formaction`/`formmethod` переопределяют атрибуты формы
- Предпочтительнее `<input type="submit">`: можно вкладывать разметку

**Отправка и валидация**
- Отправка: клик по submit, `Enter` в текстовом поле, `form.requestSubmit()` (в отличие от `submit()` запускает валидацию и событие)
- Constraint Validation: `required`, `pattern`, `min`, `max`, `minlength`, `step`
- Псевдоклассы `:valid`, `:invalid`, `:user-invalid` (только после взаимодействия)
- API: `setCustomValidity`, `checkValidity`, `reportValidity`, `validity`
- **Валидация на клиенте — удобство, не безопасность**: сервер проверяет заново

**Отправка через JS**
- `new FormData(form)` собирает поля по `name` и сам выставляет `Content-Type` с boundary — руками не задавать

## 2. Что такое блочная модель CSS? Как формируются итоговые размеры элемента и зачем различать content-box и border-box?

**Модель**
- Четыре зоны: content → padding → border → margin
- `padding` входит в фон и область клика, `margin` прозрачен и не входит

**content-box (по умолчанию)**
- `width`/`height` задают **только область содержимого**, padding и border **прибавляются**
- `width: 200 + padding: 20 + border: 5` → занимает 250 px

**border-box**
- `width` = полная ширина **включая padding и border**; содержимое вычисляется вычитанием
- Те же значения → ровно 200 px

**Зачем различать**
1. Предсказуемость сеток: две колонки по 50% с padding при content-box переполняют контейнер
2. Меньше арифметики — не нужен `calc(50% - 32px)` и пересчёт при смене отступов
3. Стабильность при `:hover` с рамкой — размер не меняется, соседи не сдвигаются
4. Совместимость: фреймворки сбрасывают глобально `*, *::before, *::after { box-sizing: border-box }`
- content-box остался по умолчанию из-за обратной совместимости

**Что не входит в box-sizing**
- `margin` всегда прибавляется к занимаемому месту
- `outline` и `box-shadow` места не занимают

**Схлопывание margin**
- Вертикальные margin соседних или вложенных блоков объединяются в наибольший: 20 и 30 → 30
- Случаи: соседи, родитель и первый/последний потомок, пустые блоки
- **Не происходит**: во flex и grid, при padding/border между margin, при `overflow` ≠ `visible`, при абсолютном позиционировании, в отдельном BFC
- Горизонтальные margin не схлопываются никогда

**Смежное**
- `max-width` побеждает `width`, `min-width` побеждает `max-width`
- Ключевые слова: `min-content`, `max-content`, `fit-content`; `aspect-ratio`
- `width: 100%` — от content-box родителя; `100vw` включает полосу прокрутки → горизонтальный скролл
- `display`: у `inline` `width`/`height` игнорируются, вертикальные отступы не влияют на высоту строки

## 3. Как браузер выбирает итоговый стиль элемента? Объясните каскад, специфичность, наследование и роль !important

**Каскад — порядок критериев**
1. **Происхождение и важность**: UA → пользователь → автор → анимации → авторские `!important` → пользовательские `!important` → UA `!important` → transitions
   - Для `!important` порядок происхождений **инвертируется** — чтобы пользователь мог переопределить сайт
2. **Слои `@layer`**: порядок объявления = приоритет; стили вне слоёв приоритетнее любого слоя
3. **Специфичность**
4. **Порядок появления** — побеждает последнее

**Специфичность**
- Тройка (A, B, C): id / классы, атрибуты, псевдоклассы / типы элементов и псевдоэлементы
- Сравнение лексикографическое, **разряды не переносятся**: 11 классов < 1 id
- Inline `style` выше любых селекторов

| Селектор | Специфичность |
|---|---|
| `li` | 0,0,1 |
| `.item` | 0,1,0 |
| `input[type="text"]` | 0,2,0 |
| `#main .item p` | 1,1,1 |

- `:where()` — **нулевая специфичность** (сбросы, библиотечные стили)
- `:is()`, `:not()`, `:has()` — специфичность самого сильного аргумента
- Вложенность (CSS Nesting) считается как `:is()`

**Наследование**
- Наследуются: `color`, `font-*`, `line-height`, `letter-spacing`, `text-align`, `white-space`, `visibility`, `cursor`, `list-style`, `--*`
- Не наследуются: `margin`, `padding`, `border`, `width`, `height`, `background`, `display`, `position`, `overflow`, `z-index`
- Логика: типографика наследуется, геометрия — нет
- Управление: `inherit`, `initial`, `unset`, `revert`, `all: unset`
- **Срабатывает только если элемент не выбран напрямую**: любое прямое объявление побеждает унаследованное

**`!important`**
- **Не увеличивает специфичность** — меняет уровень каскада
- Между двумя `!important` конфликт решается обычным порядком
- Проблемы: ломает каскад, гонка важности, сложность поддержки
- Оправдан: утилитарные классы, переопределение стороннего виджета или inline-стилей, стили доступности, отладка
- Альтернативы: снизить специфичность, `@layer`, `:where()`, CSS-переменные

**Итоговый алгоритм**
1. Фильтрация применимых объявлений
2. Каскад
3. Наследование или начальное значение
4. Computed value (относительные единицы → px)
5. Used value (проценты → px после раскладки)

**Подробнее:** [[Каскад и специфичность]], [[Наследование в CSS]]

## 4. Как работает Flexbox? Какие задачи решает, какие основные свойства и почему длинный контент ломает layout?

**Назначение**
- Одномерная раскладка вдоль **одной оси** с распределением свободного места
- Задачи: меню, тулбар, карточка с кнопкой внизу, центрирование, липкий подвал, фиксированная + резиновая колонки

**Оси**
- Главная задаётся `flex-direction`, поперечная перпендикулярна
- Свойства формулируются в терминах осей → смена направления меняет смысл выравниваний, работает в RTL

**Свойства контейнера**
- `flex-direction`, `flex-wrap` (`flex-flow`)
- `justify-content` — вдоль **главной** оси
- `align-items` — вдоль **поперечной** для каждой строки
- `align-content` — распределение строк, **только при wrap**
- `gap`

**Свойства элементов**
- `flex-grow`, `flex-shrink`, `flex-basis` (`flex`)
- `flex: 1` = `1 1 0%` → **равные** размеры независимо от контента
- `flex: auto` = `1 1 auto` → с учётом контента
- `flex: none` = `0 0 auto`
- `align-self`, `order` (меняет только визуальный порядок, **не DOM** — влияет на порядок фокуса)

**Почему длинный контент ломает layout**
- У flex-элементов начальное `min-width: auto` (для колонки `min-height: auto`)
- Это «не сжимать меньше автоматического минимального размера содержимого» ≈ `min-content` — ширина самого длинного неразрывного слова или картинки
- `flex-shrink` не может опустить ниже этого порога → элемент выдавливает соседей или даёт горизонтальный скролл
- Источники: длинный URL без пробелов, `<pre>`/`<code>`, таблица, большое изображение

**Решение**
```css
.item { min-width: 0; }            /* или overflow: hidden */
.text { overflow-wrap: break-word; }
.truncate { overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
img { max-width: 100%; height: auto; }
```

**Другие частые проблемы**
- Не переносится — `flex-wrap: nowrap` по умолчанию
- `align-content` не работает — нужна больше одной строки
- Все одинаковой высоты — `align-items: stretch` по умолчанию
- `flex: 1` даёт равные ширины — из-за `flex-basis: 0`, нужен `flex: auto`
- `justify-content` не действует — свободного места нет при `flex-grow: 1`

**Flexbox или Grid**

| | Flexbox | Grid |
|---|---|---|
| Измерения | одно | два |
| Отправная точка | содержимое | макет |
| Перекрытие | нет | да |
| Задачи | панель, меню, карточка | страница, галерея, дашборд |

**Подробнее:** [[Flexbox]], [[Почему длинный контент ломает flex-раскладку]], [[CSS Grid]]

## 5. Как работает политика same-origin и механизм CORS? Какие способы обхода существуют и когда применяются?

**Origin**
- Схема + хост + порт; совпадать должны все три
- Поддомен — другой origin

**Same-Origin Policy**
- Скрипт одного origin **не может читать данные** другого origin
- Ограничивает: чтение ответов `fetch`/XHR, доступ к DOM чужого окна, tainted canvas, чужие storage и cookies
- **Не блокирует**: загрузку `<img>`, `<script>`, `<link>`, `<iframe>` и **отправку формы** на другой origin → отсюда CSRF

**CORS**
- Механизм, которым **сервер разрешает** конкретным origin читать свои ответы
- Не обходит защиту — ослабляет её по решению сервера
- Проверку делает **браузер**, запрос при этом сервером уже выполнен

**Простые запросы**
- GET, HEAD, POST; заголовки только из безопасного списка; `Content-Type` — `text/plain`, `multipart/form-data`, `application/x-www-form-urlencoded`
- Браузер шлёт `Origin`, сервер отвечает `Access-Control-Allow-Origin`
- Не совпало → блокируется **чтение ответа**

**Preflight**
- Для PUT/PATCH/DELETE, `application/json`, кастомных заголовков
- `OPTIONS` + `Access-Control-Request-Method` / `-Headers`
- Ответ: `Allow-Origin`, `Allow-Methods`, `Allow-Headers`, **`Max-Age`** (кеш preflight)

**Учётные данные**
- Клиент: `credentials: 'include'`
- Сервер: `Access-Control-Allow-Credentials: true` + **конкретный** origin
- `Allow-Origin: *` вместе с credentials **запрещено**

**Прочее**
- `Access-Control-Expose-Headers` — какие заголовки ответа видит JS
- `Vary: Origin` обязателен, если значение зависит от запроса

**«Способы обхода» — легальные механизмы**
1. Правильно настроить CORS (если сервер свой)
2. **Прокси на своём бэкенде** — SOP не действует между серверами, заодно скрывает ключи
3. Dev-прокси в Vite/webpack
4. Обратный прокси в проде: статика и `/api` под одним доменом — CORS не нужен
5. `postMessage` между окнами — **обязательно проверять `e.origin`**
6. `document.domain` — устаревший, отключается
7. JSONP — хак на `<script src>`, только GET, полный доступ к странице → не использовать
8. `--disable-web-security` — только локальная отладка

**Диагностика**
- «No Access-Control-Allow-Origin» — не настроен, или ошибка произошла до добавления заголовков, или не обработан `OPTIONS`
- Запрос выполнен, но JS получает ошибку — нормально: блокируется чтение
- Вывод: **CORS не защищает сервер**, защищают аутентификация и авторизация

**Смежные политики**
- CSP, COOP/COEP/CORP, SRI, Private Network Access

**Подробнее:** [[Same-Origin Policy]], [[CORS]]

## 6. Что такое XSS? Какие виды существуют, почему опасно вставлять ввод в HTML без экранирования и роль контекста

**Суть**
- Внедрение чужого JS в страницу, которую браузер считает легитимной
- Код выполняется **в origin сайта** с правами пользователя

**Последствия**
- Кража cookies и токенов (если нет `HttpOnly`), захват сессии
- Чтение и отправка данных со страницы
- Действия от имени пользователя, подмена интерфейса, кейлоггер
- Обход CSRF-защиты — токен читается со страницы
- Worm через пользовательский контент

**Виды**
- **Stored** — нагрузка сохранена на сервере (комментарий, имя профиля), отдаётся всем; самый опасный
- **Reflected** — нагрузка в параметре запроса отражается в ответе; нужна ссылка и переход жертвы
- **DOM-based** — сервер не участвует: данные из `location.hash`, `postMessage`, `localStorage` попадают в `innerHTML`; актуален для SPA, не виден в серверных логах
- **mXSS** — безопасная на вид разметка мутирует при парсинге, обходит наивные санитайзеры
- **Self-XSS** — социальная инженерия (вставить код в консоль)

**Почему опасна вставка без экранирования**
- В HTML данные и код не разделены: `<` начинает тег, кавычка завершает атрибут
- Строка как есть → пользователь **дописывает разметку**, переходя из данных в код (та же природа, что SQL-инъекция)
- Чёрные списки не работают: `<script>` через `innerHTML` не выполнится, но есть `onerror`, `<svg onload>`, `autofocus onfocus`, `<iframe srcdoc>`, `javascript:` в `href`

**Роль контекста — экранирование зависит от места вставки**
- **Текст HTML** — экранировать `& < > " '`, либо `textContent`
- **Атрибут** — обязательны кавычки; без них хватит пробела, чтобы дописать атрибут
- **URL в `href`/`src`** — экранирования недостаточно, нужна **валидация схемы** (отсечь `javascript:`, `data:`)
- **Внутри `<script>`** — данные не вставлять; отдавать через `<script type="application/json">` + `JSON.parse`
- **CSS** — `url()` и подобное
- **Обработчики в атрибутах** — двойной контекст, безопасного экранирования практически нет

**Защита**
1. Контекстное экранирование по умолчанию (React, Vue, Angular); люки: `dangerouslySetInnerHTML`, `v-html`, `{@html}`
2. `textContent` вместо `innerHTML`
3. **DOMPurify** с белым списком, когда разметка нужна; свой санитайзер не писать; HTML Sanitizer API (`setHTML`)
4. **CSP** на nonce/hash: `script-src 'self' 'nonce-...'`, `object-src 'none'`; `unsafe-inline` обнуляет пользу
5. **Trusted Types** — устраняют DOM XSS на уровне платформы
6. `HttpOnly` + `Secure` + `SameSite` — снижают ущерб
7. Валидация на входе как дополнение, не замена экранированию на выходе
8. `rel="noopener noreferrer"`, `sandbox` у iframe, `X-Content-Type-Options: nosniff`

**Подробнее:** [[XSS]], [[CSRF]]

## 7. Как возникает SQL injection? Роль параметризованных запросов. Приведите схему опасного и безопасного подхода

**Природа**
- Пользовательские данные **конкатенируются в текст SQL**; СУБД получает единую строку и не отличает команду от данных
- Тот же класс, что XSS: смешение кода и данных в одном канале

**Опасный подход**
```js
const q = `SELECT * FROM users WHERE email = '${email}'`;
```
```python
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")
```

**Эксплуатация**
- Обход аутентификации: `' OR '1'='1' -- ` → условие всегда истинно, остаток закомментирован
- Извлечение данных: `' UNION SELECT username, password FROM admin_users --`
- Разрушение: `'; DROP TABLE users; --` (если драйвер разрешает несколько операторов)
- Слепая: булева `' AND SUBSTRING(password,1,1)='a' --`, временная `' AND SLEEP(5) --`; автоматизируется sqlmap
- Second-order: строка сохраняется безопасно, подставляется позже без экранирования
- Последствия: утечка ПД и хешей, обход авторизации, изменение данных, иногда чтение файлов и выполнение команд ОС

**Почему ручное экранирование не работает**
- Многобайтовые кодировки, числовой контекст без кавычек (`id = 1 OR 1=1`), диалекты, разные комментарии, `CHAR(39)` и hex-литералы
- Чёрные списки обходятся всегда

**Параметризованные запросы**
- SQL и данные передаются **раздельно**: сервер разбирает шаблон и строит план, затем подставляет значения как **типизированные данные**
- Данные не могут стать частью синтаксиса; побочный плюс — кеш плана
```js
db.query('SELECT * FROM users WHERE email = $1', [email]);      // node-postgres
conn.execute('SELECT * FROM users WHERE email = ?', [email]);   // mysql2
```
```python
cur.execute("SELECT * FROM users WHERE email = %s", (email,))   # psycopg
```

**ORM**
- Параметризуют автоматически, но `raw`, `queryRawUnsafe`, `whereRaw` возвращают ответственность разработчику
- Тегированный шаблон `$queryRaw\`... ${email}\`` параметризуется, `$queryRawUnsafe` — нет

**Что нельзя параметризовать**
- Имена таблиц и столбцов, направление сортировки, иногда LIMIT
- Единственная защита — **белый список** допустимых значений

**Схема**
```
ОПАСНО:    ввод ──► конкатенация ──► одна строка SQL ──► СУБД   (код и данные смешаны)
БЕЗОПАСНО: шаблон ─────────────────► СУБД: разбор, план
           ввод ──► параметр ──────► СУБД: подстановка как ЗНАЧЕНИЕ
```

**Эшелонированная защита**
- Валидация типов; отдельная роль БД без DROP и доступа к системным таблицам
- Не показывать тексты ошибок СУБД клиенту
- Хеширование паролей (bcrypt/argon2), бэкапы, аудит
- WAF как дополнительный обходимый слой
- Статический анализ и запрет конкатенации в SQL на уровне линтера
- Тот же принцип: NoSQL, LDAP, XPath, командная строка, шаблонизаторы (SSTI)

**Подробнее:** [[SQL injection]]

## 8. Что такое CSRF? Примеры опасных ситуаций и базовые способы защиты на практике

**Суть**
- Браузер жертвы отправляет на доверенный сайт запрос, выполняющий действие от её имени

**На чём работает**
1. Cookies отправляются **автоматически** ко всем запросам к своему домену
2. SOP **не блокирует отправку** межсайтовых запросов, только чтение ответа
3. Сервер не отличает запрос со своей страницы от запроса с чужого сайта, если полагается только на cookie
- Отличие от XSS: **не нужно видеть ответ** — «слепая» атака

**Опасные ситуации**
- Автоотправляемая скрытая форма: `POST /transfer` с параметрами перевода
- **GET, меняющий состояние** — эксплуатируется тегом `<img src="/account/delete?confirm=yes">`, срабатывает при открытии страницы или письма
- Смена email или пароля → через восстановление даёт полный захват аккаунта
- Отключение 2FA, добавление доверенного устройства, смена адреса доставки
- Действия в админке
- Login CSRF — жертву логинят в аккаунт злоумышленника, чтобы записать её данные

**Защита**
1. **`SameSite`**: `Strict` — никогда межсайтово; `Lax` (по умолчанию) — только навигация верхнего уровня GET, блокирует классический CSRF; `None` требует `Secure`
2. **CSRF-токен**: случайный, привязан к сессии, в скрытом поле; работает потому, что SOP не даёт злоумышленнику **прочитать** его со страницы; сравнение constant-time, не передавать в URL
3. **Double Submit Cookie** — stateless-вариант, слабее при уязвимостях на поддоменах
4. **Проверка `Origin`/`Referer`** на сервере — `Origin` не подделывается скриптом, но иногда отсутствует → как дополнение
5. **Кастомный заголовок** в API — добавить его межсайтово можно только через fetch, а это вызовет preflight; формой не отправить
6. **Bearer-токен** вместо cookie — CSRF невозможен по определению, но появляется уязвимость к XSS при хранении в localStorage
7. **Повторная аутентификация** для критичных действий
8. Изменяющие операции — только POST/PUT/PATCH/DELETE

**Практика**
- Комбинация: `SameSite=Lax` + `HttpOnly` + `Secure` + CSRF-токен + проверка `Origin`
- Использовать готовые модули (Django, Rails, Laravel, Spring Security), не писать своё

**Связь с XSS**
- **XSS обходит любую CSRF-защиту**: скрипт на странице прочитает токен → защита от XSS первична

**Подробнее:** [[CSRF]], [[Cookies и их атрибуты]], [[Cookie fixation]]

## 9. Как работает HTTP-кэширование? Объясните Cache-Control, ETag, Last-Modified и разницу между свежестью и условным запросом

**Уровни кеша**
- Приватный кеш браузера (memory, disk)
- Общие: CDN, обратные и корпоративные прокси
- Программируемый: Service Worker + Cache API

**Свежесть vs валидация — ключевое различие**
- **Свежесть**: ресурс не истёк → используется **без обращения к сети** (0 мс, 0 байт), в DevTools `from disk cache`
- **Валидация**: ресурс истёк → **условный запрос** → `304 Not Modified` без тела → используется сохранённая копия
- Свежесть экономит **время и трафик**, валидация — **только трафик** (round-trip остаётся)

**Cache-Control**

| Директива | Смысл |
|---|---|
| `max-age=N` | свеж N секунд |
| `s-maxage=N` | то же для общих кешей |
| `public` / `private` | можно ли в общий кеш |
| `no-cache` | кешировать **можно**, но валидировать всегда |
| `no-store` | не сохранять вообще |
| `must-revalidate` | нельзя отдавать устаревшее |
| `immutable` | не валидировать даже при обновлении страницы |
| `stale-while-revalidate=N` | отдать устаревшее, обновить в фоне |
| `stale-if-error=N` | при ошибке отдать устаревшее |

- Частая путаница: `no-cache` ≠ «не кешировать», это `no-store`
- `Expires` и `Pragma` — устаревшие, `Cache-Control` приоритетнее

**ETag / If-None-Match**
- ETag — идентификатор версии, обычно хеш содержимого
- Клиент шлёт `If-None-Match` → 304 или 200 с новым телом
- Сильный `"abc"` — побайтовая идентичность, слабый `W/"abc"` — семантическая
- Дополнительно: оптимистическая блокировка через `If-Match` → 412 Precondition Failed

**Last-Modified / If-Modified-Since**
- Ограничения: точность до секунды, дата меняется при пересборке без изменения содержимого, рассинхрон часов
- **ETag точнее и приоритетнее**; Last-Modified — запасной вариант и основа эвристического кеширования

**Схема**
```
свеж?           → да → отдать из кеша, сети нет
протух?         → условный запрос → 304 (кеш) или 200 (новая версия)
нет в кеше?     → обычный запрос
```

**Стратегия для приложения**
- **Cache busting**: хеш содержимого в имени файла (`app.a3f9c2.js`)
- HTML — `no-cache` (содержит актуальные ссылки на ассеты)
- Ассеты с хешем — `max-age=31536000, immutable`
- API — `private, no-cache` + ETag; персональные данные — `no-store`
- `Vary: Accept-Encoding, Accept-Language`; не включать `User-Agent`

**Инвалидация**
- Кеш браузера **нельзя очистить с сервера** → отсюда важность cache busting
- CDN — purge по API; Service Worker — полный программный контроль

**Подробнее:** [[HTTP-кеширование]], [[Кеширование]]

## 10. Какие способы обмена данными в реальном времени вы знаете? Сравните WebSocket и SSE: сценарии и критерии выбора

**Способы**
- **Short polling** — периодический опрос; просто, но задержка = интервалу и много лишних запросов
- **Long polling** — сервер удерживает запрос; низкая задержка, проходит везде, но расходует соединения
- **SSE** — однонаправленный поток сервер → клиент поверх HTTP
- **WebSocket** — полнодуплексный канал после апгрейда
- **WebRTC DataChannel** — p2p, минимальная задержка, нужен сигнальный сервер и STUN/TURN
- **WebTransport** — поверх HTTP/3, потоки и датаграммы, нет head-of-line blocking
- **Streaming fetch** (`ReadableStream`, NDJSON) — стриминг ответа
- HTTP/2 Server Push — удалён из браузеров, не применяется

**SSE**
- Клиент — `EventSource`; сервер — `Content-Type: text/event-stream`, поля `data`, `event`, `id`, `retry`
- **Автоматическое переподключение** и **возобновление с места разрыва** через `Last-Event-ID`
- Отключить буферизацию прокси: `X-Accel-Buffering: no`

**WebSocket**
- HTTP-запрос с `Upgrade` → `101 Switching Protocols` → бинарные кадры в обе стороны
- Текст и `ArrayBuffer`/`Blob`

**Сравнение**

| | WebSocket | SSE |
|---|---|---|
| Направление | **двунаправленное** | сервер → клиент |
| Протокол | ws/wss | обычный HTTP |
| Формат | текст и **бинарные** | только UTF-8 текст |
| Переподключение | вручную | **встроено** |
| Возобновление | вручную | **`Last-Event-ID`** |
| Прокси и файрволы | иногда блокируется | проходит |
| CORS | своя модель | стандартный |
| Лимит соединений | высокий | **6 на домен в HTTP/1.1**, снимается в HTTP/2 |
| Инфраструктура | сложнее | проще |

**Когда SSE**
- Поток только от сервера: уведомления, котировки, лента, прогресс операции, логи, метрики, стриминг ответов LLM
- Действия клиента отправляются обычными POST
- Нестабильная сеть, ограниченная инфраструктура, serverless

**Когда WebSocket**
- Частый двусторонний обмен: чаты, совместное редактирование, игры, торговые терминалы, WebRTC-сигналинг
- Бинарные данные, собственный прикладной протокол

**Критерии выбора**
1. Двунаправленность с высокой частотой? → WebSocket
2. Достаточно потока от сервера? → SSE
3. Обновления раз в минуту и реже? → polling
4. Ограничения инфраструктуры? → SSE / long polling
5. Бинарные данные или p2p? → WebSocket / WebRTC

**Эксплуатация**
- Масштабирование: sticky sessions или брокер (Redis Pub/Sub, NATS, Kafka)
- Heartbeat: ping/pong у WebSocket, комментарии `: keep-alive` у SSE каждые 15–30 с
- Переподключение с экспоненциальной задержкой и джиттером
- Аутентификация: у WebSocket нельзя задать кастомные заголовки → cookie, подпротокол или первое сообщение
- **Проверять `Origin` на сервере** — SOP на WebSocket не распространяется (Cross-Site WebSocket Hijacking)
- Только `wss://`, лимит частоты и размера сообщений

**Подробнее:** [[WebSocket и SSE]], [[Обмен данными в реальном времени]]
