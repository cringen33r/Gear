## Свойства методов

Три ортогональных характеристики:

- **Безопасный (safe)** — не изменяет состояние на сервере (только чтение).
- **Идемпотентный (idempotent)** — многократное выполнение одного и того же запроса даёт тот же результат на сервере, что и однократное.
- **Кешируемый** — ответ можно кешировать.

| Метод | Назначение | Тело | Safe | Идемпотентен | Кешируем |
|---|---|---|---|---|---|
| GET | получить ресурс | нет | да | **да** | да |
| HEAD | как GET, только заголовки | нет | да | **да** | да |
| OPTIONS | узнать возможности / CORS preflight | нет | да | **да** | нет |
| POST | создать подчинённый ресурс, произвольное действие | да | нет | **нет** | редко |
| PUT | полностью заменить ресурс по известному URI | да | нет | **да** | нет |
| PATCH | частично изменить ресурс | да | нет | **не гарантирован** | нет |
| DELETE | удалить ресурс | обычно нет | нет | **да** | нет |

## Разбор ключевых различий

**GET vs POST.** GET передаёт параметры в query-строке — они видны в URL, попадают в логи, историю браузера и `Referer`, ограничены длиной (~2–8 КБ на практике); ответ кешируется; запрос можно повторить кнопкой обновления безопасно. POST передаёт данные в теле, не кешируется по умолчанию, повторная отправка вызывает предупреждение браузера. Пароли и персональные данные — только POST (и по HTTPS).

**PUT vs POST.** `PUT /users/42` — «сделай так, чтобы ресурс 42 имел это состояние»; клиент знает URI. `POST /users` — «создай нового пользователя»; URI назначает сервер и возвращает в `Location`. PUT идемпотентен: три одинаковых PUT дают то же состояние, что и один. POST — нет: три POST создадут трёх пользователей.

**PUT vs PATCH.** PUT заменяет ресурс целиком: отсутствующие поля трактуются как удалённые/сброшенные. PATCH описывает изменение: `{"age": 31}` меняет только возраст. Форматы: JSON Merge Patch (RFC 7396) и JSON Patch (RFC 6902, операции add/remove/replace).

**Почему PATCH не идемпотентен в общем случае.** `{"op":"add","path":"/tags/-","value":"new"}` при повторе добавит тег второй раз. А вот `{"age": 31}` в Merge Patch идемпотентен. Идемпотентность PATCH зависит от семантики патча, поэтому спецификация её не гарантирует.

**DELETE идемпотентен**, хотя коды ответов различаются: первый вызов вернёт 204, второй — 404. Идемпотентность про **состояние сервера**, а не про идентичность ответов: после любого числа DELETE ресурса нет.

## Почему идемпотентность важна на практике

1. **Безопасные повторы при сбоях.** Если ответ не пришёл из-за таймаута, клиент не знает, дошёл ли запрос. Идемпотентный запрос можно спокойно повторить; неидемпотентный — нет (риск двойного списания денег).
2. **Автоматические ретраи.** Библиотеки HTTP, прокси, service mesh и балансировщики по умолчанию ретраят только идемпотентные методы. Ретрай POST может продублировать заказ.
3. **Кеширование и предзагрузка.** Браузеры и прокси свободно кешируют GET; они также могут делать спекулятивную предзагрузку. Отсюда правило: **GET не должен менять состояние**. Классическая ошибка — `GET /delete?id=5`: краулер или префетчер удалит данные.
4. **Проектирование распределённых систем.** Гарантия «at least once» в очередях сообщений означает, что обработчик обязан быть идемпотентным.

## Ключи идемпотентности

Когда POST по смыслу должен быть безопасным для повтора (платежи), применяют **idempotency key**: клиент генерирует UUID и передаёт в заголовке `Idempotency-Key`. Сервер сохраняет результат первой обработки и на повторный запрос с тем же ключом возвращает сохранённый ответ, не выполняя операцию заново. Так работают API Stripe и большинство платёжных шлюзов.
