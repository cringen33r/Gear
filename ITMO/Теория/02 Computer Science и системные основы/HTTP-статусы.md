## Классы статусов

- **1xx** — информационные (`100 Continue`, `101 Switching Protocols` — используется при апгрейде на WebSocket).
- **2xx** — успех.
- **3xx** — перенаправление (`301` постоянное, `302`/`307` временное, `304 Not Modified` — валидация кеша).
- **4xx** — ошибка клиента: запрос неверен, повторять «как есть» бессмысленно.
- **5xx** — ошибка сервера: запрос, возможно, корректен, повтор может помочь.

Главный принцип: **4xx — вина клиента, 5xx — вина сервера**. От этого зависят алертинг, метрики SLA и логика ретраев.

## Разбор запрошенных кодов

**200 OK** — успешный запрос, тело содержит результат. Для GET — представление ресурса, для POST/PUT/PATCH — обновлённое состояние или результат операции. Универсальный «успех с телом».

**201 Created** — создан новый ресурс. Обязательно возвращайте заголовок `Location` с URI созданного ресурса; в теле обычно — само представление. Типично для `POST /users`.

**204 No Content** — успех, но **тела нет** и его не будет. Уместен для `DELETE`, для `PUT`, когда клиенту нечего возвращать, для операций «сохранить настройки». Клиенту не следует парсить тело. Не путайте с 200 и пустым JSON.

**400 Bad Request** — запрос **синтаксически** некорректен: битый JSON, отсутствует обязательный параметр, неверный тип. Общая ошибка «я не смог разобрать/понять запрос».

**401 Unauthorized** — на самом деле «не аутентифицирован»: учётные данные отсутствуют, недействительны или истекли. Ответ **должен** содержать `WWW-Authenticate`. Клиенту имеет смысл обновить токен и повторить.

**403 Forbidden** — «аутентифицирован, но не авторизован»: личность установлена, прав недостаточно. Повторять с теми же данными бесполезно. Иногда 403 используют вместо 404, чтобы не раскрывать существование ресурса — либо наоборот, отдают 404 для сокрытия.

**404 Not Found** — ресурс по данному URI не существует (или сервер не хочет раскрывать его существование). Применяется и к несуществующему маршруту, и к несуществующей записи.

**409 Conflict** — запрос конфликтует с **текущим состоянием** ресурса. Примеры: регистрация на уже занятый email, попытка удалить сущность, на которую есть ссылки, конфликт оптимистической блокировки (`If-Match` с устаревшим ETag), повторное подтверждение уже подтверждённого заказа. Смысл: «данные валидны, но в текущем состоянии операция невозможна».

**422 Unprocessable Content** (ранее Unprocessable Entity) — синтаксис корректен, но **семантика** нарушена: JSON распарсился, поля есть, но `email` не является email, `age` отрицателен, дата окончания раньше даты начала. Это код для **ошибок валидации бизнес-правил**.

**500 Internal Server Error** — необработанное исключение на сервере. Никогда не отдавайте 500 при ошибке ввода пользователя и **не показывайте stack trace** клиенту — это утечка информации. Каждый 500 должен попадать в мониторинг.

## 400 vs 422 vs 409

| Ситуация | Код |
|---|---|
| `{"name": ` — сломанный JSON | 400 |
| Отсутствует обязательное поле `email` | 400 или 422 (обе практики распространены) |
| `email: "не-email"` — не проходит валидацию | 422 |
| `email` уже зарегистрирован | 409 |
| Возраст −5 при правиле «≥ 0» | 422 |
| Заказ уже оплачен, повторная оплата | 409 |

Строгих обязательств спецификация не накладывает; важна **последовательность внутри одного API** и документированность.

## Другие полезные коды

- **202 Accepted** — запрос принят в асинхронную обработку; результат позже (возвращают URL для опроса статуса).
- **206 Partial Content** — ответ на `Range`-запрос (докачка, видео).
- **304 Not Modified** — ресурс не изменился, используйте кеш (тела нет).
- **405 Method Not Allowed** — маршрут есть, метод не поддерживается; обязателен заголовок `Allow`.
- **406 Not Acceptable** — сервер не может отдать формат из `Accept`.
- **410 Gone** — ресурс существовал и удалён навсегда (в отличие от 404).
- **415 Unsupported Media Type** — неподдерживаемый `Content-Type` запроса.
- **418 I'm a teapot** — шуточный, из первоапрельского RFC.
- **429 Too Many Requests** — превышен rate limit; отдавайте `Retry-After`.
- **501 Not Implemented**, **502 Bad Gateway**, **503 Service Unavailable** (перегрузка/обслуживание, тоже с `Retry-After`), **504 Gateway Timeout**.

## Формат тела ошибки

Стандартизованный подход — **RFC 9457 Problem Details** (`application/problem+json`):

```json
{
  "type": "https://example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "Field 'email' must be a valid email address",
  "instance": "/api/users",
  "errors": [{ "field": "email", "code": "format" }]
}
```

Правила: статус должен быть машиночитаемым, тело — содержать код ошибки для программной обработки и человекочитаемое описание; не раскрывать внутренние детали (SQL-запросы, пути файлов, версии ПО).

## Частые ошибки

- Всегда отдавать 200 и класть ошибку в тело (`{"success": false}`) — ломает кеширование, мониторинг и клиентские библиотеки.
- Отдавать 500 при некорректном вводе — искажает метрики надёжности и вызывает ложные алерты.
- Использовать 401 вместо 403 и наоборот.
- Возвращать 200 на создание вместо 201 без `Location`.
- Отдавать тело с 204.
