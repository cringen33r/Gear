## Индексы: зачем

Без индекса СУБД выполняет **полное сканирование таблицы (seq scan)** — O(n) чтений. Индекс — отдельная структура, хранящая значения столбца в упорядоченном виде вместе со ссылками на строки. Поиск по индексу — **O(log n)**.

Аналогия: индекс в книге. Найти упоминание слова можно, перелистав все страницы (seq scan), а можно по алфавитному указателю (index scan).

## B+-дерево — основная структура

Большинство индексов — **B+-деревья**: сбалансированные многопутевые деревья, где узел равен странице диска (обычно 4–8 КБ) и содержит сотни ключей. Высота дерева для миллионов строк — 3–4 уровня, то есть 3–4 обращения к диску вместо миллионов.

Ключевые свойства:

- Все данные — в листьях, листья связаны в **двусвязный список** → эффективные диапазонные запросы и `ORDER BY`.
- Индекс поддерживает: точный поиск (`=`), диапазоны (`<`, `>`, `BETWEEN`), префиксный `LIKE 'abc%'`, сортировку, `MIN`/`MAX`.
- Индекс **не помогает** при `LIKE '%abc'`, при вычислениях над столбцом (`WHERE YEAR(created_at) = 2024` — нужен индекс по выражению) и при неявном приведении типов.

## Другие типы индексов

- **Hash** — только равенство, O(1), нет диапазонов.
- **GiST / GIN** (PostgreSQL) — полнотекстовый поиск, JSONB, массивы, геоданные.
- **BRIN** — компактный индекс для больших таблиц с естественной упорядоченностью (логи по времени).
- **Bitmap** — для столбцов малой кардинальности в аналитических СУБД.

## Составные и покрывающие индексы

Составной индекс `(a, b, c)` работает по **принципу левого префикса**: он полезен для условий по `a`, `(a, b)`, `(a, b, c)`, но не для `b` или `c` по отдельности. Порядок столбцов важен: сначала те, что используются с равенством, затем диапазонные.

**Покрывающий индекс** содержит все столбцы, нужные запросу, — тогда СУБД читает только индекс и не обращается к таблице (index-only scan). Мощная оптимизация для «горячих» запросов.

**Кластеризованный индекс** (InnoDB в MySQL) физически хранит строки в порядке первичного ключа; вторичные индексы ссылаются на PK. В PostgreSQL все индексы вторичные, строки лежат в heap.

## Почему индекс замедляет запись

При каждом `INSERT`, `UPDATE` (затронутых столбцов) и `DELETE` СУБД обязана поддерживать **все** индексы таблицы в согласованном состоянии:

1. Найти место в B+-дереве — O(log n).
2. Вставить запись; при переполнении страницы — **расщепление узла**, возможно каскадное вверх по дереву.
3. Записать изменения в WAL (журнал) — дополнительный ввод-вывод.
4. При удалении — пометить запись и позже собрать мусор (VACUUM в PostgreSQL).
5. Всё это ещё и под блокировками, что снижает параллелизм.

Итог: таблица с 8 индексами делает при вставке 9 операций записи вместо одной. На нагруженной OLTP-системе это заметно. Кроме того, индексы занимают место на диске и вытесняют полезные данные из кеша (shared buffers).

**Правило: индексируйте то, по чему часто ищете, но не создавайте индексы «на всякий случай».** Неиспользуемые индексы — чистые потери. В PostgreSQL их видно в `pg_stat_user_indexes` (`idx_scan = 0`).

## Что индексировать в первую очередь

- Первичные ключи (индексируются автоматически).
- **Внешние ключи** — критично для JOIN и для проверок при удалении родителя.
- Столбцы в `WHERE`, `JOIN ... ON`, `ORDER BY`, `GROUP BY` частых запросов.
- Столбцы с **высокой селективностью**. Индекс по полю `gender` (2 значения) бесполезен: планировщик всё равно выберет seq scan, потому что он дешевле.

## Диагностика

`EXPLAIN ANALYZE` показывает план запроса: используется ли индекс (`Index Scan` / `Bitmap Index Scan`) или идёт `Seq Scan`, каковы оценки и фактические строки, где расходуется время. Это основной инструмент оптимизации.

Типичная проблема, решаемая индексами и переписыванием запроса, — **N+1**: приложение делает один запрос за списком и по одному запросу на каждый элемент. Лечится JOIN, `IN (...)` или eager loading в ORM.
