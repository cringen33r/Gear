## 0. Разбор строки и подготовка

Браузер решает, что введено — поисковый запрос или URL. URL разбирается на компоненты:

```
https://example.com:443/path/page?q=1#section
scheme  host        port path  query  fragment
```

Проверяется список **HSTS** (HTTP Strict Transport Security): если домен в нём, схема `http` принудительно заменяется на `https` ещё до отправки запроса. Хост нормализуется (Punycode для не-ASCII доменов).

## 1. Разрешение имени (DNS)

Нужно получить IP-адрес. Поиск идёт по кешам, от ближайшего к дальнему:

1. **Кеш браузера** (в Chrome — `chrome://net-internals/#dns`).
2. **Кеш ОС** и файл `hosts`.
3. **Кеш DNS-резолвера** провайдера или публичного (8.8.8.8, 1.1.1.1).
4. **Рекурсивный обход**: корневые серверы (`.`) → TLD-серверы (`.com`) → авторитативный сервер зоны (`example.com`) → ответ A/AAAA-записью.

DNS обычно работает по UDP-порту 53; современные варианты — **DoH** (DNS over HTTPS) и **DoT**, скрывающие запросы от посредников. У каждой записи есть **TTL**, определяющий время кеширования. Ответ может быть CNAME (алиас) — тогда резолвинг продолжается.

Оптимизации: `<link rel="dns-prefetch">` и `<link rel="preconnect">` позволяют разрешить имя и установить соединение заранее.

## 2. Установление соединения

**TCP-хендшейк** (три пакета: SYN → SYN-ACK → ACK) — один RTT. Для HTTP/3 вместо TCP используется **QUIC поверх UDP**, где транспортное и криптографическое рукопожатие совмещены (0-RTT/1-RTT).

**TLS-хендшейк** (для HTTPS): согласование версии и шифронабора, отправка сертификата сервера, проверка цепочки доверия до корневого CA, проверка срока действия, соответствия домену и статуса отзыва (OCSP stapling), обмен ключами (обычно ECDHE — даёт forward secrecy), переход на симметричное шифрование (AES-GCM/ChaCha20). TLS 1.3 требует 1 RTT, при возобновлении сессии — 0 RTT.

В расширении ALPN согласуется протокол приложения: `h2`, `h3` или `http/1.1`. SNI сообщает серверу, какой домен запрашивается (важно при нескольких сайтах на одном IP).

## 3. HTTP-запрос

Браузер отправляет запрос:

```
GET /path/page?q=1 HTTP/2
Host: example.com
User-Agent: ...
Accept: text/html,application/xhtml+xml,...
Accept-Encoding: gzip, br
Cookie: ...
```

Заметьте: **фрагмент `#section` на сервер не отправляется** — он обрабатывается только на клиенте.

Перед сетевым запросом браузер проверяет кеши: **Service Worker** (может ответить сам), **HTTP-кеш** (memory/disk cache). Если ресурс свежий — сеть не задействуется вовсе; если протух, но есть валидаторы — отправляется условный запрос (см. блок 04, вопрос 9).

## 4. Обработка на сервере

Запрос проходит через балансировщик/CDN, обратный прокси (nginx), приложение, БД, кеши. Возвращается статус, заголовки и тело. Возможен редирект (301/302/307) — браузер повторяет процесс для нового URL.

## 5. Ответ и начало обработки

Ответ приходит **потоково**, порциями TCP-сегментов. Браузер определяет тип по `Content-Type` (а не по расширению) и, если это `text/html`, запускает парсер, **не дожидаясь конца ответа** (streaming parsing).
