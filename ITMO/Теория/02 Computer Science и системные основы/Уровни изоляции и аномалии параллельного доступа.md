## Проблемы параллельного доступа

**Грязное чтение (dirty read)** — транзакция читает данные, записанные другой, ещё не закоммиченной транзакцией. Если та откатится, прочитанное никогда не существовало.

**Неповторяющееся чтение (non-repeatable read)** — одна и та же строка, прочитанная дважды внутри транзакции, даёт разные значения, потому что между чтениями другая транзакция её изменила и закоммитила.

**Фантомное чтение (phantom read)** — повторный запрос по тому же условию возвращает **новые строки**, добавленные другой транзакцией. Отличается от предыдущего тем, что меняется набор строк, а не значение конкретной.

**Потерянное обновление (lost update)** — две транзакции читают значение, каждая вычисляет новое и записывает; одно из обновлений теряется. Классический случай: «прочитал баланс 100, прибавил 50, записал 150» — параллельно то же сделала другая транзакция, итог 150 вместо 200.

**Аномалия записи (write skew)** — обе транзакции читают согласованное состояние и пишут в разные строки, нарушая инвариант, который проверяли (например, «хотя бы один врач на дежурстве» — оба уходят одновременно).

## Уровни изоляции (SQL-стандарт)

| Уровень | Dirty read | Non-repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | возможно | возможно | возможно |
| READ COMMITTED | нет | возможно | возможно |
| REPEATABLE READ | нет | нет | возможно* |
| SERIALIZABLE | нет | нет | нет |

\* В PostgreSQL уровень REPEATABLE READ реализован через snapshot isolation и фантомы не допускает; в MySQL InnoDB — через next-key locks.

Умолчания различаются: PostgreSQL, Oracle, SQL Server — READ COMMITTED; MySQL InnoDB — REPEATABLE READ.

Чем строже изоляция, тем ниже параллелизм и выше вероятность откатов из-за конфликтов сериализации. SERIALIZABLE в PostgreSQL (SSI) требует от приложения готовности повторить транзакцию при ошибке сериализации.

## Механизмы реализации

**Блокировки (2PL)** — разделяемые (S) на чтение и монопольные (X) на запись; удерживаются до конца транзакции. Возможны **взаимоблокировки (deadlock)**, которые СУБД обнаруживает и разрывает, откатывая одну из транзакций. Профилактика: одинаковый порядок захвата ресурсов, короткие транзакции.

**MVCC (многоверсионность)** — вместо блокировок хранятся версии строк; читатели видят снимок на момент начала транзакции. **Читатели не блокируют писателей, писатели не блокируют читателей** — основа производительности PostgreSQL, Oracle, MySQL InnoDB. Плата — рост числа мёртвых версий и необходимость их очистки (VACUUM).

## Оптимистическая и пессимистическая блокировка

**Пессимистическая:** `SELECT ... FOR UPDATE` — строка блокируется на время транзакции. Подходит при высокой конкуренции.

**Оптимистическая:** в таблице хранится `version` или `updated_at`; обновление выполняется с условием `WHERE version = :read_version`, и если затронуто 0 строк — кто-то опередил, нужно перечитать и повторить. В HTTP-API аналог — `ETag` + `If-Match` с ответом 409.
