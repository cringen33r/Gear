## Назначение формы

`<form>` — механизм сбора пользовательского ввода и отправки его на сервер. Это единственный способ отправить данные без JavaScript, поэтому формы работают всегда: при отключённом JS, в поисковых роботах, в вспомогательных технологиях.

```html
<form action="/api/login" method="post">
  <label for="email">Электронная почта</label>
  <input type="email" id="email" name="email" required autocomplete="email">

  <label for="password">Пароль</label>
  <input type="password" id="password" name="password" required
         minlength="8" autocomplete="current-password">

  <button type="submit">Войти</button>
</form>
```

## `<form>` и его атрибуты

**`action`** — URL, куда отправляются данные. Пустое значение или отсутствие означает «текущий URL». Может быть относительным или абсолютным.

**`method`** — HTTP-метод. Нативно поддерживаются только `GET` и `POST` (а также `dialog` для форм внутри `<dialog>`). PUT/PATCH/DELETE через HTML-форму отправить нельзя — нужен `fetch` или method override на сервере.

- **GET**: данные кодируются в query-строку URL (`/search?q=книги&page=2`). Подходит для поиска и фильтров: результат можно сохранить в закладки, отправить ссылкой, обновить страницу без предупреждения. Ограничение длины URL, данные видны в истории и логах.
- **POST**: данные передаются в теле запроса. Нужен для изменяющих операций, больших объёмов и чувствительных данных.

**`enctype`** — кодировка тела для POST:
- `application/x-www-form-urlencoded` (по умолчанию) — пары `key=value&key2=value2` с процентным кодированием;
- `multipart/form-data` — **обязателен для загрузки файлов**;
- `text/plain` — почти не используется.

**`novalidate`** — отключает встроенную валидацию браузера.

**`target`** — куда открыть ответ (`_self`, `_blank`).

**`autocomplete`** — `on`/`off` для всей формы.

## `<input>` и другие элементы управления

`<input>` — основной элемент ввода; поведение задаётся атрибутом `type`:

`text`, `email`, `password`, `number`, `tel`, `url`, `search`, `date`, `time`, `datetime-local`, `month`, `week`, `color`, `range`, `file`, `checkbox`, `radio`, `hidden`, `submit`, `reset`, `button`.

Правильный `type` даёт: подходящую экранную клавиатуру на мобильных, встроенную валидацию, нативный виджет (календарь, палитра), корректную работу автозаполнения.

Другие элементы: `<textarea>` (многострочный текст), `<select>`/`<option>`/`<optgroup>` (выбор из списка), `<output>` (результат вычисления), `<fieldset>` + `<legend>` (группировка со смысловым заголовком — критично для доступности радиогрупп), `<datalist>` (подсказки для input).

## `name` — ключ данных

**`name` — самый важный атрибут поля.** Без него значение **не будет отправлено** вообще. Именно `name` становится ключом в query-строке или в теле запроса:

```html
<input name="email" value="a@b.c">   →   email=a%40b.c
```

Особенности:

- Для **радиокнопок** одинаковый `name` объединяет их в группу с взаимоисключающим выбором.
- Для **чекбоксов** одинаковый `name` даёт массив значений (`tags=a&tags=b`); отмеченный чекбокс без `value` отправляет `on`.
- **Неотмеченные** чекбоксы и радиокнопки не отправляются вовсе — на сервере это `undefined`, а не `false`. Обходной приём — скрытое поле с тем же именем перед чекбоксом.
- **Отключённые** (`disabled`) поля не отправляются; `readonly` — отправляются.
- Синтаксис вида `name="user[address][city]"` понимают многие серверные фреймворки (PHP, Rails), превращая его во вложенные структуры.

## `value` — значение поля

Начальное значение элемента и то, что уйдёт на сервер.

- Для `text`/`email`/`hidden` — содержимое поля.
- Для `checkbox`/`radio` — значение, отправляемое **при выборе**.
- Для `<option>` — значение пункта (если не указано, берётся текст).
- Для `<button type="submit" name="action" value="save">` — позволяет узнать, **какой именно кнопкой** отправлена форма.
- Для `<textarea>` значение задаётся содержимым тега, а не атрибутом.

Важно различать HTML-атрибут `value` (начальное значение, `defaultValue` в DOM) и свойство `input.value` (текущее). Именно поэтому в React есть контролируемые компоненты (`value` + `onChange`) и `defaultValue` для неконтролируемых.

## `<label>` — связь подписи и поля

Метка делает интерфейс доступным и удобным. Два способа связывания:

```html
<!-- явный: for указывает на id поля -->
<label for="name">Имя</label>
<input id="name" name="name">

<!-- неявный: поле внутри метки -->
<label>Имя <input name="name"></label>
```

Что даёт `<label>`:

- **Скринридер** объявляет подпись при фокусе на поле. Без метки пользователь слышит просто «поле ввода».
- **Клик по подписи** переводит фокус в поле, а для чекбокса/радио — переключает его. Это заметно увеличивает область попадания, особенно на мобильных.
- Формирует **доступное имя** элемента для программной идентификации и тестов.

`placeholder` **не заменяет** метку: он исчезает при вводе, имеет низкий контраст и не читается некоторыми вспомогательными технологиями.

## `<button>`

Три значения `type`:

- **`submit`** (по умолчанию внутри формы) — отправляет форму;
- **`reset`** — сбрасывает поля к начальным значениям (используется редко, легко нажать по ошибке);
- **`button`** — ничего не делает сама, для JS-обработчиков.

Частая ошибка — забыть `type="button"` у кнопки-помощника внутри формы: браузер посчитает её submit-кнопкой и отправит форму.

`<button>` предпочтительнее `<input type="submit">`: внутрь можно вложить разметку (иконку, span), проще стилизовать. И то и другое предпочтительнее `<div onclick>`, который не фокусируется, не активируется с клавиатуры и не объявляется как кнопка.

Атрибут `formaction`/`formmethod` на кнопке переопределяет `action`/`method` формы — удобно для «Сохранить» и «Сохранить и опубликовать».

## Отправка и валидация

**Способы отправки:** клик по submit-кнопке, `Enter` в текстовом поле (если submit-кнопка есть), `form.requestSubmit()` из JS (в отличие от `form.submit()`, запускает валидацию и событие `submit`).

**Встроенная валидация (Constraint Validation API):** `required`, `min`, `max`, `minlength`, `maxlength`, `pattern`, `step`, а также семантика типа (`type="email"`). Браузер блокирует отправку и показывает подсказку. Стилизация: псевдоклассы `:valid`, `:invalid`, `:user-invalid` (срабатывает только после взаимодействия — лучше для UX), `:required`.

Программный контроль:

```js
input.setCustomValidity('Пароли не совпадают');
form.checkValidity();      // булев результат
form.reportValidity();     // показать сообщения
input.validity.tooShort;   // детали
```

**Валидация на клиенте — это удобство, а не безопасность.** Сервер обязан проверять всё заново: HTTP-запрос можно отправить в обход формы.

## Отправка через JavaScript

```js
form.addEventListener('submit', async (e) => {
  e.preventDefault();
  const data = new FormData(form);          // собирает поля по name
  const res = await fetch(form.action, { method: 'POST', body: data });
  // для JSON: body: JSON.stringify(Object.fromEntries(data))
  //           headers: { 'Content-Type': 'application/json' }
});
```

`FormData` автоматически выставляет `multipart/form-data` с корректным boundary — заголовок `Content-Type` руками задавать не нужно.

## Практические рекомендации

- Всегда использовать `<form>`, даже в SPA: это даёт отправку по Enter, семантику и работу без JS.
- Всегда указывать `name` и связывать `<label>`.
- Правильный `type` и `autocomplete` (`email`, `current-password`, `one-time-code`, `postal-code`) — заметно ускоряют заполнение.
- `inputmode="numeric"` для числовых кодов вместо `type="number"` (у последнего есть стрелки и проблемы с ведущими нулями).
- Ошибки показывать рядом с полем и связывать через `aria-describedby` (см. блок 05).
- Не полагаться на `placeholder` как на подпись.
- Защита от CSRF для изменяющих форм (см. вопрос 8).
