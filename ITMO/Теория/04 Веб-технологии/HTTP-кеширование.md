## Зачем

Кэширование убирает лишние сетевые обращения: снижает задержку, нагрузку на сервер и трафик. Уровни кеша:

- **приватный кеш браузера** (memory cache, disk cache);
- **общие кеши**: CDN, обратные прокси, корпоративные прокси;
- **Service Worker / Cache API** — программируемый кеш под контролем приложения.

## Две принципиально разные ситуации

**1. Свежесть (freshness).** Если ресурс в кеше ещё «свеж», браузер использует его **вообще без обращения к сети**. Это самый быстрый путь: 0 мс, 0 байт. В DevTools отображается как `(from disk cache)` или `(memory cache)`.

**2. Валидация (условный запрос).** Если ресурс «протух», браузер не выбрасывает его, а спрашивает сервер: «изменился ли он?» Если нет — сервер отвечает **304 Not Modified без тела**, и браузер использует сохранённую копию. Экономится трафик, но один round-trip всё равно происходит.

Свежесть экономит **время и трафик**; валидация — **только трафик**.

## Cache-Control

Основной заголовок управления кешированием.

**Директивы ответа:**

| Директива | Значение |
|---|---|
| `max-age=3600` | ресурс свеж 3600 секунд с момента получения |
| `s-maxage=600` | то же, но для **общих** кешей (CDN); переопределяет `max-age` |
| `public` | можно кешировать в общих кешах даже при наличии авторизации |
| `private` | только приватный кеш браузера (персонализированный ответ) |
| `no-cache` | кешировать **можно**, но перед каждым использованием обязательна валидация |
| `no-store` | **не сохранять вообще** — для чувствительных данных |
| `must-revalidate` | по истечении срока обязательна валидация, отдавать устаревшее нельзя |
| `immutable` | ресурс никогда не изменится — не валидировать даже при обновлении страницы |
| `stale-while-revalidate=60` | отдать устаревшее сразу, обновить в фоне |
| `stale-if-error=86400` | при ошибке сервера отдать устаревшее |

Частая путаница: **`no-cache` не значит «не кешировать»** — это «кешируй, но всегда проверяй». «Не кешировать» — это `no-store`.

Типичные конфигурации:

```
# HTML — всегда актуальный
Cache-Control: no-cache

# Статика с хешем в имени (app.a3f9c2.js)
Cache-Control: public, max-age=31536000, immutable

# Персональный API-ответ
Cache-Control: private, max-age=0, must-revalidate

# Секреты, банковские данные
Cache-Control: no-store
```

Устаревшие механизмы: `Expires` (абсолютная дата, зависит от часов клиента) и `Pragma: no-cache` — поддерживаются ради совместимости, но `Cache-Control` имеет приоритет.

## ETag и If-None-Match

**ETag** — идентификатор конкретной версии ресурса (обычно хеш содержимого):

```
HTTP/1.1 200 OK
ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"
Cache-Control: max-age=60
```

При следующем запросе после истечения свежести:

```
GET /style.css
If-None-Match: "33a64df551425fcc55e4d42a148795d9f25f89d4"
```

Ответ сервера:
- **304 Not Modified** (без тела) — версия совпала, используйте кеш;
- **200 OK** с новым телом и новым ETag — ресурс изменился.

Виды: **сильный** ETag (`"abc"`) — побайтовая идентичность; **слабый** (`W/"abc"`) — семантическая эквивалентность (допустимы незначительные отличия).

ETag также применяется для **оптимистической блокировки** в API: клиент отправляет `If-Match: "abc"` при обновлении, и сервер отвечает **412 Precondition Failed** (или 409), если ресурс успели изменить.

## Last-Modified и If-Modified-Since

Более старый механизм, основанный на времени:

```
Last-Modified: Wed, 21 Oct 2025 07:28:00 GMT
```

```
GET /style.css
If-Modified-Since: Wed, 21 Oct 2025 07:28:00 GMT
```

Ограничения: **точность до секунды** (изменения в пределах секунды не обнаружатся), дата может измениться при пересборке или деплое без изменения содержимого, проблемы с синхронизацией часов и с динамически генерируемым контентом.

**ETag точнее и приоритетнее.** Если сервер прислал оба заголовка, браузер отправляет оба условия, но `If-None-Match` имеет приоритет. Last-Modified полезен как запасной вариант и для эвристического кеширования (когда `Cache-Control` отсутствует, браузер может считать ресурс свежим примерно 10 % от времени с момента последнего изменения).

## Полная схема

```
Запрос ресурса
   │
   ├─ Есть в кеше и свеж (max-age не истёк)?
   │     └─ ДА → отдать из кеша. Сети НЕТ. (200 from cache)
   │
   ├─ Есть в кеше, но протух?
   │     └─ Условный запрос (If-None-Match / If-Modified-Since)
   │           ├─ 304 → обновить метаданные, отдать из кеша (трафик ~0)
   │           └─ 200 → сохранить новую версию и отдать
   │
   └─ Нет в кеше → обычный запрос (200 с телом)
```

## Стратегия кеширования для веб-приложения

**Cache busting** — фундаментальный приём: имя файла содержит хеш содержимого (`app.a3f9c2.js`). Тогда:

- **HTML** — `no-cache`: всегда проверяется, содержит актуальные ссылки на ассеты;
- **JS/CSS/шрифты/изображения с хешем** — `max-age=31536000, immutable`: год в кеше без единого запроса. При изменении содержимого меняется имя, то есть URL — коллизий не бывает;
- **API-ответы** — `private, no-cache` с ETag, или короткий `max-age` для редко меняющихся справочников;
- **Пользовательские данные** — `private`, часто `no-store`.

`Vary` сообщает кешам, от каких заголовков запроса зависит ответ:

```
Vary: Accept-Encoding, Accept-Language
```

Без него кеш может отдать сжатый ответ клиенту, не поддерживающему сжатие, или русскую версию англоязычному пользователю. Не включайте в `Vary` заголовки с высокой вариативностью (`User-Agent`) — это убивает эффективность кеша.

## Инвалидация

Кеш браузера **нельзя очистить с сервера** — отсюда важность cache busting. Для CDN доступны purge/invalidate по API. Service Worker даёт полный программный контроль: стратегии cache-first, network-first, stale-while-revalidate реализуются явно.

## Диагностика

DevTools → Network: колонка Size показывает `(disk cache)`, `(memory cache)` или размер; статус 304 виден явно. Полезно снять галочку «Disable cache», иначе поведение будет нереалистичным. Заголовки ответа и запроса показывают, какие директивы и валидаторы реально применяются.
