## Обзор технологий

**1. Short polling.** Клиент периодически опрашивает сервер (`setInterval` + `fetch`). Просто, работает везде, но: задержка до интервала опроса, много бесполезных запросов, нагрузка растёт линейно с числом клиентов. Приемлемо для редких обновлений и небольшой аудитории.

**2. Long polling.** Сервер **удерживает** запрос открытым, пока не появятся данные или не истечёт таймаут; клиент сразу открывает следующий. Задержка близка к нулю, работает через любые прокси. Минусы: расход соединений и памяти сервера, накладные расходы на переустановку запроса, сложность с балансировщиками.

**3. Server-Sent Events (SSE).** Однонаправленный поток «сервер → клиент» поверх обычного HTTP. Стандартный API `EventSource`, автоматическое переподключение, текстовый формат.

**4. WebSocket.** Полнодуплексный двунаправленный канал поверх TCP после HTTP-апгрейда. Отдельный протокол (`ws://`/`wss://`).

**5. WebRTC (DataChannel).** Peer-to-peer соединение с минимальной задержкой, поверх UDP. Для видео/аудио и игр; требует сигнального сервера, STUN/TURN.

**6. WebTransport** — современный транспорт поверх HTTP/3 (QUIC): несколько потоков, ненадёжная доставка датаграмм, отсутствие head-of-line blocking. Поддержка пока частичная.

**7. HTTP/2 Server Push** — фактически объявлен устаревшим и удалён из браузеров; для реального времени не применяется.

**8. Streaming fetch** (`ReadableStream`, NDJSON, gRPC-Web) — потоковое чтение ответа; используется, например, для стриминга токенов LLM.

## Критерии выбора: практический алгоритм

1. **Нужна ли двунаправленность с высокой частотой?** Да → WebSocket. Нет → продолжить.
2. **Достаточно ли потока от сервера?** Да → SSE.
3. **Насколько редки обновления?** Раз в минуту и реже → достаточно обычного polling.
4. **Есть ли ограничения инфраструктуры** (прокси, корпоративные сети, serverless-хостинг без долгих соединений)? → SSE или long polling.
5. **Нужны бинарные данные или p2p?** → WebSocket или WebRTC.

## Практические аспекты

**Масштабирование.** Постоянные соединения привязаны к конкретному инстансу сервера, поэтому нужны sticky sessions или брокер (Redis Pub/Sub, NATS, Kafka) для рассылки между инстансами. Соединения потребляют файловые дескрипторы и память — планируйте лимиты.

**Heartbeat.** Прокси и балансировщики разрывают «тихие» соединения. Для WebSocket — ping/pong кадры; для SSE — периодические комментарии (`: keep-alive\n\n`) каждые 15–30 секунд.

**Переподключение.** Для WebSocket реализуйте экспоненциальную задержку с джиттером, чтобы после сбоя сервера тысячи клиентов не ударили одновременно.

**Аутентификация.** У WebSocket нельзя задать кастомные заголовки при подключении — передавайте токен через cookie, подпротокол или первое сообщение после установления соединения; **обязательно проверяйте `Origin` на сервере** (SOP на WebSocket не распространяется, отсюда угроза Cross-Site WebSocket Hijacking).

**Безопасность.** Всегда `wss://` и `https://`; ограничение частоты сообщений; валидация каждого входящего сообщения; ограничение размера кадра.

**Библиотеки.** Socket.IO (WebSocket с автоматическим fallback на long polling, комнаты, переподключение), ws и uWebSockets.js (низкоуровневые, быстрые), SignalR (.NET), Phoenix Channels (Elixir), Centrifugo (готовый сервер реального времени), Pusher/Ably (управляемые сервисы).
