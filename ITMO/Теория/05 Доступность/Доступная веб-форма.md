## Почему формы критичны

Формы — точка, где пользователь совершает целевое действие: вход, оплата, запись, отправка заявки. Недоступная форма означает, что человек не может воспользоваться сервисом вообще. Кроме того, форма — место, где пользователь наиболее уязвим к ошибкам, поэтому WCAG выделяет для неё отдельную группу критериев (3.3.1–3.3.4).

## Полный пример

```html
<form novalidate>
  <div class="field">
    <label for="email">Электронная почта</label>

    <p id="email-hint" class="hint">
      Например, name@example.com. Мы отправим на неё чек.
    </p>

    <input
      type="email"
      id="email"
      name="email"
      required
      autocomplete="email"
      aria-describedby="email-hint email-error"
      aria-invalid="false"
    >

    <p id="email-error" class="error" role="alert" hidden>
      Введите адрес в формате name@example.com
    </p>
  </div>

  <button type="submit">Отправить</button>
</form>
```

Разберём, как связаны элементы.

## 1. Метка (label) — обязательна

Каждое поле должно иметь программно связанную метку.

```html
<!-- Явная связь: for = id -->
<label for="phone">Телефон</label>
<input id="phone" name="phone">

<!-- Неявная: поле внутри метки -->
<label>Телефон <input name="phone"></label>
```

Что это даёт:

- скринридер объявляет подпись при получении фокуса;
- клик по подписи переводит фокус в поле (для чекбоксов — переключает), увеличивая область попадания — важно при тремоле и на мобильных;
- формируется доступное имя для голосового управления.

**`placeholder` не является меткой** (частая ошибка): он исчезает при вводе, имеет низкий контраст, не переводится частью инструментов, теряется при автозаполнении и создаёт когнитивную нагрузку («что я тут ввожу?»). Placeholder допустим только как **дополнение** к метке, для примера формата.

Если по дизайну метка не должна быть видна — прячьте её визуально, но оставляйте в DOM (класс `.visually-hidden` из первого вопроса), либо в крайнем случае используйте `aria-label`.

**Плавающие метки (floating label)** допустимы, если это настоящий `<label>`, который сдвигается, а не исчезает.

Метка должна **сохраняться при масштабировании и на узких экранах** и находиться рядом с полем — обычно над ним (лучше всего для мобильных и для пользователей экранной лупы).

## 2. Подсказка — `aria-describedby`

Дополнительная информация (формат, требования к паролю, пояснение) связывается через `aria-describedby`:

```html
<label for="pwd">Пароль</label>
<p id="pwd-hint">Минимум 8 символов, хотя бы одна цифра</p>
<input type="password" id="pwd" aria-describedby="pwd-hint" autocomplete="new-password">
```

Скринридер прочитает: «Пароль, поле ввода пароля, минимум 8 символов, хотя бы одна цифра».

Важно: `aria-describedby` принимает **список id через пробел** — так одно поле связывается сразу с подсказкой и с сообщением об ошибке. `aria-labelledby` задаёт имя (что это), `aria-describedby` — описание (подробности); имя объявляется первым и всегда, описание — после паузы.

Требования к формату должны быть видны **до** ввода, а не появляться только в виде ошибки (WCAG 3.3.2 «Инструкции»).

## 3. Обязательность

```html
<input id="name" required aria-required="true">
<label for="name">Имя <span aria-hidden="true">*</span>
  <span class="visually-hidden">обязательное поле</span>
</label>
```

Нативный `required` уже сообщается вспомогательным технологиям, `aria-required` нужен лишь для кастомных элементов. Звёздочку следует расшифровать текстом — символ `*` сам по себе может быть прочитан как «звёздочка» или пропущен.

## 6. Момент валидации

- **Не проверяйте поле на каждом нажатии клавиши** — сообщения «неверный email» во время набора мешают и порождают шум в live region.
- Оптимально: проверка **при потере фокуса** (`blur`) для формата и **при отправке** для всей формы; после первой ошибки — повторная проверка на `input`, чтобы пользователь видел исчезновение ошибки при исправлении.
- CSS-псевдокласс `:user-invalid` (в отличие от `:invalid`) срабатывает только после взаимодействия — как раз то, что нужно.
- Не блокируйте ввод символов молча: пользователь не поймёт, почему клавиши «не работают».

## 7. Группировка полей

Радиокнопки и чекбоксы объединяются в группу с общим вопросом:

```html
<fieldset>
  <legend>Способ доставки</legend>

  <input type="radio" id="d1" name="delivery" value="courier" checked>
  <label for="d1">Курьер</label>

  <input type="radio" id="d2" name="delivery" value="pickup">
  <label for="d2">Самовывоз</label>
</fieldset>
```

`<legend>` объявляется скринридером вместе с каждым вариантом: «Способ доставки, Курьер, переключатель, выбран, 1 из 2». Без группировки пользователь слышит только «Курьер» и не понимает, к какому вопросу это относится.

Альтернатива для кастомных групп — `role="group"` или `role="radiogroup"` с `aria-labelledby`.

## 8. Автозаполнение и типы полей

```html
<input type="email"  autocomplete="email">
<input type="tel"    autocomplete="tel"    inputmode="tel">
<input type="text"   autocomplete="name">
<input type="text"   autocomplete="street-address">
<input type="text"   autocomplete="postal-code" inputmode="numeric">
<input type="password" autocomplete="current-password">
<input type="text"   autocomplete="one-time-code" inputmode="numeric">
```

WCAG 1.3.5 («Identify Input Purpose», уровень AA) прямо требует указывать `autocomplete` для полей, собирающих данные о пользователе. Это помогает людям с когнитивными нарушениями и моторными ограничениями, а также ускоряет заполнение для всех.

Правильный `type` даёт подходящую клавиатуру на мобильных и встроенную валидацию. Для числовых кодов предпочтительнее `type="text" inputmode="numeric" pattern="[0-9]*"`, чем `type="number"` (у последнего есть стрелки, проблемы с ведущими нулями и случайное изменение колесом мыши).

## 9. Достаточное время и предотвращение потерь

- **WCAG 2.2.1**: если у формы есть таймаут (сессия, бронирование), предупредите и дайте возможность продлить.
- **WCAG 3.3.4 / 3.3.6**: для действий с юридическими или финансовыми последствиями обеспечьте возможность отменить, проверить введённое или подтвердить.
- Сохраняйте введённые данные при ошибке — не заставляйте заполнять форму заново.
- **WCAG 2.2, критерий 3.3.7 «Redundant Entry»**: не требуйте повторного ввода той же информации в рамках одного процесса.
- **WCAG 2.2, критерий 3.3.8 «Accessible Authentication»**: не требуйте когнитивных тестов (запомнить и ввести, распознать картинки) без альтернативы; разрешайте вставку в поле пароля.

## 10. Состояние загрузки и результат

```html
<button type="submit" aria-describedby="submit-status">Отправить</button>
<p id="submit-status" role="status" aria-live="polite"></p>
```

При отправке: «Отправка…», при успехе: «Заявка отправлена, номер 1234». Не блокируйте кнопку без объяснения — пользователь скринридера не поймёт, что происходит. Если кнопка временно неактивна, предпочтителен `aria-disabled="true"` (элемент остаётся фокусируемым и объявляется как недоступный) вместо `disabled`, который убирает элемент из табуляции.

## Чек-лист доступной формы

- [ ] У каждого поля есть связанный `<label>` (или обоснованный `aria-label`)
- [ ] `placeholder` не используется вместо метки
- [ ] Правильные `type`, `inputmode` и `autocomplete`
- [ ] Подсказки связаны через `aria-describedby` и видны до ввода
- [ ] Ошибки: конкретный текст, `aria-describedby`, `aria-invalid="true"`, `role="alert"`
- [ ] Ошибка обозначена не только цветом
- [ ] Сводка ошибок в начале формы, фокус переводится на неё, ссылки ведут к полям
- [ ] Радио и чекбоксы сгруппированы в `<fieldset>` с `<legend>`
- [ ] Обязательность обозначена и текстом, и атрибутом `required`
- [ ] Вся форма проходится и отправляется только с клавиатуры
- [ ] Виден индикатор фокуса, порядок табуляции логичен
- [ ] Контраст текста ≥ 4.5:1, границ полей ≥ 3:1
- [ ] Целевые области ≥ 24×24 px
- [ ] Данные сохраняются при ошибке валидации
- [ ] Результат отправки объявляется через live region
- [ ] Проверено скринридером (NVDA/VoiceOver) и при масштабе 200 %
