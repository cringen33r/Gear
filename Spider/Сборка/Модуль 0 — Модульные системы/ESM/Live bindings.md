Импорт в ESM — **не копия значения, а живая ссылка на ячейку памяти в модуле-владельце**. Это одно из главных семантических отличий от [[CommonJS]] и источник неочевидных различий в поведении при миграции.

# Демонстрация

```js
// counter.js
export let count = 0;
export function increment() { count += 1; }
```

```js
// app.js
import { count, increment } from './counter.js';

console.log(count);   // 0
increment();
console.log(count);   // 1  ← значение обновилось само
```

В CommonJS то же самое не работает:

```js
// counter.cjs
let count = 0;
exports.count = count;                          // скопировали значение
exports.increment = () => { count += 1; };      // мутируем локальную переменную

// app.cjs
const { count, increment } = require('./counter.cjs');
console.log(count);   // 0
increment();
console.log(count);   // 0  ← копия не изменилась
```

Чтобы получить похожее поведение в CJS, приходится экспортировать геттер или обращаться через объект (`mod.count`), и это ручная работа. В ESM связывание живое по умолчанию.

# Как это устроено

На этапе instantiation (см. [[Фазы загрузки ESM]]) движок создаёт для модуля **environment record** — таблицу его переменных. Экспорт регистрирует имя как ссылку на конкретную ячейку этой таблицы. Импорт в другом модуле создаёт **indirect binding** — указатель на ту же ячейку.

Отсюда все свойства:

- обращение к импортированному имени читает ячейку владельца в момент чтения;
- никакой копии не существует, поэтому «рассинхрона» быть не может;
- связывание создаётся **до** выполнения тел модулей — поэтому работают циклы и hoisting.

# Импорт доступен только для чтения

```js
import { count } from './counter.js';
count = 5;   // TypeError: Assignment to constant variable
```

Менять значение может **только модуль-владелец**. Это не ограничение ради ограничения: read-only на стороне импортёра гарантирует, что граф остаётся анализируемым, и никто не подменит зависимость незаметно.

Аналогично для namespace-объекта:

```js
import * as ns from './counter.js';
ns.count = 5;      // TypeError — объект запечатан
```

Но осторожно: read-only относится к **связыванию**, а не к содержимому объекта.

```js
// store.js
export const state = { user: null };

// app.js
import { state } from './store.js';
state = {};                 // TypeError — нельзя переприсвоить связывание
state.user = 'admin';       // работает — мутация объекта разрешена
```

Именно поэтому паттерн «экспортируем объект состояния» встречается повсеместно.

# Temporal Dead Zone

Связывание создаётся до выполнения, но **значение появляется только при выполнении**. До этого момента ячейка в TDZ:

```js
// a.js
import { value } from './b.js';
console.log(value);       // ReferenceError: Cannot access 'value' before initialization

// b.js
import './a.js';          // цикл: a выполнится до того, как b объявит value
export const value = 42;
```

Это не баг, а честное сообщение о циклической зависимости. В CJS то же самое дало бы `undefined` и падение где-то позже. Разбор — [[Циклические зависимости]].

Исключение: **объявления функций поднимаются полностью**, поэтому импортированная функция доступна даже в цикле, если её вызов отложен.

# Практические следствия

## Реактивные счётчики и флаги без обёрток

```js
// feature-flags.js
export let flags = {};
export async function load() {
  flags = await fetch('/flags').then(r => r.json());
}
```

Любой импортёр `flags` увидит обновление после `load()`. В CJS понадобился бы объект-контейнер.

## HMR

Замена модуля при hot reload опирается на то, что импортёры смотрят на ячейку, а не держат копию. Без live bindings пришлось бы перезапускать всех потребителей.

## Мокинг в тестах ломается иначе

Read-only связывания означают, что классический приём «подменим импортированную функцию» не работает:

```js
import * as api from './api.js';
api.fetchUser = jest.fn();   // TypeError
```

Поэтому в ESM-мире мокают на уровне загрузчика (`vi.mock`, `jest.unstable_mockModule`), а не присваиванием. Это частая причина, по которой миграция тестов с CJS на ESM оказывается дороже миграции продакшн-кода.

Важно: при сборке через транспилятор в CJS (старый Jest + Babel) присваивание может «работать», потому что ESM был скомпилирован в объект с геттерами. Тот же тест на нативном ESM упадёт. Не полагайтесь на это поведение.

## Разница в поведении между dev и prod

Vite в dev отдаёт нативный ESM — live bindings настоящие. В prod после бандлинга и scope hoisting модули схлопываются в общую область, и переменная становится обычной переменной. Наблюдаемое поведение спецификация сохраняет, но именно здесь всплывают тесты, зависевшие от подмены импортов.
