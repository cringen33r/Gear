Каждое ESM-окружение ведёт **реестр модулей** (module map / module registry) — таблицу «ключ → экземпляр модуля». Из неё следует главное практическое свойство: модуль выполняется один раз, а его экспорты общие для всех импортёров. И из неё же следует главная практическая проблема — [[Dual package hazard]].

# Как работает

При разрешении импорта (фаза construction, см. [[Фазы загрузки ESM]]) движок:

1. Резолвит спецификатор в **ключ** — абсолютный URL в браузере, абсолютный путь файла в Node.
2. Смотрит в реестр. Есть запись — использует её, ничего не грузит.
3. Нет — создаёт запись и запускает загрузку.

Ключ — именно **разрешённый идентификатор ресурса**, а не то, что вы написали в спецификаторе.

```js
// все три импорта из разных файлов дают ОДИН экземпляр
import './utils.js'        // из /src/
import '../src/utils.js'   // из /src/nested/
import '/src/utils.js'     // абсолютный путь
```

# Singleton-семантика

```js
// registry.js
console.log('registry инициализирован');
export const items = new Map();
```

```js
// a.js
import { items } from './registry.js';
items.set('a', 1);

// b.js
import { items } from './registry.js';
console.log(items.get('a'));   // 1 — та же Map
```

Сообщение в консоли выведется **один раз**, сколько бы модулей ни импортировало `registry.js`. Это основа паттерна «модуль как синглтон»: конфиг, кэш, шина событий, инстанс HTTP-клиента.

Ровно так же работает `require.cache` в [[CommonJS]] — механика одинаковая, отличается только ключ и API доступа.

# Когда singleton ломается: разные ключи

Единственность гарантирована **на ключ**. Разные ключи — разные экземпляры, даже если это байт-в-байт один файл. Это происходит чаще, чем кажется.

**1. Query-параметр в URL (браузер).**

```js
import './mod.js';
import './mod.js?v=2';   // ДРУГОЙ модуль, выполнится ещё раз
```

Именно так работает инвалидация при HMR: dev-сервер добавляет `?t=timestamp`, чтобы заставить браузер перезагрузить и переисполнить модуль. Побочный эффект — старый экземпляр остаётся в памяти со своим состоянием, поэтому глобальное состояние при HMR «двоится», если его явно не переносить (`import.meta.hot.data`).

**2. Две копии пакета в `node_modules`.**

```
node_modules/lib-a/node_modules/shared/index.js
node_modules/lib-b/node_modules/shared/index.js
```

Разные пути → два экземпляра `shared`. Классические симптомы: «два экземпляра React», `instanceof` возвращает `false`, контекст не находится, RxJS-операторы не работают с чужими Observable. Диагностика: `npm ls shared`, дедупликация: `npm dedupe`, `overrides`/`resolutions`, корректные `peerDependencies`.

**3. Один пакет в двух форматах.** ESM-версия и CJS-версия — разные файлы, значит два экземпляра со своим состоянием. Это и есть [[Dual package hazard]].

**4. Разный регистр пути.** На регистронезависимой ФС (macOS, Windows) `./Utils.js` и `./utils.js` резолвятся в один файл, но могут дать два ключа. Собирается локально, ломается в Linux-CI. Отсюда правило «всегда точный регистр в импортах» и плагин `case-sensitive-paths-webpack-plugin`.

**5. Symlink.** Node по умолчанию резолвит symlink в реальный путь (`--preserve-symlinks` меняет это). В монорепе с `npm link` или pnpm пакет может оказаться доступен по двум путям.

# Реестр в сборщике

После сборки нативного реестра нет — бандлер создаёт свой:

```js
var __modules = { /* id -> factory */ };
var __cache = {};
function __require(id) {
  if (__cache[id]) return __cache[id].exports;
  // выполнить фабрику один раз, положить в кэш
}
```

Семантика воспроизведена, ключ — внутренний id модуля. Отсюда следствие: **дедупликация решается на этапе сборки**. Если сборщик увидел два пути к одному пакету, он создаст два id и включит обе копии в бандл. Поэтому «два React» — это проблема разрешения зависимостей, а не рантайма, и лечится она в конфиге (`resolve.alias`, `resolve.dedupe` в Vite) или в `node_modules`.

Обратная сторона: Module Federation и микрофронтенды имеют **каждый свой реестр**. Общий синглтон между ними возможен только через явно объявленный `shared` с `singleton: true`.

# Отдельные реестры окружений

Один процесс может содержать несколько независимых реестров:

- главный поток и каждый Web Worker;
- каждый iframe;
- ESM-граф и CJS-граф в Node — это разные кэши;
- `vm`-контексты в Node.

Практически: модуль-синглтон **не разделяется** между главным потоком и воркером. Состояние туда нужно передавать сообщениями.

# Диагностический приём

Когда подозреваете дублирование, самый быстрый способ — пометить модуль:

```js
// suspect.js
const id = Math.random();
console.log('suspect загружен', id);
export const marker = id;
```

Два и более сообщения = два экземпляра. Дальше ищите причину по списку выше.

Для проверки в собранном бандле: поиск по уникальной строке из библиотеки — если она встречается дважды, копий две.
