Справочник по формам `import`/`export` с акцентом на то, **как каждая форма влияет на сборку**. Теория механики — в [[Статическая структура ESM]] и [[Live bindings]].

# Экспорты

## Именованные (named)

```js
export const PI = 3.14;
export function add(a, b) { return a + b; }
export class Widget {}

// или списком в конце файла
const version = '1.0';
function helper() {}
export { version, helper };

// с переименованием
export { helper as internalHelper };
```

Предпочтительная форма для библиотек: каждое имя видно сборщику отдельно, неиспользуемые удаляются при tree shaking.

## Default

```js
export default function multiply(a, b) { return a * b; }
export default class Widget {}
export default { a: 1, b: 2 };   // можно любое выражение
```

Ровно один на модуль. Импортёр даёт ему любое имя.

Практический нюанс: **default хуже поддаётся tree shaking**, если это объект. `export default { a, b, c }` — единая сущность, вырезать из неё `c` сборщик не может. Для библиотек предпочтительны named exports; default уместен для «одна сущность на файл» (компонент, класс).

Второй нюанс: default-экспорт плохо переименовывается инструментами и путает автоимпорт в IDE — в одном месте `import Button`, в другом `import Btn`. Многие командные стандарты запрещают default именно поэтому (правило ESLint `import/no-default-export`).

## Ре-экспорт

```js
export { add, sub } from './math.js';        // проброс без импорта в текущую область
export { add as sum } from './math.js';      // с переименованием
export * from './math.js';                   // все named (без default)
export * as math from './math.js';           // как namespace-объект
export { default } from './Widget.js';       // проброс default
export { default as Widget } from './Widget.js';
```

Основа «barrel-файлов» (`index.ts`), собирающих публичный API папки. Важно понимать цену:

**Barrel-файлы вредят сборке.** Импортируя одно имя из `index.ts`, вы затягиваете в граф весь файл со всеми его ре-экспортами. При хорошем tree shaking лишнее удалится, но:
- в dev-режиме Vite это реальные сетевые запросы за каждым модулем — заметное замедление;
- при наличии побочных эффектов хоть в одном модуле барреля лишнее не удалится вовсе;
- `export *` заставляет сборщик резолвить все имена, чтобы разрешить возможные конфликты.

Практика: для крупных библиотек публикуйте subpath-экспорты (см. [[Поле exports]]) вместо одного барреля.

## Экспорт типов (TypeScript)

```ts
export type { User } from './types';
export interface Config {}
```

`export type` стирается при компиляции. Это критично для инструментов, транспилирующих файл за файлом без знания типов (esbuild, swc) — подробнее в модуле 1 плана, ключевые флаги `isolatedModules` и `verbatimModuleSyntax`.

# Импорты

```js
import defaultExport from './mod.js';
import { a, b } from './mod.js';
import { a as alpha } from './mod.js';
import defaultExport, { a } from './mod.js';
import * as ns from './mod.js';
import './mod.js';                        // только ради побочного эффекта
import type { User } from './types';      // TS, стирается
```

## Namespace-объект

```js
import * as math from './math.js';
math.add(1, 2);
math.default;      // default доступен как свойство
```

Что это за объект:
- запечатан (`Object.isSealed` === true), свойства нельзя добавлять или удалять;
- свойства — live bindings, а не копии;
- присваивание `math.add = ...` даёт `TypeError` в strict mode;
- имеет `Symbol.toStringTag === 'Module'`;
- порядок ключей — лексикографический, а не порядок объявления.

**Влияние на сборку:** namespace-импорт часто ломает tree shaking, потому что сборщик не всегда может доказать, какие именно свойства читаются. `import * as _ from 'lodash'` затянет всю библиотеку; `import { debounce } from 'lodash-es'` — только нужное. Хорошие бандлеры умеют «разворачивать» namespace при статических обращениях, но полагаться на это не стоит.

## Импорт ради побочного эффекта

```js
import './polyfills.js';
import './styles.css';        // расширение сборщика, не стандарт
```

Модуль выполняется, ничего не связывается. Именно эти импорты чаще всего мешают tree shaking и требуют аккуратного `sideEffects` — см. [[sideEffects в package.json]].

# Ограничения, которые нужно помнить

**Только верхний уровень.** Внутри функции, `if`, `try` — синтаксическая ошибка:

```js
if (cond) {
  import x from './a.js';   // SyntaxError
}
```

Нужна условность — [[Динамический import()]].

**Спецификатор — только строковый литерал.** Никаких шаблонных строк и переменных:

```js
import x from `./${name}.js`;   // SyntaxError
```

**Импорты read-only:**

```js
import { count } from './counter.js';
count = 5;                      // TypeError: Assignment to constant variable
```

**Объявления поднимаются.** Импорты обрабатываются до выполнения тела, где бы они ни стояли:

```js
console.log(add(1, 2));         // работает
import { add } from './math.js';
```

Работает, но читаемость страдает — линтеры (`import/first`) требуют импорты сверху.

# Что из этого следует для практики

| Хотите | Пишите | Почему |
|---|---|---|
| Максимальный tree shaking | named exports, named imports | каждое имя анализируется отдельно |
| Ленивая загрузка | `import()` | точка разрыва графа для сборщика |
| Публичный API библиотеки | subpath exports вместо барреля | не тянуть лишнее в граф |
| Только типы | `import type` / `export type` | корректная работа esbuild/swc |
| Полифил | `import './polyfills.js'` + запись в `sideEffects` | иначе будет вырезан |
