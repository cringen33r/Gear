Загрузка ESM-графа разбита на три фазы, идущие строго последовательно для **всего графа целиком**. Понимание этого разделения объясняет hoisting импортов, [[Live bindings]], поведение [[Циклические зависимости|циклов]] и то, почему браузер может грузить зависимости параллельно.

# Три фазы

## 1. Construction (загрузка и парсинг)

Начиная с точки входа:

1. Разрешить спецификатор в конкретный ресурс (URL в браузере, путь в Node) — см. [[Спецификаторы модулей]] и [[Резолвинг модулей в Node.js]].
2. Проверить реестр: если модуль с таким ключом уже есть — взять его, не грузить повторно (см. [[Реестр модулей и singleton-семантика]]).
3. Скачать/прочитать файл.
4. Распарсить в **Module Record** — структуру со списком импортов, экспортов и телом.
5. Рекурсивно повторить для каждой зависимости.

Ключевое: **код не выполняется**. Именно поэтому браузер, разобрав модуль, немедленно запускает загрузку всех его зависимостей параллельно — их список уже известен благодаря [[Статическая структура ESM|статической структуре]].

Ошибки этой фазы: файл не найден (404 / `ERR_MODULE_NOT_FOUND`), синтаксическая ошибка парсинга, ошибка резолвинга спецификатора.

## 2. Instantiation / Linking (связывание)

Граз построен целиком. Теперь движок обходит его и:

1. Создаёт для каждого модуля **environment record** — таблицу его переменных.
2. Резервирует ячейки под все объявления модуля; они в TDZ (не инициализированы).
3. Связывает каждый импорт с ячейкой экспортирующего модуля — создаёт indirect binding.
4. Проверяет, что каждый запрошенный экспорт существует.

Код по-прежнему **не выполняется**. Но связи уже проложены — отсюда и live bindings, и возможность работы циклов.

Ошибка этой фазы — та самая:

```
SyntaxError: The requested module './math.js' does not provide an export named 'addd'
```

Обратите внимание на класс ошибки: `SyntaxError`, хотя синтаксис файла корректен. Это ошибка связывания, и она возникает **до** выполнения любого кода, включая код точки входа. Практическое следствие: опечатка в импорте в глубоко ленивом модуле обнаружится при загрузке этого чанка, а не при вызове функции.

## 3. Evaluation (выполнение)

Обход графа в глубину, **post-order**: сначала выполняются зависимости, потом сам модуль.

```
app.js → math.js → utils.js
```

Порядок выполнения: `utils.js`, `math.js`, `app.js`.

Каждый модуль выполняется ровно один раз; результат (успех или исключение) запоминается в реестре. Повторный импорт того же модуля не перезапускает тело — даже если первый прогон бросил исключение, повторный импорт вернёт то же исключение, не выполняя код заново.

Ошибки этой фазы — обычные рантайм-ошибки вашего кода.

# Почему это важно на практике

## Импорты «поднимаются»

```js
console.log(greet());          // работает
import { greet } from './greet.js';
```

Ничего магического: `./greet.js` выполнен на фазе 3 раньше, чем тело текущего модуля, а связывание создано на фазе 2. Расположение строки `import` в файле не влияет ни на что.

## Побочные эффекты порядка

```js
import './polyfills.js';    // выполнится первым
import { app } from './app.js';
```

Порядок **объявления** импортов задаёт порядок выполнения зависимостей. Это единственный рычаг влияния на последовательность — и он ломается, если сборщик переупорядочит импорты (обычно не делает, но при агрессивной оптимизации возможно). Надёжнее выносить порядок-критичную инициализацию в отдельную точку входа.

## Ошибка резолвинга валит всё

Если один модуль в глубине графа не найден, **не выполнится ничего**, включая точку входа. Фаза 1 не завершилась — фазы 3 не будет. В CJS сломался бы только тот `require`, который до него дошёл, и приложение могло частично работать.

## Асинхронность фаз

Фазы 1 и 2 асинхронны (сетевые запросы, чтение с диска), фаза 3 синхронна — **кроме** модулей с [[Top-level await]]. TLA делает модуль асинхронным, и его импортёры ждут завершения. Это меняет фазу 3 из «синхронный обход» в «обход с точками ожидания» и влияет на возможные форматы вывода сборщика.

# Как это делает сборщик

Бандлер выполняет фазы 1 и 2 **на этапе сборки**, а не в рантайме:

- фаза 1 → построение графа модулей, обход всех `import`;
- фаза 2 → разрешение имён, вычисление, какие экспорты используются (основа tree shaking), проверка отсутствующих экспортов;
- фаза 3 → остаётся в рантайме, но модули уже склеены, а связывание заменено прямыми ссылками (при scope hoisting) или обращениями к объекту-реестру.

Отсюда практический вывод: **ошибки, которые в нативном ESM возникают в фазах 1–2, сборщик находит во время сборки**. Это одна из причин, почему сборка ловит то, что dev-сервер пропускает, и наоборот.

# Схема

```
[Construction]  найти → скачать → распарсить → рекурсия по зависимостям
       ↓                              (код не выполняется)
[Instantiation] создать ячейки → связать импорты с экспортами → проверить наличие
       ↓                              (код не выполняется)
[Evaluation]    выполнить тела в порядке post-order DFS, по одному разу
```
