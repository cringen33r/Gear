Цикл — ситуация, когда модуль прямо или косвенно зависит сам от себя: `a → b → a`. Модульные системы обязаны как-то это разрулить, и разруливают они **по-разному**, что делает циклы одним из самых болезненных мест при миграции с [[CommonJS]] на ESM.

# Как цикл выглядит в реальном проекте

Редко в виде двух файлов. Обычно так:

```
user.model.ts → order.model.ts → user.model.ts
```

или через barrel-файл:

```
components/index.ts → Button.ts → components/index.ts
```

Последнее — самая частая причина циклов на практике: компонент импортирует соседа через общий `index.ts`, замыкая граф на себя.

# Поведение в ESM

Опирается на [[Фазы загрузки ESM]]: связывание происходит **до** выполнения, поэтому цикл не приводит к бесконечной рекурсии — второй заход просто находит модуль в реестре. Но значения к этому моменту могут быть не инициализированы.

```js
// a.js
import { bValue } from './b.js';
export const aValue = 'A';
console.log('a видит b:', bValue);

// b.js
import { aValue } from './a.js';
export const bValue = 'B';
console.log('b видит a:', aValue);
```

Точка входа `a.js`. Порядок: граф построен, связывания созданы, выполнение идёт в post-order — сначала `b.js`.

```
ReferenceError: Cannot access 'aValue' before initialization
```

`b.js` выполняется первым, обращается к `aValue`, а тело `a.js` ещё не выполнялось — ячейка в TDZ. Ошибка **явная и в точке проблемы** — это принципиально лучше поведения CJS.

## Что в цикле работает

Объявления функций поднимаются полностью, поэтому цикл через функции безопасен, если вызов отложен:

```js
// a.js
import { fromB } from './b.js';
export function fromA() { return 'A'; }
export const result = fromB();   // ← вызов на верхнем уровне, упадёт

// b.js
import { fromA } from './a.js';
export function fromB() { return fromA() + 'B'; }   // ← вызов внутри функции, безопасно
```

Правило: **в цикле опасны обращения на верхнем уровне модуля**, а не сами импорты. Отложите использование до вызова функции или до `class` в рантайме — цикл станет незаметным.

## Классы — частая ловушка

```js
// base.js
import { Child } from './child.js';
export class Base { static create() { return new Child(); } }

// child.js
import { Base } from './base.js';
export class Child extends Base {}   // ← extends вычисляется НА ВЕРХНЕМ УРОВНЕ
```

`extends Base` — верхнеуровневое выражение, оно упадёт, если `base.js` ещё не выполнен. Отсюда `Class extends value undefined is not a constructor` — типовая ошибка в TypeScript-проектах с двусторонними связями моделей.

# Поведение в CommonJS

Ошибки нет — есть тихо неверные данные.

```js
// a.cjs
exports.done = false;
const b = require('./b.cjs');
console.log('a: b.done =', b.done);
exports.done = true;

// b.cjs
const a = require('./a.cjs');
console.log('b: a.done =', a.done);   // false — a не дошёл до конца
exports.done = true;
```

`require` возвращает `module.exports` **в текущем состоянии**, то есть частично заполненный объект. Никакого предупреждения. Ошибка проявится позже и в другом месте.

С деструктуризацией становится ещё хуже: `const { done } = require('./a.cjs')` копирует `undefined` навсегда — нет [[Live bindings|live binding]], который позже подтянул бы значение.

# Сравнение

| | CommonJS | ESM |
|---|---|---|
| Что возвращается | частичный `module.exports` | связывание, возможно в TDZ |
| Сигнал о проблеме | нет | `ReferenceError` |
| Когда падает | позже, в другом месте | сразу, в точке обращения |
| Восстановление значения | нет (если деструктурировали) | да, live binding подтянется |

Практический вывод для миграции: **код, который годами «работал» в CJS с циклами, при переходе на ESM начнёт падать**. Это не регрессия — это обнаружение существовавшей проблемы.

# Как сборщики к этому относятся

**webpack** воспроизводит семантику, циклы работают, но при `harmony import` возможны различия с нативным ESM.

**Rollup** предупреждает: `Circular dependency: src/a.js -> src/b.js -> src/a.js`. При scope hoisting Rollup вынужден выбрать порядок объявлений, и в сложных циклах результат может отличаться от нативного поведения — предупреждения игнорировать не стоит.

**Vite** в dev использует нативный ESM браузера (поведение честное), в prod — Rollup. Отсюда классическое «в dev работает, в prod падает» и наоборот.

Важно: **сборщик может замаскировать цикл**. После scope hoisting модули схлопываются в общую область, и порядок объявлений иногда оказывается «удачным». Полагаться на это нельзя.

# Как находить и лечить

## Находить

- `madge --circular src/` — обход графа, самый прямой инструмент;
- ESLint: `import/no-cycle` (учтите, что правило медленное — обычно включают только в CI);
- предупреждения Rollup/Vite при сборке;
- в webpack — `CircularDependencyPlugin`.

## Лечить

**1. Извлечь общее в третий модуль.** Самое частое и самое правильное. Если `a` и `b` тянут друг у друга общие типы/константы — вынесите их в `shared.js`, цикл разомкнётся.

**2. Убрать barrel из внутренних импортов.** Компоненты внутри библиотеки должны импортировать друг друга **напрямую** (`./Button`), а не через `index.ts`. Баррель — публичный вход для потребителей, а не для своих.

**3. Инвертировать зависимость.** Передавайте нужное параметром/через DI вместо импорта. В Angular это естественно через инжектор: вместо `import { UserService }` в модели — внедрение сервиса там, где он нужен.

**4. Отложить обращение.** Если разорвать граф нельзя, перенесите использование из верхнего уровня внутрь функции.

**5. `import type`.** Если зависимость нужна только для типов, `import type { User } from './user'` полностью стирается при компиляции и цикла в рантайме не создаёт. Самый дешёвый фикс для TS-проектов — но требует, чтобы вы действительно не использовали значение.

**6. Динамический импорт.** [[Динамический import()]] разрывает статический цикл ценой асинхронности.
