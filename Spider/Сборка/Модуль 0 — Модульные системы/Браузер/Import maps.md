Import map — механизм браузера, позволяющий переопределять разрешение спецификаторов модулей. Решает главную проблему нативного ESM в браузере: **bare-спецификаторы вроде `import 'lodash'` без сборщика не работают** (см. [[Спецификаторы модулей]]).

# Базовый синтаксис

```html
<script type="importmap">
{
  "imports": {
    "lodash": "https://cdn.jsdelivr.net/npm/lodash-es@4/lodash.js",
    "@app/": "/src/",
    "#config": "/src/config.prod.js"
  }
}
</script>

<script type="module">
  import { debounce } from 'lodash';   // теперь резолвится
  import { Button } from '@app/ui/Button.js';
</script>
```

# Правила сопоставления

**Точное совпадение.** Ключ без слеша в конце матчится целиком: `"lodash"` покрывает `import 'lodash'`, но не `import 'lodash/debounce'`.

**Префиксное совпадение.** Ключ, **заканчивающийся слешем**, работает как префикс:

```json
{ "imports": { "lodash/": "https://cdn.example.com/lodash-es/" } }
```

`import 'lodash/debounce.js'` → `https://cdn.example.com/lodash-es/debounce.js`. Слеш в конце обязателен и у ключа, и у значения.

**Длиннейший ключ выигрывает.** При конкуренции `"lodash/"` и `"lodash/fp/"` для `lodash/fp/map.js` победит второй.

**Переопределение относительных путей.** Ключом может быть и обычный путь — так подменяют конкретный файл:

```json
{ "imports": { "/src/config.js": "/src/config.mock.js" } }
```

# `scopes` — разные версии для разных частей приложения

```json
{
  "imports": {
    "lodash": "/vendor/lodash@4.js"
  },
  "scopes": {
    "/legacy/": {
      "lodash": "/vendor/lodash@3.js"
    }
  }
}
```

Модули, загруженные из `/legacy/`, получат третью версию, все остальные — четвёртую. Ключ scope — префикс URL **импортирующего** модуля.

Это ровно тот механизм вложенности, который в Node реализован через вложенные `node_modules` (см. [[Резолвинг модулей в Node.js]]). И ровно так же он создаёт два экземпляра библиотеки со всеми последствиями из [[Реестр модулей и singleton-семантика]] — применять осознанно.

# Ограничения

**Должен идти до первого импорта.** Карта обязана быть распарсена раньше, чем начнётся разрешение любого модуля. На практике — сразу в `<head>`, до всех `<script type="module">`.

**Только инлайн (исторически).** Долгое время `src` у `type="importmap"` не поддерживался, карту приходилось встраивать в HTML. Поддержка внешних карт появляется в браузерах, но при написании кода на сегодня безопаснее рассчитывать на инлайн. Практическое следствие: карта попадает в HTML, а значит, влияет на CSP (нужен `nonce` или хеш при жёсткой политике).

**Ограничение по количеству.** Изначально спецификация допускала одну карту на документ; поддержка нескольких (с объединением) появилась в современных браузерах позже. Если пишете код с расчётом на широкую совместимость — исходите из одной карты.

**Не действует на `<script src>` и `fetch`.** Только на разрешение спецификаторов внутри модулей.

**Нет резолвинга по `package.json`.** Карта не читает `exports`, `main`, условия. Полный путь к файлу указываете вы.

# Реальные применения

## Приложение без сборки

Прототип, внутренний инструмент, демо. Пишете обычный ESM с bare-импортами, зависимости берёте с CDN (`esm.sh`, `jsdelivr`, `unpkg`), сборка не нужна вовсе. См. [[Практикум — приложение на нативном ESM]].

## Микрофронтенды и разделяемые зависимости

Несколько независимо задеплоенных приложений на одной странице должны использовать **один** экземпляр React. Import map задаёт единый URL для всех — это альтернатива механизму `shared` в Module Federation, только на уровне платформы и без рантайма сборщика.

## Подмена в тестах и на стендах

Ключ-путь позволяет заменить модуль без пересборки: `"/src/api.js": "/src/api.mock.js"`. Удобно для e2e и демо-стендов.

## Совместимость с Node

Node и Deno понимают import maps в своей форме, что позволяет разделять карту между окружениями. Для Node более идиоматичен `imports` в `package.json` — см. [[Поле imports и внутренние алиасы]].

# Import maps против сборщика

Import map решает **только** резолвинг. Не решает: минификацию, tree shaking, водопад запросов, транспиляцию TS/JSX, обработку CSS и ассетов, code splitting с хешированием.

Поэтому это не «замена бандлеру», а инструмент для конкретных задач: прототипы, разделяемые зависимости между независимыми приложениями, точечная подмена модулей. В обычном продакшн-приложении сборщик всё равно нужен — почему именно, разбирается в [[Предел нативного ESM в браузере]].

# Практический совет

Если хотите увидеть механику своими руками — соберите страницу на import map и посмотрите в Network, как браузер разворачивает граф. Это самый быстрый способ понять, какую именно работу за вас делает сборщик.
