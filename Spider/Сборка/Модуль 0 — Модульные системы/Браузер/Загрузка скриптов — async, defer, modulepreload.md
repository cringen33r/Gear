Порядок и момент выполнения скриптов — то, чем сборщик управляет за вас, генерируя `index.html`. Понимание механики нужно, чтобы читать вывод сборки и осмысленно настраивать предзагрузку.

# Четыре режима классического скрипта

```html
<script src="a.js"></script>              <!-- блокирующий -->
<script defer src="b.js"></script>        <!-- отложенный -->
<script async src="c.js"></script>        <!-- независимый -->
<script type="module" src="d.js"></script><!-- модуль = defer по умолчанию -->
```

**Блокирующий.** Парсер HTML останавливается, скрипт скачивается и выполняется, затем парсинг продолжается. Каждый такой тег — пауза в построении DOM. Единственная причина использовать сегодня — код, который обязан выполниться до первого рендера (антифликер-скрипты темы, критичные фича-флаги).

**`defer`.** Скачивается параллельно парсингу, выполняется **после** завершения парсинга, перед `DOMContentLoaded`. Порядок нескольких `defer`-скриптов сохраняется в порядке документа. Это правильный режим по умолчанию для кода приложения.

**`async`.** Скачивается параллельно, выполняется **сразу по готовности**, прерывая парсинг в произвольный момент. Порядок не гарантирован — кто раньше скачался, тот раньше выполнился. Годится только для полностью независимых скриптов: аналитика, счётчики, чат-виджеты.

**Модуль.** Ведёт себя как `defer`; подробнее в [[Модули в браузере — script type=module]]. С атрибутом `async` — как `async`, включая инлайновые.

# Итоговый порядок выполнения

```html
<script>A</script>
<script defer src="B"></script>
<script type="module">C</script>
<script>D</script>
<script async src="E"></script>
```

Гарантированно: `A` → `D` (синхронные, по порядку) → `B` и `C` (отложенные, по порядку документа, после парсинга). `E` — в любой момент после своей загрузки.

Правило для запоминания: **синхронные по порядку сразу → отложенные по порядку после парсинга → async когда угодно**.

# Подсказки предзагрузки

Скрипт можно попросить загрузить заранее, не выполняя.

## `rel="modulepreload"`

```html
<link rel="modulepreload" href="/chunk-abc123.js">
```

Специально для ESM. Отличие от обычного `preload`:

- ресурс не только скачивается, но и **парсится, компилируется и кладётся в реестр модулей** — к моменту импорта работа уже сделана;
- браузер может рекурсивно предзагрузить **зависимости** модуля, вскрыв его импорты (поведение зависит от браузера).

Второй пункт — главное. Он лечит водопад запросов: без предзагрузки браузер узнаёт о зависимости второго уровня только распарсив первый уровень. См. [[Предел нативного ESM в браузере]].

Именно `modulepreload` генерируют сборщики в `index.html` для чанков стартового пути. Vite делает это автоматически и дополнительно вставляет полифил для браузеров без поддержки.

## `rel="preload"`

```html
<link rel="preload" href="/font.woff2" as="font" crossorigin>
```

Универсальный: качает ресурс с высоким приоритетом, но не выполняет и не парсит. Для скриптов уступает `modulepreload`. Атрибут `as` обязателен — без него браузер не знает приоритет и может скачать ресурс дважды.

## `rel="prefetch"`

```html
<link rel="prefetch" href="/reports-chunk.js">
```

Низкий приоритет, «на будущее» — для ресурсов **следующей** навигации. Браузер грузит в простое. Типовое применение — чанк вероятного следующего маршрута.

Разница в одной строке: `preload`/`modulepreload` — «нужно на этой странице», `prefetch` — «вероятно понадобится на следующей».

## Как этим управлять из кода

Через магические комментарии webpack (см. [[Динамический import()]]):

```js
import(/* webpackPreload: true */ './critical.js');
import(/* webpackPrefetch: true */ './next-route.js');
```

Или вручную, по действию пользователя:

```js
link.addEventListener('mouseenter', () => { import('./reports.js'); }, { once: true });
```

Модуль осядет в реестре, и реальный переход будет мгновенным. Простой и эффективный приём для ленивых маршрутов.

# Влияние на метрики

Практический смысл всего этого — три вещи:

**Блокирующие скрипты в `<head>` ухудшают FCP/LCP.** Каждый — пауза перед первой отрисовкой.

**Слишком много `modulepreload` вредит.** Предзагрузка конкурирует за пропускную способность с критичными ресурсами (CSS, шрифты, LCP-картинка). Предзагружать нужно **только стартовый путь**, а не весь граф.

**`async` для кода приложения — источник плавающих багов.** Порядок не гарантирован, значит, зависимость между двумя `async`-скриптами когда-нибудь сломается.

Проверка: DevTools → Network, колонка Priority, и вкладка Performance для порядка выполнения.

# Что генерирует сборщик

Типичный вывод современного бандлера:

```html
<script type="module" crossorigin src="/assets/index-a1b2.js"></script>
<link rel="modulepreload" crossorigin href="/assets/vendor-c3d4.js">
<link rel="stylesheet" href="/assets/index-e5f6.css">
```

Читается так: точка входа — модуль (значит, отложен); общий вендорный чанк предзагружается, чтобы не ждать его после разбора точки входа; CSS отдельным файлом, чтобы не блокировать JS.

Умение прочитать этот HTML и сказать, что грузится параллельно, а что последовательно, — практический навык из этого модуля.
