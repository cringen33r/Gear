Браузер умеет грузить ESM-граф сам. Возникает резонный вопрос: зачем тогда бандлер? Эта заметка — ответ, и одновременно мост к модулю 2 плана ([[00 MOC — План изучения сборки]]).

# Проблема 1: водопад запросов

Главное ограничение. Браузер узнаёт о зависимости, только **распарсив** модуль, который её импортирует.

```
main.js  →  app.js  →  store.js  →  utils.js
```

Каждая стрелка — отдельный round-trip. Четыре уровня вложенности = четыре последовательных запроса, и никакая пропускная способность не поможет: это задержка, а не объём. При RTT 100 мс глубина 5 стоит полсекунды пустого ожидания.

Реальный граф приложения имеет глубину 10–20 и ширину в сотни модулей. Бандлер схлопывает это в единицы файлов, устраняя и глубину, и количество.

Частичное лечение — `<link rel="modulepreload">` для известных заранее модулей (см. [[Загрузка скриптов — async, defer, modulepreload]]). Но чтобы сгенерировать полный список, надо знать граф целиком — то есть выполнить работу бандлера.

# Проблема 2: количество запросов

Средний проект с зависимостями — тысячи модулей (`lodash-es` один даёт около 600 файлов). Даже по HTTP/2 с мультиплексированием это тысячи запросов: заголовки, приоритизация, накладные расходы на TLS-фреймы, память браузера на каждый запрос.

Распространённое заблуждение — «HTTP/2 сделал бандлинг ненужным». Мультиплексирование сняло лимит на параллельные соединения, но не сделало запросы бесплатными и **не устранило водопад** — он определяется структурой графа, а не транспортом. Практика показала: бандлинг выигрывает у неограниченного числа мелких файлов.

Обратная крайность тоже плоха: один гигантский файл ломает кэширование (изменили строчку — инвалидировали всё). Оптимум — несколько десятков чанков, и это уже задача сборщика, а не браузера.

# Проблема 3: bare-спецификаторы

```js
import { debounce } from 'lodash-es';   // браузер не знает, где это
```

Браузер не умеет искать `node_modules` и читать `package.json`. Частично решается через [[Import maps]], но карту нужно сгенерировать, а `exports` с условиями (см. [[Условия резолвинга]]) она не понимает вовсе.

# Проблема 4: нет CommonJS

Значительная часть npm до сих пор публикует только [[CommonJS]]. Браузер его не исполняет в принципе. Единственный способ использовать такой пакет — конвертировать в ESM, а это уже работа инструмента сборки (в Vite — этап `optimizeDeps`).

# Проблема 5: нет оптимизаций

Браузеру нечем:

- **минифицировать** — файлы отдаются как написаны;
- **делать tree shaking** — движок грузит модуль целиком, даже если из него нужна одна функция;
- **хешировать имена** для долгосрочного кэширования;
- **инлайнить мелкие ассеты**, объединять CSS, оптимизировать картинки.

# Проблема 6: только JavaScript

TypeScript, JSX, Vue SFC, SCSS, `.svg` как компонент — ничего этого браузер не понимает. Нужен шаг трансформации (модуль 1 плана).

# Что нативный ESM всё-таки даёт

Не отменяя бандлер, он изменил **дев-режим**, и это главная революция последних лет.

Раньше: dev-сервер собирал весь бандл перед первой отдачей → минуты ожидания на большом проекте, секунды на каждое изменение.

Теперь (Vite): сервер отдаёт `index.html` с `<script type="module">`, браузер сам запрашивает граф, сервер трансформирует **только запрошенные файлы** и только по требованию. Старт мгновенный независимо от размера проекта; при изменении файла пересобирается один модуль.

Именно поэтому у Vite две разные машины: dev на нативном ESM, prod на Rollup. Понимание этой асимметрии объясняет львиную долю различий поведения между режимами:

| | dev (нативный ESM) | prod (бандл) |
|---|---|---|
| Модули | по одному, как есть | схлопнуты в чанки |
| CJS-зависимости | пре-бандлятся заранее | бандлятся в общем графе |
| Tree shaking | нет | да |
| Live bindings | настоящие | после scope hoisting иначе |
| Циклы | поведение браузера | поведение Rollup |

Отсюда классическое «работает в dev, падает в prod». Разбор конкретных случаев — [[Диагностика ошибок модульных систем]].

# Когда бандлер действительно не нужен

Честный список:

- прототип, демо, страница с парой скриптов;
- внутренний инструмент без требований к скорости загрузки;
- библиотека, потребители которой соберут её сами;
- Deno/Bun-скрипты, где рантайм сам резолвит и транспилирует.

Во всех остальных случаях вопрос не «нужен ли бандлер», а «какой».
