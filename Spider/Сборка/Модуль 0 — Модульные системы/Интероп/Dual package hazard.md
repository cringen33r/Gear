Ситуация, когда один и тот же пакет загружен в приложение **дважды** — как ESM и как CJS — и существует в двух независимых экземплярах со своим состоянием. Официальный термин из документации Node.

Это не абстрактная проблема: «два React», «два экземпляра RxJS», «контекст не находится», «`instanceof` возвращает false» — всё это её проявления.

# Как возникает

Корень — в [[Реестр модулей и singleton-семантика|реестре модулей]]: экземпляр уникален **на разрешённый путь**. Разные пути = разные экземпляры.

Пакет с двойной сборкой:

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

Дальше достаточно, чтобы одна часть приложения пришла через `import`, а другая через `require`:

```js
// app.mjs
import { registry } from 'shared-lib';        // → dist/index.mjs

// legacy.cjs (зависимость, которую вы не контролируете)
const { registry } = require('shared-lib');   // → dist/index.cjs
```

Два файла — два экземпляра — два разных `registry`.

# Симптомы

**Состояние не разделяется.** Инициализировали в одном месте, читаете в другом — пусто.

```js
// в ESM-части
config.set('apiUrl', '/api');
// в CJS-части
config.get('apiUrl');   // undefined
```

**`instanceof` ломается.** Класс из одного экземпляра не является классом из другого:

```js
error instanceof CustomError;   // false, хотя объект «того самого» типа
```

Поэтому надёжные библиотеки проверяют тип по свойству-маркеру, а не через `instanceof`.

**Хуки/контексты не находятся.** В React: «Invalid hook call» или контекст возвращает дефолт. Провайдер зарегистрирован в одном экземпляре React, потребитель ищет в другом.

**Размер бандла удвоился** по этой библиотеке.

**Синглтоны не синглтоны.** Два подключения к БД, два HTTP-клиента с разными интерцепторами, две шины событий.

# Другие пути к той же проблеме

Формат — лишь одна из причин. Экземпляры двоятся и без него:

**Разные версии в дереве.**
```
node_modules/lib-a/node_modules/shared@1.0.0
node_modules/shared@2.0.0
```

**Пакет и в зависимостях, и в бандле библиотеки.** Библиотека забыла объявить React как `peerDependency` и вкомпилировала его в себя.

**Разные условия резолвинга.** Одна часть сборки резолвит по `browser`, другая по `node` — см. [[Условия резолвинга]].

**Разные точки входа.** Один потребитель через `main`, другой через `module` — см. [[Точки входа пакета — main, module, browser, types]].

**Монорепа с symlink.** Пакет доступен и по реальному пути, и по ссылке.

# Диагностика

## Найти копии в дереве

```bash
npm ls react
npm why react          # кто именно притянул
pnpm why react
```

Вывод покажет все места установки. Несколько строк с разными версиями — почти наверняка проблема.

## Пометить экземпляр

Самый надёжный способ, работающий и в бандле:

```js
// в подозреваемом модуле, временно
console.log('загружен', import.meta.url ?? __filename, Math.random());
```

Два сообщения = две копии.

## Найти в собранном бандле

Поиск по уникальной строке из библиотеки (сообщение об ошибке, имя внутренней функции). Встретилась дважды — копий две.

Инструменты анализа бандла (`source-map-explorer`, `rollup-plugin-visualizer`) показывают это наглядно: одна библиотека двумя блоками.

# Лечение

## На стороне потребителя

**Дедупликация зависимостей:**
```bash
npm dedupe
```

**Принудительная версия:**
```json
// package.json
{ "overrides": { "shared-lib": "2.0.0" } }      // npm
{ "resolutions": { "shared-lib": "2.0.0" } }    // yarn
{ "pnpm": { "overrides": { "shared-lib": "2.0.0" } } }
```

**Алиас в сборщике** — самый прямой способ:
```js
// vite.config.ts
resolve: {
  dedupe: ['react', 'react-dom'],
  alias: { 'shared-lib': path.resolve(__dirname, 'node_modules/shared-lib') }
}
```

```js
// webpack
resolve: { alias: { react: path.resolve('./node_modules/react') } }
```

**Явные условия.** Заставьте всю сборку идти одной веткой `exports` через `resolve.conditions`.

## На стороне автора библиотеки

**Вариант 1: публиковать один формат.** Радикально и надёжно. С появлением [[require(esm) в Node.js]] ESM-only стал реалистичным вариантом.

**Вариант 2: изолировать состояние в CJS-ядре.** Обе сборки требуют один и тот же CJS-файл с состоянием:

```
dist/state.cjs        ← единственный носитель состояния
dist/index.mjs        ← import ... from './state.cjs'
dist/index.cjs        ← require('./state.cjs')
```

Даже при двух обёртках состояние одно.

**Вариант 3: ESM-обёртка над CJS.** ESM-сборка — тонкий фасад, ре-экспортирующий CJS:

```js
// dist/index.mjs
import cjs from './index.cjs';
export const { add, sub } = cjs;
export default cjs;
```

Код один, обёрток две. Минус — теряется tree shaking, поскольку реальная реализация в CJS.

**Вариант 4: не хранить состояние вообще.** Библиотека из чистых функций к этой проблеме иммунна. Лучшее решение там, где применимо.

**Вариант 5: `peerDependencies`.** Для React, Angular, RxJS — обязательно. Пакет не должен тащить фреймворк в свои зависимости.

# Как не допустить

Чеклист при публикации библиотеки:

- [ ] Есть ли в пакете модульное состояние (кэш, реестр, синглтон)? Если да — dual-сборка опасна.
- [ ] Фреймворки и крупные общие библиотеки — в `peerDependencies`, не в `dependencies`.
- [ ] `exports` не даёт двух путей к одной сущности.
- [ ] Проверено `npx publint` и `npx @arethetypeswrong/cli`.
- [ ] Протестировано потребление обоими способами.
