Долгие годы `require()` ESM-модуля был невозможен и давал `ERR_REQUIRE_ESM`. В Node 22 появилась поддержка синхронного `require(esm)`, что заметно упростило сосуществование форматов.

# Как было

```js
const esm = require('./module.mjs');
// Error [ERR_REQUIRE_ESM]: require() of ES Module ... not supported
```

Причина принципиальная: ESM-граф загружается асинхронно (см. [[Фазы загрузки ESM]]), а `require` обязан вернуть значение синхронно.

Практическое последствие было болезненным: **ESM-only пакет нельзя было использовать в CJS-кодовой базе**, кроме как через `await import()`. Когда популярные библиотеки одна за другой переходили на ESM-only, это ломало сборки и инструменты, где `await` был недоступен (например, в синхронно загружаемом конфиге).

Обходные пути были такими:

```js
// динамический импорт — требует асинхронного контекста
const esm = await import('./module.mjs');

// или откат на старую версию пакета, или бандлинг зависимости в свой код
```

# Как стало

Node 22 (и в частях бэкпортировано в 20.x) умеет загружать ESM синхронно, если это возможно:

```js
const esm = require('./module.mjs');   // работает
```

## Условие: отсутствие top-level await

Синхронная загрузка возможна, только когда **весь граф модуля синхронен**. Если модуль или любая его зависимость использует [[Top-level await]], Node не может дождаться результата в синхронном контексте:

```
ERR_REQUIRE_ASYNC_MODULE
```

Это, кстати, ещё один аргумент против TLA в библиотеках: он делает пакет недоступным для `require`.

## Что возвращается

**Namespace-объект**, а не `module.exports`. То есть default лежит в свойстве:

```js
// esm.mjs
export default function main() {}
export const helper = () => {};
```

```js
const mod = require('./esm.mjs');
mod.default();   // ← так
mod.helper();
mod();           // ❌ TypeError
```

Это отличается от привычного поведения `require` с CJS и легко ловится на невнимательности. Ранние версии реализации добавляли эвристику для «похожих на CJS» модулей, но полагаться на это не стоит — пишите `.default` явно.

Проверить, что вернулось, можно по маркеру:

```js
const mod = require('./unknown.js');
const isEsm = mod?.[Symbol.toStringTag] === 'Module';
```

# Что это меняет на практике

**Библиотеки могут публиковаться ESM-only смелее.** Раньше это отрезало CJS-потребителей; теперь — только тех, кто на старом Node.

**Уменьшается потребность в dual-сборке.** Если ваша аудитория на Node 22+, можно публиковать только ESM и не платить за двойную сборку и риск [[Dual package hazard]].

**Проще инструменты.** Конфиги и плагины, загружаемые синхронно, теперь могут подтягивать ESM.

# Чего это не меняет

**Старые версии Node.** Пока в поддержке Node 18/20 без бэкпорта, ESM-only публикация всё ещё отрезает часть пользователей. Смотрите на `engines` и реальную аудиторию.

**Браузер.** Там CJS не существует в принципе.

**Сборщики.** Они решают интероп сами, на своём уровне (см. [[ESM и CommonJS — взаимодействие]]), и от версии Node не зависят.

**Семантику.** ESM остаётся strict-mode, с [[Live bindings]] и без `__dirname`. `require(esm)` меняет способ загрузки, а не природу модуля.

# Как решать сегодня

| Ситуация | Действие |
|---|---|
| Пишете приложение на Node 22+ | Смело используйте ESM-only зависимости |
| Публикуете библиотеку с широкой аудиторией | Пока безопаснее dual (`import` + `require` в [[Поле exports]]) |
| Публикуете инструмент для современного стека | ESM-only оправдан |
| Нужна совместимость со старым Node | `await import()` в асинхронном контексте |
| Внутренний код компании | Смотрите на минимальную версию Node в CI и проде |

При написании библиотеки перепроверяйте оба пути потребления после сборки:

```bash
node -e "import('./dist/index.js').then(m => console.log(Object.keys(m)))"
node -e "console.log(Object.keys(require('./dist/index.cjs')))"
```

Точное поведение `require(esm)` зависит от минорной версии Node — при работе с этим механизмом сверяйтесь с документацией конкретной версии, на которой у вас прод.
