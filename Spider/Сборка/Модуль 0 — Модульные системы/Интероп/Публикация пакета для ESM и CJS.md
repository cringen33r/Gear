Сводная практическая заметка: как собрать `package.json` библиотеки, чтобы она работала у всех потребителей и не создавала проблем. Опирается на [[Поле exports]], [[Условия резолвинга]] и [[Dual package hazard]].

# Сначала решите: нужен ли dual

Двойная сборка — это удвоение артефактов, риск двух экземпляров и лишняя сложность. Не берите её по умолчанию.

| Аудитория | Публикуйте |
|---|---|
| Только браузер через сборщик | ESM |
| Современный Node (22+) и сборщики | ESM |
| Есть CJS-потребители на старом Node | ESM + CJS |
| Подключение через `<script>` | + IIFE/UMD сборка |

С появлением [[require(esm) в Node.js]] аргументы за dual заметно ослабли. Проверьте реальную минимальную версию Node у ваших пользователей, прежде чем платить за вторую сборку.

# Раскладка ESM-only

Самый простой и предпочтительный вариант:

```json
{
  "name": "my-lib",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "default": "./dist/index.js"
    },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "sideEffects": false,
  "engines": { "node": ">=20" }
}
```

Заявите минимальную версию Node в `engines` — это честный контракт с потребителем.

# Раскладка dual

```json
{
  "name": "my-lib",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    },
    "./utils": {
      "types": "./dist/utils.d.ts",
      "import": "./dist/utils.js",
      "require": "./dist/utils.cjs"
    },
    "./package.json": "./package.json"
  },
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "files": ["dist"],
  "sideEffects": false
}
```

Разбор по строкам:

- `type: module` → `.js` в `dist` считается ESM;
- CJS-сборка лежит в `.cjs` — расширение перекрывает `type` (см. [[Поле type и расширения mjs cjs]]);
- `types` первым в каждой ветке — иначе TypeScript возьмёт не тот файл;
- `default` последним;
- `main`/`module`/`types` в корне — фолбэк для инструментов, не читающих `exports`;
- `./package.json` экспортирован явно;
- `files` ограничивает содержимое публикуемого архива.

## Типы для двух форматов

Тонкость, которую часто пропускают: TypeScript определяет формат `.d.ts` по тем же правилам, что и `.js`. При `type: module` файл `index.d.ts` считается ESM-декларацией, и для CJS-ветки формально нужен `index.d.cts`.

На практике многие пакеты обходятся одним `.d.ts`, и это работает при `moduleResolution: bundler`, но ломается при `node16`. Проверка — `npx @arethetypeswrong/cli`, он показывает разрешение типов во всех режимах.

Большинство современных сборщиков библиотек (`tsup`, `unbuild`, `rollup-plugin-dts`) генерируют оба файла автоматически.

# Subpath-экспорты вместо барреля

Плохо:

```json
{ "exports": { ".": "./dist/index.js" } }
```

Единственный вход означает, что импорт одной функции тянет в граф весь `index.js` с его ре-экспортами. При хорошем tree shaking лишнее удалится, но не всегда — см. [[Синтаксис импортов и экспортов]].

Лучше:

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./*": "./dist/*.js"
  }
}
```

Потребитель может взять `my-lib/button` напрямую. Шаблон избавляет от ручного перечисления, инкапсуляция сохраняется.

# Обязательные проверки перед публикацией

```bash
npx publint                      # корректность exports, форматов, полей
npx @arethetypeswrong/cli .      # разрешение типов во всех режимах
npm pack --dry-run               # что реально попадёт в архив
```

Проверка потребления вручную:

```bash
# ESM
node -e "import('my-lib').then(m => console.log(Object.keys(m)))"
# CJS
node -e "console.log(Object.keys(require('my-lib')))"
# сборщиком — создайте тестовое приложение на Vite и соберите
```

Ставьте `publint` и `arethetypeswrong` в CI — они ловят большинство ошибок этого раздела автоматически.

# Частые ошибки

**`require` указывает на ESM-файл.** Потребитель получит `ERR_REQUIRE_ESM`. Ловится `publint`.

**`types` не первым.** Типы не находятся, IDE показывает `any`.

**`default` первым.** Все последующие условия недостижимы.

**Забыт `sideEffects`.** Без него сборщик не удалит неиспользуемое из вашего пакета — см. [[sideEffects в package.json]].

**Фреймворк в `dependencies` вместо `peerDependencies`.** Прямая дорога к двум экземплярам React/Angular у потребителя.

**Модульное состояние при dual-сборке.** См. [[Dual package hazard]] — вынесите состояние в общий CJS-модуль или откажитесь от dual.

**Отсутствие `files`.** В npm-архив уезжают исходники, тесты и конфиги. Не критично, но раздувает установку.

# Чем собирать

- **tsup** — обёртка над esbuild, dual + `.d.ts` из коробки, минимальный конфиг. Дефолтный выбор для небольших библиотек.
- **unbuild** — на Rollup, умеет «заглушки» для dev-режима в монорепе.
- **Rollup** напрямую — максимальный контроль, нужен для нетривиальных случаев.
- **Vite library mode** — если библиотека уже живёт в Vite-проекте.
- **ng-packagr** — для Angular-библиотек, формат навязан Angular Package Format (модуль 5 плана).
