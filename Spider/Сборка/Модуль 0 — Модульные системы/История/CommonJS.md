CommonJS (CJS) — модульная система Node.js, появившаяся в 2009 году. Формат по умолчанию для `.js` в Node до сих пор (пока в `package.json` не стоит `"type": "module"` — см. [[Поле type и расширения mjs cjs]]).

Это не стандарт ECMAScript. Это соглашение, реализованное рантаймом: `require`, `module`, `exports` — обычные переменные, которые Node подставляет в каждый файл.

# Синтаксис

```js
// math.js
function add(a, b) { return a + b; }
function sub(a, b) { return a - b; }

module.exports = { add, sub };
```

```js
// app.js
const math = require('./math');       // синхронно читает и выполняет файл
const { add } = require('./math');    // деструктуризация уже готового объекта

console.log(add(1, 2));
```

# Обёртка модуля — ключ к пониманию

Перед выполнением Node оборачивает содержимое файла в функцию:

```js
(function (exports, require, module, __filename, __dirname) {
  // ваш код
});
```

Отсюда следует всё остальное:

- **Изоляция бесплатна.** `var` на верхнем уровне файла — локальная переменная функции-обёртки, а не глобаль. Проблема из [[Эпоха до модулей]] решена самим механизмом.
- **`this` на верхнем уровне === `module.exports`.** В ESM там `undefined` — частая причина поломки при миграции.
- **`__dirname` и `__filename` существуют** — это аргументы обёртки. В ESM их нет, есть [[import.meta]].
- **Модуль не в strict mode по умолчанию.** ESM всегда strict.

# `module.exports` против `exports`

Самая распространённая ошибка новичков в CJS.

```js
exports.foo = 1;          // работает: мутируем объект, на который смотрит module.exports
module.exports.bar = 2;   // то же самое

exports = { baz: 3 };     // НЕ работает: переприсвоили локальный параметр
module.exports = { baz: 3 }; // работает: заменили сам экспортируемый объект
```

`exports` — просто ещё одна ссылка на тот же объект, что и `module.exports`. Присваивание в `exports` рвёт эту связь, а наружу отдаётся `module.exports`, который остался старым. Правило: **мутировать можно любое, присваивать — только `module.exports`**.

# Кэш модулей

`require` кэширует результат по абсолютному разрешённому пути в `require.cache`:

```js
require('./config');  // файл выполнен
require('./config');  // файл НЕ выполнен, вернулся тот же объект
```

Следствия:
- модуль — синглтон в пределах одного пути (см. [[Реестр модулей и singleton-семантика]]);
- **две копии пакета в разных `node_modules` — два разных экземпляра**, это корень [[Dual package hazard]];
- в тестах кэш иногда чистят (`delete require.cache[require.resolve('./x')]`) — в ESM такой возможности нет, что важно при миграции тестов.

# Динамичность — и почему она ломает сборщики

`require` — обычный вызов функции. Значит, он может стоять где угодно и принимать что угодно:

```js
if (process.env.NODE_ENV === 'production') {
  config = require('./config.prod');   // условный импорт
}

const plugin = require(pluginPath);    // имя вычисляется в рантайме

function lazy() {
  return require('./heavy');           // загрузка по требованию
}
```

Для разработчика это гибкость. Для сборщика — катастрофа: **граф модулей нельзя построить статически**. Именно поэтому:

- **tree shaking по CJS в общем случае невозможен.** Сборщик не знает, какие свойства `module.exports` вы используете, и не может доказать, что остальное не нужно;
- `require(pluginPath)` заставляет webpack включить в бандл **всю папку** (`ContextReplacementPlugin` существует именно для сужения этого поведения) либо упасть с предупреждением `Critical dependency: the request of a dependency is an expression`;
- Vite и другие ESM-first инструменты вынуждены **пре-бандлить** CJS-зависимости через esbuild, конвертируя их в ESM.

Сравните со статическим `import` в [[Статическая структура ESM]] — там граф известен до выполнения кода.

# Синхронность

`require` читает файл с диска **блокирующе**. В Node это приемлемо: файлы локальны, а модули грузятся при старте. В браузере — неприемлемо в принципе: синхронный сетевой запрос заморозил бы вкладку. Поэтому CommonJS в браузере работает только после сборки — бандлер заранее склеивает все модули в один файл и подменяет `require` на функцию, которая берёт модуль из локального реестра.

Именно из-за синхронности для браузера придумали [[AMD и RequireJS]].

# Циклические зависимости

CJS не падает на циклах, но возвращает **частично заполненный** объект:

```js
// a.js
exports.done = false;
const b = require('./b');   // здесь b уже выполнен, но он видел a незавершённым
exports.done = true;

// b.js
const a = require('./a');   // a.done === false — a ещё не дошёл до конца
exports.done = true;
```

Никакой ошибки, просто тихо неверные данные. В ESM то же самое даёт явный `ReferenceError` — подробности в [[Циклические зависимости]].

# Как CJS попадает в ваш фронтенд-бандл сегодня

Даже в чистом ESM-проекте CommonJS никуда не делся:

- множество npm-пакетов до сих пор публикует только CJS;
- `@rollup/plugin-commonjs` и esbuild конвертируют их в ESM на лету;
- конвертация не бесплатна: named exports из CJS определяются эвристикой (`cjs-module-lexer`), и на нестандартном коде она ошибается — отсюда ошибки вида `"X" is not exported by "node_modules/..."`;
- Vite делает это на этапе `optimizeDeps` (pre-bundling), и «зависимость не работает в dev, но работает в prod» почти всегда про это.

Разбор ошибок — в [[ESM и CommonJS — взаимодействие]] и [[Диагностика ошибок модульных систем]].

# Чеклист практика

- Пакет публикует только CJS → в браузерном бандле он будет сконвертирован, tree shaking не сработает, размер вырастет.
- Видите `require()` с переменной внутри → готовьтесь к проблемам со сборкой.
- Мигрируете файл на ESM → проверьте `__dirname`, `this`, `module.exports`, `require.cache`.
