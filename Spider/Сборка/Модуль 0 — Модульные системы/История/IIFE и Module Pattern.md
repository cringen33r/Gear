IIFE (Immediately Invoked Function Expression) — функция, которая объявляется и тут же вызывается. До появления модульных систем это был единственный способ создать приватную область видимости, поскольку в JavaScript до ES6 областью видимости была **только функция** (`var` не знает блочной области).

# Базовая форма

```js
(function () {
  var counter = 0; // не попадает в window
  // ...
})();
```

Скобки вокруг `function` превращают объявление функции в **выражение** — иначе парсер ждёт имя функции и падает. Отсюда варианты записи: `(function(){}())`, `!function(){}()`, `void function(){}()`. В минифицированном коде вы увидите все три.

# Module Pattern: IIFE + возврат публичного API

```js
var Counter = (function () {
  var count = 0;              // приватное

  function increment() {      // приватная реализация
    count += 1;
    return count;
  }

  return {                    // публичный контракт
    inc: increment,
    get value() { return count; }
  };
})();

Counter.inc();      // 1
Counter.count;      // undefined — недоступно снаружи
```

Это первый в истории JS способ разделить публичное и приватное. Замыкание удерживает `count` живым, наружу выдаётся только объект с методами.

# Revealing Module Pattern

Вариация, где вся реализация объявлена как обычные функции, а возвращается только «карта» имён:

```js
var Api = (function () {
  function load() { /* ... */ }
  function save() { /* ... */ }
  function internalRetry() { /* ... */ }

  return { load: load, save: save };  // internalRetry скрыт
})();
```

Читаемее, потому что публичный контракт собран в одном месте — принцип, который позже воспроизведён в `index.ts` с ре-экспортами (см. [[Синтаксис импортов и экспортов]]).

# Явные зависимости через аргументы

Ключевая деталь, которую стоит заметить: зависимости передаются **параметрами IIFE**.

```js
var Widget = (function ($, _) {
  // внутри $ и _ — локальные имена, не глобальные
  return { /* ... */ };
})(jQuery, lodash);
```

Это ровно та идея, которую позже формализовали [[AMD и RequireJS]] и [[CommonJS]]: модуль объявляет, что ему нужно, а система подставляет реализацию. Плюс побочная выгода — минификатор может сжать локальные `$` и `_` до однобуквенных имён, а движок резолвит их быстрее, чем глобальные.

Ещё один типовой приём — передача глобального объекта, чтобы код работал и в браузере, и в Node:

```js
(function (root, factory) {
  root.MyLib = factory();
})(typeof self !== 'undefined' ? self : this, function () { /* ... */ });
```

Это уже почти [[UMD]].

# Что IIFE решил и что нет

Решил: конфликты имён, приватность, контроль над тем, что публикуется наружу.

Не решил:
- **Загрузку.** Файл всё равно надо подключить `<script>` вручную и в правильном порядке.
- **Граф зависимостей.** Никто, кроме человека, не знает, что `Widget` нужен `jQuery`.
- **Дедупликацию.** Подключили библиотеку дважды — получили два экземпляра.

Именно поэтому IIFE — паттерн, а не модульная система.

# Где IIFE живёт сегодня

Не архаика: это **формат вывода сборщика**. `format: 'iife'` в Rollup, `libraryTarget: 'var'` в webpack.

```js
// build/widget.js
var MyWidget = (function () {
  'use strict';
  // ... весь граф модулей, схлопнутый в одну функцию
  return { mount: mount };
})();
```

Когда это нужно:
- виджет, встраиваемый на чужую страницу одним `<script>`;
- скрипт без сборщика на стороне потребителя;
- букмарклеты, инъекции, расширения.

Кроме того, **scope hoisting** (module concatenation) в современных бандлерах — это по сути автоматическое схлопывание графа модулей в одну IIFE-подобную область. Об этом в модуле 2 плана.

Отдельно: `/*#__PURE__*/` перед IIFE — аннотация для минификатора, что вызов можно удалить, если результат не используется. См. [[Побочные эффекты модулей]].
