UMD (Universal Module Definition) — не формат, а **паттерн-обёртка**, которая определяет окружение в рантайме и подстраивается: [[AMD и RequireJS]], [[CommonJS]] или глобальная переменная. Родился из необходимости публиковать одну сборку для всех потребителей сразу.

Вы встречаете UMD постоянно: `dist/*.umd.js`, `dist/*.js` у библиотек с широкой совместимостью, вывод `format: 'umd'` в Rollup.

# Канонический вид

```js
(function (root, factory) {
  if (typeof define === 'function' && define.amd) {
    define(['dependency'], factory);              // AMD
  } else if (typeof module === 'object' && module.exports) {
    module.exports = factory(require('dependency')); // CommonJS
  } else {
    root.MyLib = factory(root.Dependency);        // глобальная переменная
  }
})(typeof self !== 'undefined' ? self : this, function (dependency) {
  'use strict';
  function doWork() { /* ... */ }
  return { doWork: doWork };
});
```

Читается так: сначала проверка на AMD (`define` с флагом `amd`), потом на CJS (`module.exports`), иначе — фолбэк в глобаль. Порядок проверок именно такой, потому что AMD-загрузчик мог присутствовать одновременно с CJS-подобным окружением.

`typeof self !== 'undefined' ? self : this` — попытка добыть глобальный объект: `self` есть в браузере и в Web Worker, `this` работает в CJS-обёртке. В современном коде эту акробатику заменяет `globalThis`.

# Чем UMD платит

**1. Не поддаётся tree shaking.** Экспорт — это объект, собранный внутри функции в рантайме. Сборщик не может статически доказать, что `doWork` не используется, и удалить его. UMD-сборка всегда попадает в бандл целиком. Это главная причина не подключать `dist/*.umd.js` в приложении, если у пакета есть ESM-сборка — см. [[Точки входа пакета — main, module, browser, types]].

**2. Ветвление сбивает анализаторы.** Внутри бандлера все три ветки остаются в коде, а `typeof define` может неожиданно оказаться истинным.

**3. Именованные зависимости.** Глобальная ветка требует, чтобы `root.Dependency` уже существовал, то есть возвращает нас к ручному порядку подключения из [[Эпоха до модулей]].

**4. Размер.** Обёртка на каждый файл, если публикуется не единым бандлом.

# Когда UMD всё ещё правильный выбор

- **Виджет/SDK для встраивания на чужой сайт** одним `<script src>` без сборки на стороне потребителя.
- **Библиотека с неизвестной аудиторией**, часть которой сидит на старых стеках.
- **CDN-раздача** (`unpkg`, `jsdelivr`) — там ожидают именно глобальную переменную.

Во всех этих случаях UMD публикуется **дополнительно**, а не вместо ESM. Современная раскладка пакета: ESM для сборщиков, CJS для Node, UMD/IIFE для `<script>`. Как это описать в `package.json` — [[Публикация пакета для ESM и CJS]].

# UMD против IIFE в выводе сборщика

| | IIFE | UMD |
|---|---|---|
| Определяет окружение | нет | да |
| Работает в AMD-загрузчике | нет | да |
| Работает как CJS-модуль | нет | да |
| Размер обёртки | минимальный | больше |
| Когда брать | только `<script>` | `<script>` + легаси-потребители |

Если аудитория точно современная — берите `iife`, он проще (см. [[IIFE и Module Pattern]]). UMD нужен, только если реально ожидаются AMD- или CJS-потребители одного и того же файла.

# Типовые проблемы на практике

**Библиотека «не находит» зависимость в бандле.** UMD ушёл в глобальную ветку и ищет `window.React`, которого нет. Лечится настройкой `externals`/`output.globals` либо переходом на ESM-сборку пакета.

**Двойное подключение.** UMD-файл через `<script>` плюс тот же пакет в бандле = два экземпляра со своим состоянием. Механика та же, что в [[Dual package hazard]].

**`define is not defined` или, наоборот, захват AMD-веткой.** В окружении присутствует чужой `define`. Обходной приём — временно снять его перед подключением скрипта.
