До 2009 года в JavaScript не было ни одного способа изолировать код. Всё, что объявлено на верхнем уровне скрипта, попадало в глобальный объект. Понимание этой отправной точки объясняет, зачем существуют все последующие форматы.

# Как это работало

```html
<script src="jquery.js"></script>
<script src="utils.js"></script>
<script src="app.js"></script>
```

Каждый файл выполнялся в **общей глобальной области**. `var name = 'x'` на верхнем уровне создавал `window.name`. Никакого `import` не было: файлы «общались» через глобальные переменные, а порядок подключения был контрактом между ними.

```js
// utils.js
var formatDate = function (d) { /* ... */ };

// app.js — работает только потому, что utils.js подключён выше
var text = formatDate(new Date());
```

# Четыре проблемы, которые породили модули

**1. Конфликты имён.** Две библиотеки, объявившие `$` или `each`, молча затирали друг друга. Побеждала та, что подключена позже. Отсюда родился паттерн `noConflict()` у jQuery — попытка вернуть себе имя после захвата.

**2. Неявные зависимости.** Ниоткуда не видно, что `app.js` нужен `utils.js`. Зависимости жили в HTML, а не в коде, и при рефакторинге терялись. Сломанный порядок давал `undefined is not a function` в рантайме, а не ошибку загрузки.

**3. Ручное управление порядком.** С ростом проекта порядок `<script>` превращался в топологическую сортировку, выполняемую человеком. Циклическая зависимость означала, что решения нет вообще.

**4. Блокирующая загрузка.** Классический `<script>` без атрибутов останавливает парсинг HTML: браузер скачивает и выполняет файл, потом продолжает строить DOM. Десяток скриптов в `<head>` — это десяток последовательных блокировок. Отсюда практика «скрипты в конец `<body>`» и позже атрибуты `defer`/`async` — см. [[Загрузка скриптов — async, defer, modulepreload]].

# Что из этого осталось в современной сборке

Это не только история. Легаси-код и часть библиотек до сих пор рассчитывают на глобальное окружение, и сборщик обязан это поддерживать:

- **`script`-поле в `angular.json` и аналоги** — файлы, которые подключаются как классические скрипты и намеренно пишут в `window` (например, старые полифилы или SDK аналитики).
- **Формат вывода `iife`/`umd`** — сборщик заворачивает бандл в функцию и публикует одно имя в глобальной области. Нужен для виджетов, встраиваемых на чужие сайты. См. [[UMD]].
- **`externals` в webpack / `external` в Rollup** — зависимость не бандлится, а ожидается в `window` (классика: React с CDN).
- **`ProvidePlugin` / `inject`** — автоподстановка глобалей вроде `$` в модули, которые их не импортируют.

Практический вывод: если библиотека в `dist` объявляет `window.SomeLib`, она из этой эпохи. Импортировать её через `import` можно только если сборщик обёрнут поверх неё shim — либо через `script`-подключение и объявление типов.

# Почему просто «обернуть в функцию» оказалось недостаточно

Следующий шаг эволюции — изоляция средствами самого языка, без стандарта: [[IIFE и Module Pattern]]. Он решил проблему конфликтов имён, но не решил проблему зависимостей и порядка. Настоящие модули появились только с [[CommonJS]] и позже [[ES Modules — обзор]].
