Поле `sideEffects` — обещание, которое пакет даёт сборщику: «модули отсюда можно не выполнять, если из них ничего не импортируют». Без него tree shaking работает вполсилы даже для идеального ESM-кода.

Не стандарт Node — соглашение webpack, подхваченное Rollup, Vite и esbuild.

# Синтаксис

```json
{ "sideEffects": false }
```

«Ни один модуль пакета не имеет [[Побочные эффекты модулей|побочных эффектов]] — удаляй смело».

```json
{ "sideEffects": ["./src/polyfills.js", "*.css", "*.scss"] }
```

«Все модули чисты, **кроме** перечисленных». Значения — глобы. Самая частая и правильная форма для библиотеки со стилями.

```json
{ "sideEffects": true }
```

Значение по умолчанию при отсутствии поля: «эффекты возможны везде, ничего не удаляй».

# Что именно меняется

```js
import { formatDate } from 'my-lib';
```

Предположим, `my-lib/index.js` ре-экспортирует 50 модулей.

**Без `sideEffects`.** Сборщик обязан **выполнить** все 50 модулей — вдруг у них есть эффекты. Он может выбросить неиспользуемые *экспорты*, но сами модули остаются в бандле.

**С `sideEffects: false`.** Сборщик выбрасывает 49 модулей целиком, не включая их код в бандл вовсе.

Разница на реальных библиотеках — десятки и сотни килобайт. Это то самое поле, из-за отсутствия которого «tree shaking не работает».

# Практическое влияние: barrel-файлы

```js
// my-lib/index.js
export * from './Button.js';
export * from './Table.js';       // тяжёлый, тянет виртуализацию
export * from './Chart.js';       // очень тяжёлый, тянет d3
// ... ещё 40 строк
```

Потребитель импортирует только `Button`. Попадёт ли `Chart` в бандл, определяется **исключительно** наличием `sideEffects: false`. Именно поэтому у UI-китов это поле — обязательное.

# Главная ловушка: CSS

```js
// Button.js
import './Button.css';        // эффектный импорт
export function Button() {}
```

При `sideEffects: false` сборщик считает, что `Button.css` можно не подключать, — и **стили исчезают из прода**. Симптом узнаваемый: локально всё красиво, после сборки компоненты голые.

Правильно:

```json
{ "sideEffects": ["*.css", "*.scss"] }
```

Это самая частая ошибка при добавлении поля. Если ваша библиотека содержит стили — `false` вам не подходит.

# Взаимодействие с `/*#__PURE__*/`

Два механизма разного уровня:

- `sideEffects` — на уровне **модуля**: «этот файл можно не включать»;
- `/*#__PURE__*/` — на уровне **выражения**: «этот вызов можно удалить, если результат не нужен».

Они дополняют друг друга. Аннотации нужны там, где на верхнем уровне есть вызовы функций, — см. [[Побочные эффекты модулей]].

# Поддержка инструментами

**webpack** — родной механизм, `optimization.sideEffects` (включён в `mode: production`).

**Rollup** — читает через `@rollup/plugin-node-resolve`; собственные настройки в `treeshake.moduleSideEffects`.

**Vite** — наследует поведение Rollup в prod-сборке. В dev не применяется (там нет tree shaking вовсе — см. [[Предел нативного ESM в браузере]]).

**esbuild** — учитывает поле, но его tree shaking в целом менее агрессивен, чем у Rollup.

Практическое следствие: **эффект от `sideEffects` виден только в продакшн-сборке**. Проверять в dev бессмысленно.

# Как выставить у себя

Алгоритм для своей библиотеки:

1. Найдите все модули с эффектами: импорты CSS, полифилы, регистрации, патчи прототипов, верхнеуровневые вызовы.
2. Нет ни одного → `"sideEffects": false`.
3. Есть → перечислите их глобами.
4. Соберите тестовое приложение, импортирующее одну функцию, и посмотрите размер бандла.
5. Проверьте, что стили и полифилы на месте.

Пункты 4–5 обязательны: ошибка в любую сторону не даёт ошибки сборки, только неверный результат.

# Как проверить чужой пакет

```bash
cat node_modules/some-lib/package.json | grep sideEffects
```

Нет поля → библиотека попадёт в бандл почти целиком. Если это заметная часть вашего размера, варианты:

- взять субимпорт конкретного модуля (`some-lib/dist/button`), если пакет это позволяет;
- заменить пакет на более дружественный (классика: `lodash` → `lodash-es`);
- в webpack переопределить через `module.rules` с `sideEffects: false` для конкретного пути — приём рискованный, но работающий;
- открыть issue.

# Типовые ошибки

| Ошибка | Симптом |
|---|---|
| `false` при наличии CSS-импортов | пропали стили в проде |
| `false` при наличии полифилов | падение в старых браузерах |
| Поле отсутствует | бандл больше ожидаемого |
| Глоб не совпадает с путями | эффектные модули всё равно удаляются |
| Ждут эффекта в dev-режиме | tree shaking там не работает |

Про глобы: пути в массиве сопоставляются относительно корня пакета. Проверяйте, что `"*.css"` действительно покрывает ваши файлы во вложенных папках — при сомнениях пишите `"**/*.css"`.
