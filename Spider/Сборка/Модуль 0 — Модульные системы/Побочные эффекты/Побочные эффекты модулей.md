Побочный эффект модуля — любое наблюдаемое действие, которое происходит **при выполнении его тела**, а не при вызове экспортированных функций. Понятие критично, потому что оно определяет границу возможностей tree shaking: [[Статическая структура ESM]] даёт знание графа, но право удалить код даёт только отсутствие эффектов.

# Что считается эффектом

```js
// utils.js
console.log('загружен');                   // ✅ эффект: вывод
window.myGlobal = {};                      // ✅ эффект: запись в глобаль
Array.prototype.last = function () {};     // ✅ эффект: патч прототипа
document.addEventListener('click', fn);    // ✅ эффект: подписка
registry.register('utils', handler);       // ✅ эффект: регистрация
fetch('/analytics');                       // ✅ эффект: сетевой запрос
let cache = new Map();                     // ❌ не эффект: локальная переменная
export function helper() {}                // ❌ не эффект: объявление
export const CONST = 42;                   // ❌ не эффект: примитив
```

Формулировка для практики: **эффект — это когда удаление модуля из бандла изменит поведение программы, даже если из него ничего не импортировали**.

# Почему это блокирует удаление кода

```js
import { formatDate } from './utils.js';
```

Сборщик видит, что нужен только `formatDate`, и хочет выбросить остальное. Но если в `utils.js` на верхнем уровне есть `Array.prototype.last = ...`, выбрасывать нельзя: код, полагающийся на этот патч, сломается.

Сборщик не может доказать безопасность, поэтому действует консервативно — **оставляет всё**. Тот же принцип применяется к пакету целиком через [[sideEffects в package.json]].

# Неочевидные источники эффектов

## Вызов функции на верхнем уровне

```js
export const config = loadConfig();   // сборщик не знает, что делает loadConfig
```

Любой вызов на верхнем уровне потенциально имеет эффект. Даже если функция чистая, доказать это статически трудно.

Решение — аннотация:

```js
export const config = /*#__PURE__*/ loadConfig();
```

Комментарий `/*#__PURE__*/` — обещание минификатору: «вызов чист, если результат не нужен — удали его». Терсер и esbuild его понимают.

Внимание: это **обещание, а не проверка**. Соврали — получили тихо сломанный прод.

## Классы с декораторами

```ts
@Injectable({ providedIn: 'root' })
export class UserService {}
```

Декоратор компилируется в вызов функции на верхнем уровне модуля. Именно поэтому Angular-компилятор помечает свой сгенерированный код `/*#__PURE__*/` — без этого ни один сервис не удалился бы из бандла никогда.

## Полифилы

```js
import 'core-js/stable';
import 'zone.js';
```

Это чистые эффекты, и это нормально — они для того и существуют. Важно только не дать сборщику их удалить (см. [[sideEffects в package.json]]).

## Импорт CSS

```js
import './styles.css';
```

Расширение сборщика, и с точки зрения графа — эффектный импорт. Самая частая причина, по которой `sideEffects: false` в библиотеке приводит к пропаже стилей в проде.

## Инициализация статических полей

```js
class Registry {
  static instance = new Registry();   // выполняется при загрузке модуля
}
```

## Модификация импортированного объекта

```js
import { config } from './config.js';
config.debug = true;      // эффект: мутация чужого состояния
```

# Как писать код, дружественный к tree shaking

**Выносите инициализацию в функции.**

```js
// ❌ эффект при загрузке
export const client = new ApiClient({ baseUrl: '/api' });

// ✅ эффект при вызове
export function createClient() { return new ApiClient({ baseUrl: '/api' }); }
```

Второй вариант позволяет выбросить `ApiClient` целиком, если `createClient` никто не зовёт.

**Не патчите прототипы.** Расширения встроенных типов — эффект, который держит модуль в бандле навсегда, и вдобавок конфликтует с чужим кодом.

**Не регистрируйте ничего при загрузке.** Паттерн «модуль сам себя регистрирует в реестре при импорте» удобен, но делает модуль неудаляемым и создаёт неявную зависимость от порядка импортов.

**Отделяйте эффектные модули.** Полифилы, глобальные стили, регистрации — в отдельные файлы, импортируемые явно из точки входа. Тогда остальная кодовая база остаётся чистой.

**Аннотируйте чистые вызовы** через `/*#__PURE__*/`, если без верхнеуровневого вызова не обойтись.

# Как проверить

**Отключите минификацию и посмотрите бандл.** Самый прямой способ: собрали, нашли в выводе функцию, которую не импортировали, — значит, что-то удержало модуль.

**Анализатор бандла.** `source-map-explorer`, `rollup-plugin-visualizer` покажут, какой модуль занимает место вопреки ожиданиям.

**Rollup сообщает о причинах.** При `treeshake: { moduleSideEffects: false }` можно поэкспериментировать и увидеть разницу.

**Тест-заглушка.** Соберите файл, который импортирует одну функцию из библиотеки, и посмотрите размер. Это базовая проверка «шейкается ли пакет вообще».

# Граница ответственности

Побочные эффекты — не зло. Полифил обязан иметь эффект, глобальные стили обязаны применяться. Задача не в том, чтобы их не было, а в том, чтобы:

1. они были **осознанными** и локализованными в отдельных модулях;
2. сборщик **знал** о них — через [[sideEffects в package.json]] или их отсутствие.

Ошибка в любую сторону дорога: недообъявили — пропали стили и полифилы в проде; переобъявили — в бандл уехало всё.
