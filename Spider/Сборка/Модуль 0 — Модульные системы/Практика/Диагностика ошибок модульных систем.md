Справочник по сообщениям об ошибках. Читается не подряд, а по симптому. Каждая запись: что означает → почему возникло → что делать.

# Ошибки формата файла

## `Cannot use import statement outside a module`

Файл разбирается как [[CommonJS]], а внутри ESM-синтаксис.

Причины и лечение:
- нет `"type": "module"` в ближайшем `package.json` → добавить, либо переименовать файл в `.mjs`;
- файл имеет расширение `.cjs` → переименовать;
- инструмент прогоняет файл через CJS-загрузчик (старый Jest без ESM-режима, ts-node с `module: commonjs`) → настроить инструмент;
- зависимость публикует ESM, а вы её `require` → см. [[require(esm) в Node.js]].

См. [[Поле type и расширения mjs cjs]].

## `require is not defined in ES module scope`

Обратная ситуация: файл — ESM, а в нём `require`.

```js
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
```

Либо переименовать файл в `.cjs`, либо переписать на `import`.

Частный случай: **упал конфиг после добавления `"type": "module"`**. Конфиги (`.eslintrc.js`, `jest.config.js`, `tailwind.config.js`) стали ESM. Переименуйте их в `.cjs`.

## `__dirname is not defined in ES module scope`

```js
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';
const __dirname = dirname(fileURLToPath(import.meta.url));
// или в Node 21.2+:
const __dirname = import.meta.dirname;
```

См. [[import.meta]].

## `ERR_REQUIRE_ESM`

CJS пытается `require` ESM-модуль.

- обновить Node до версии с поддержкой `require(esm)` — [[require(esm) в Node.js]];
- либо `await import()` в асинхронном контексте;
- либо, если это ваш пакет, проверить, что условие `require` в [[Поле exports]] указывает на настоящий CJS-файл.

## `ERR_REQUIRE_ASYNC_MODULE`

`require(esm)` сработал бы, но в графе есть [[Top-level await]]. Синхронная загрузка невозможна в принципе. Только `await import()`.

## `ERR_UNKNOWN_FILE_EXTENSION ".ts"`

Node не умеет исполнять TypeScript без загрузчика. Нужен `tsx`, `ts-node`, `--experimental-strip-types` или предварительная компиляция.

# Ошибки резолвинга

## `ERR_MODULE_NOT_FOUND`

В ESM расширения обязательны:

```js
import './utils';       // ❌
import './utils.js';    // ✅
```

Если это bare-спецификатор — пакет не установлен или недоступен по этому пути. Проверьте `npm ls <пакет>`.

## `ERR_UNSUPPORTED_DIR_IMPORT`

Импорт директории. В ESM `index.js` не подставляется автоматически:

```js
import './components/index.js';
```

## `ERR_PACKAGE_PATH_NOT_EXPORTED`

Пакет использует [[Поле exports]], и запрошенный подпуть в нём не описан.

```
Package subpath './dist/internal/helper.js' is not defined by "exports"
```

Типично после обновления зависимости, которая добавила `exports`.

- найдите официальный подпуть в документации пакета;
- если его нет — issue автору;
- временный обход в сборщике: `resolve.alias` напрямую на файл (в чистом Node обойти нельзя).

## `Failed to resolve module specifier "lodash"`

Браузер не умеет bare-спецификаторы. Нужен [[Import maps]] или сборщик. См. [[Спецификаторы модулей]].

## `Cannot find module '@app/...'` при работающих типах

Классический рассинхрон: `paths` в `tsconfig.json` есть, алиас в конфиге сборщика — нет. TypeScript **не переписывает пути** при компиляции.

Продублируйте алиас в сборщике (`resolve.alias`), тест-раннере (`moduleNameMapper`), линтере. Или используйте `vite-tsconfig-paths` / `tsconfig-paths-webpack-plugin`. Стандартная альтернатива — [[Поле imports и внутренние алиасы]].

## Собирается локально, падает в CI

Почти всегда — **регистр пути**. macOS/Windows регистронезависимы, Linux нет.

```js
import { Button } from './components/button';   // файл Button.tsx
```

Лечение: точный регистр везде, `case-sensitive-paths-webpack-plugin` локально, чтобы ловить сразу.

# Ошибки экспортов

## `The requested module does not provide an export named 'X'`

Класс ошибки — `SyntaxError`, и возникает она **до выполнения кода** (фаза instantiation, см. [[Фазы загрузки ESM]]).

Два разных случая:

**1. Опечатка или экспорта действительно нет.** Проверьте имя.

**2. Модуль — CommonJS, и named-экспорт не распознан статическим анализом.** Обходной путь:

```js
import pkg from 'some-cjs-lib';
const { thing } = pkg;
```

См. [[ESM и CommonJS — взаимодействие]].

## `"X" is not exported by "node_modules/..."` (Rollup/Vite)

То же самое на стороне сборщика: `@rollup/plugin-commonjs` не смог вывести named-экспорт.

- в Vite: добавить пакет в `optimizeDeps.include`;
- либо `commonjsOptions.namedExports` (в старых версиях);
- либо импортировать default и деструктурировать.

## `X is not a function` после сборки

Проблема интеропа default. Проверьте:

- нужен ли `.default`: `const fn = mod.default ?? mod`;
- включён ли `esModuleInterop` в `tsconfig.json`;
- не изменился ли формат вывода (`cjs` вместо `esm`).

# Ошибки времени выполнения

## `Cannot access 'X' before initialization`

[[Циклические зависимости]]. Модуль обращается к значению, чьё тело ещё не выполнилось.

- найти цикл: `npx madge --circular src/`;
- вынести общее в третий модуль;
- если зависимость только по типам — `import type`;
- отложить обращение внутрь функции.

## `Class extends value undefined is not a constructor`

Частный случай цикла: `extends` вычисляется на верхнем уровне. Типично при двусторонних связях моделей.

## Приложение зависло без ошибки

Дедлок [[Top-level await]] в цикле. Никакого исключения не будет. Проверьте, есть ли TLA в модулях, участвующих в цикле.

## `Invalid hook call` / контекст не находится / `instanceof` false

Два экземпляра библиотеки. См. [[Dual package hazard]].

```bash
npm ls react
npm why react
```

Лечение: `dedupe`, `overrides`, `resolve.alias`, `peerDependencies`.

# Браузерные ошибки

## `Failed to load module script: MIME type "text/plain"`

Сервер отдаёт JS с неправильным `Content-Type`. Настройте статику (частая проблема с `.mjs` в nginx).

## Модули не грузятся с `file://`

Origin — `null`, CORS не пройдёт. Нужен HTTP-сервер: `npx serve`.

## `Access to script blocked by CORS policy`

Модули всегда загружаются в режиме CORS. Кросс-доменный модуль требует `Access-Control-Allow-Origin`. См. [[Модули в браузере — script type=module]].

## `Failed to fetch dynamically imported module`

Ленивый чанк недоступен. Самый частый продовый сценарий: **был деплой, старые чанки с прежними хешами удалены с CDN, у пользователя открыта старая вкладка**.

Обязательный обработчик в приложениях с ленивыми маршрутами:

```js
try {
  const m = await import('./route.js');
} catch {
  // предложить перезагрузку страницы
}
```

См. [[Динамический import()]].

# Проблемы сборки

## Node-модули в браузерном бандле

```
Module "fs" has been externalized for browser compatibility
Can't resolve 'path'
```

В граф попал серверный код. Правильный ответ — **убрать зависимость**, а не полифилить. Проверьте:

- не активировано ли условие `browser` (см. [[Условия резолвинга]]);
- нет ли случайного импорта серверного модуля;
- корректны ли `target`/`platform` в конфиге сборщика.

Полифилить (`node-stdlib-browser`, `vite-plugin-node-polyfills`) — последнее средство: это лишние килобайты и часто нерабочие заглушки.

## `Critical dependency: the request of a dependency is an expression`

`require()` или `import()` с полностью динамическим путём. Сборщик не может построить граф.

Сузьте путь до литерала или шаблона со статической частью. См. [[Динамический import()]].

## Пропали стили в проде

`sideEffects: false` при наличии CSS-импортов. См. [[sideEffects в package.json]].

```json
{ "sideEffects": ["**/*.css", "**/*.scss"] }
```

## Работает в dev, падает в prod (Vite)

Разные машины: dev — нативный ESM + esbuild-пребандлинг, prod — Rollup. Типовые причины:

- CJS-зависимость по-разному конвертируется → `optimizeDeps.include`;
- в dev нет tree shaking, в prod что-то удалилось → проверьте побочные эффекты;
- разные условия резолвинга для dev и prod.

См. [[Предел нативного ESM в браузере]].

## На pnpm не собирается, на npm собиралось

Фантомная зависимость: вы импортируете пакет, не объявленный в своём `package.json`. При плоской установке npm он оказывался доступен как транзитивный; pnpm это запрещает.

Лечение правильное: добавить пакет в `dependencies`.

# Общий порядок отладки

1. **Определить фазу.** Резолвинг (файл не найден) → связывание (нет экспорта) → выполнение (ошибка в коде). Класс ошибки почти всегда подсказывает.
2. **Проверить формат.** ESM или CJS? Что говорит `type` ближайшего `package.json`?
3. **Проверить резолвинг.** `node -e "console.log(require.resolve('пакет'))"`, `npm ls пакет`.
4. **Прочитать `package.json` зависимости.** `exports`, `main`, `module`, `type` — этого хватает в большинстве случаев.
5. **Сравнить окружения.** Работает в Node, но не в сборке (или наоборот) → разные условия резолвинга.
