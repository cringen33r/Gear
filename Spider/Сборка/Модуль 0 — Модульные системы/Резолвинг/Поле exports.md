`exports` — современный способ описать публичный интерфейс пакета. Заменяет `main`/`module`/`browser` и добавляет два принципиально новых свойства: **инкапсуляцию** и **условный резолвинг**.

Главное правило: **если `exports` присутствует, он единственный источник истины**. `main` и `module` игнорируются, всё, что не перечислено, недоступно.

# Формы записи

## Сокращённая

```json
{ "exports": "./dist/index.js" }
```

Эквивалент `main`, но с инкапсуляцией: доступен только корневой импорт.

## Условия для корня

```json
{
  "exports": {
    "types": "./dist/index.d.ts",
    "import": "./dist/index.js",
    "require": "./dist/index.cjs",
    "default": "./dist/index.js"
  }
}
```

Разные файлы для разных способов подключения. Механика — [[Условия резолвинга]].

## Subpath exports

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js",
    "./styles.css": "./dist/styles.css",
    "./package.json": "./package.json"
  }
}
```

`"."` — корневой импорт (`import 'pkg'`), остальные — подпути (`import 'pkg/utils'`).

Обратите внимание на `"./package.json"`: без него потребитель не сможет прочитать ваш `package.json`, а некоторые инструменты это делают. Хорошая практика — всегда экспортировать его явно.

## Комбинация: подпути с условиями

Основная форма для реальных пакетов:

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "browser": "./dist/index.browser.js",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./server": {
      "types": "./dist/server.d.ts",
      "node": "./dist/server.js",
      "default": null
    }
  }
}
```

`"default": null` блокирует импорт `pkg/server` везде, кроме Node — попытка собрать это в браузерный бандл даст внятную ошибку вместо непонятного падения.

## Шаблоны

```json
{
  "exports": {
    "./features/*": "./dist/features/*.js",
    "./locales/*.json": "./dist/locales/*.json"
  }
}
```

`*` подставляется буквально: `import 'pkg/features/auth'` → `./dist/features/auth.js`. Это не glob — просто подстановка подстроки.

Практическая ценность: **не нужно перечислять сотни файлов вручную**, при этом инкапсуляция сохраняется (доступна только папка `features`, а не весь `dist`).

## Блокировка

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./internal/*": null
  }
}
```

# Инкапсуляция — главное следствие

До `exports` любой файл пакета был доступен:

```js
import helper from 'some-lib/dist/internal/helper.js';   // работало всегда
```

Это делало **любой** файл частью публичного API: переименовали внутренний файл — сломали чужой код. С `exports` доступно только перечисленное:

```
ERR_PACKAGE_PATH_NOT_EXPORTED: Package subpath './dist/internal/helper.js'
is not defined by "exports"
```

Два практических следствия:

**Для автора библиотеки** — свобода рефакторинга внутренностей. Явно опишите публичный API, остальное ваше.

**Для потребителя** — добавление `exports` в новую версию зависимости может **сломать сборку**. Ошибка `ERR_PACKAGE_PATH_NOT_EXPORTED` при обновлении пакета означает именно это. Лечится переходом на официальный подпуть; если такого нет — issue в репозиторий, а как временный обход — `resolve.alias` на файл напрямую (сборщики позволяют обойти инкапсуляцию, Node — нет).

# Критично: порядок ключей значим

`exports` резолвится **сверху вниз, первое совпадение выигрывает**. Это не обычный объект, где порядок безразличен.

```json
// ❌ неправильно
{ "exports": { ".": { "default": "./index.js", "import": "./index.mjs" } } }
```

`default` совпадает всегда, поэтому `import` недостижим. Правило: **`default` всегда последний, `types` всегда первый**.

```json
// ✅ правильно
{ "exports": { ".": {
  "types": "./index.d.ts",
  "browser": "./index.browser.js",
  "import": "./index.mjs",
  "require": "./index.cjs",
  "default": "./index.mjs"
} } }
```

Подробнее о порядке и наборе условий — [[Условия резолвинга]].

# Ограничения

**Только относительные пути.** Значение обязано начинаться с `./`. Нельзя перенаправить на другой пакет.

**Нет расширений по умолчанию.** Указываете точный файл.

**Все пути от корня пакета**, а не от `exports`-записи.

# Типовые ошибки

**Забыли `types` и типы «отвалились» после смены `moduleResolution`.** При `node16`/`bundler` TypeScript ищет типы внутри `exports`; корневое поле `types` перестаёт использоваться. Условие `types` должно быть первым в каждой ветке.

**Условие `require` указывает на ESM-файл.** Приводит к `ERR_REQUIRE_ESM` у потребителя. Проверяйте, что формат файла соответствует условию — см. [[Поле type и расширения mjs cjs]].

**Разное состояние в ESM- и CJS-ветках.** Прямая дорога к [[Dual package hazard]].

**Забыли `./package.json`.** Инструменты, читающие метаданные пакета, ломаются.

# Как проверить

```bash
npx publint                    # проверка корректности exports и формата файлов
npx @arethetypeswrong/cli pkg  # проверка типов во всех режимах резолвинга
```

Оба инструмента стоит поставить в CI любой публикуемой библиотеки — они ловят большинство описанных ошибок автоматически.

Ручная проверка после сборки:

```bash
node -e "import('pkg').then(m => console.log(Object.keys(m)))"
node -e "console.log(Object.keys(require('pkg')))"
```
