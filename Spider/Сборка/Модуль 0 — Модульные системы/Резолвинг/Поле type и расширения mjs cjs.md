Найдя файл, Node должен решить: разбирать его как ESM или как CommonJS. Формат влияет на синтаксис, семантику и доступные глобали, и **определяется не содержимым файла**, а расширением и полем `type`.

# Правила определения формата

| Расширение | Формат |
|---|---|
| `.mjs` | всегда ESM |
| `.cjs` | всегда CommonJS |
| `.js` | зависит от `type` ближайшего `package.json` |
| `.json` | JSON (в ESM нужен атрибут, см. [[Import attributes и JSON-модули]]) |
| `.node` | нативный аддон, только CJS |

Для TypeScript зеркально: `.mts` → ESM, `.cts` → CJS, `.ts` → по `type`.

# Поле `type`

```json
{ "type": "module" }     // .js в этом дереве = ESM
{ "type": "commonjs" }   // .js = CJS (значение по умолчанию)
```

Отсутствие поля равносильно `"commonjs"`.

# «Ближайший package.json»

Ключевая деталь. Node ищет `package.json` **вверх по дереву от файла**, до первого найденного:

```
proj/
├── package.json          { "type": "module" }
├── src/
│   └── app.js            → ESM
└── legacy/
    ├── package.json      { "type": "commonjs" }
    └── old.js            → CJS
```

Отсюда стандартный приём: держать основной проект в ESM, а папку с легаси-скриптами перевести обратно, положив туда `package.json` с одной строкой. То же работает и наоборот — точечно включить ESM в CJS-проекте.

Обратите внимание: **правило применяется и внутри `node_modules`**. Формат каждой зависимости определяется её собственным `package.json`, независимо от вашего.

# Что меняется при `"type": "module"`

Список того, что сломается в существующем проекте. Каждый пункт — реальная поломка при миграции.

**Расширения становятся обязательными.**
```js
import './utils';       // ERR_MODULE_NOT_FOUND
import './utils.js';    // ✅
```

**Директории не разворачиваются.**
```js
import './components';        // ERR_UNSUPPORTED_DIR_IMPORT
import './components/index.js';
```

**`require` недоступен.** Нужен `import` или `createRequire`:
```js
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
```

**`__dirname` и `__filename` исчезают.** Замена — [[import.meta]].

**`this` на верхнем уровне — `undefined`** вместо `module.exports`.

**Всегда strict mode.**

**JSON требует атрибут импорта.**

**Все конфиги в проекте становятся ESM.** `vite.config.js`, `.eslintrc.js`, `jest.config.js`, `tailwind.config.js` — всё, что лежит в дереве и имеет расширение `.js`, теперь разбирается как ESM. Инструмент, ожидающий `module.exports`, сломается. Лечение — переименовать конфиг в `.cjs`.

Последний пункт вызывает больше всего недоумения: «я добавил одну строку в package.json, и упал ESLint».

# Диагностика по сообщениям

**`Cannot use import statement outside a module`** — файл разбирается как CJS, а внутри ESM-синтаксис. Причины: нет `"type": "module"`, либо расширение `.cjs`, либо инструмент (старый Jest) прогоняет файл через CJS-загрузчик.

**`require is not defined in ES module scope`** — обратная ситуация: файл ESM, а в нём `require`.

**`ERR_REQUIRE_ESM`** — CJS пытается затянуть ESM. В свежих версиях Node это часто уже работает — см. [[require(esm) в Node.js]].

**`ERR_UNKNOWN_FILE_EXTENSION`** — Node не знает, что делать с расширением (типично при попытке запустить `.ts` напрямую без загрузчика).

Полный разбор — [[Диагностика ошибок модульных систем]].

# Практические стратегии

## Новый проект

`"type": "module"` сразу. Проблем не будет — с нуля всё пишется правильно.

## Библиотека, публикуемая в оба формата

Проблема: `.js` файл может быть только одним форматом. Стандартное решение — разные расширения:

```json
{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

ESM-сборка в `.js` (работает, потому что `type: module`), CJS — в `.cjs` (расширение перекрывает `type`). Ключевое: **условие `require` обязано указывать на файл, который реально является CJS**. Указали на `.js` при `type: module` — потребитель получит `ERR_REQUIRE_ESM`.

Проверка — `npx publint`.

## Миграция существующего проекта

Дешёвый порядок действий:

1. Переименовать все конфиги в `.cjs` **заранее**.
2. Добавить `"type": "module"`.
3. Прогнать сборку и тесты, чинить импорты по ошибкам.
4. Заменить `__dirname`/`require` на ESM-эквиваленты.
5. Проверить зависимости, которые могли использовать `require.cache` или монки-патчинг.

Пункт 5 обычно самый дорогой: тесты с подменой модулей нужно переписывать (см. [[Live bindings]]).

## Если мигрировать не хочется

В приложении, собираемом Vite/webpack, поле `type` влияет **только на конфиги и Node-скрипты**. Исходники приложения проходят через сборщик, который сам разбирается с форматом. Поэтому многие проекты живут без `"type": "module"` годами — и это нормально.

Осознанная миграция нужна, когда: пишете CLI/скрипты на Node, публикуете библиотеку, или зависимость стала ESM-only.
