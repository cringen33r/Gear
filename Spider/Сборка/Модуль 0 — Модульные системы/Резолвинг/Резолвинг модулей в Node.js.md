Алгоритм, превращающий строку из `import`/`require` в конкретный файл на диске. Сборщики его воспроизводят (с поправками), поэтому знание алгоритма Node — это знание того, как резолвит webpack, Vite и Rollup.

# Общая схема

```
спецификатор
   ├─ node:* или встроенный → модуль Node, поиск окончен
   ├─ ./ ../ /  → относительно текущего файла
   ├─ #...      → поле imports текущего пакета
   └─ bare      → поиск по node_modules вверх по дереву
```

# Относительные и абсолютные пути

**В CJS** Node последовательно пробует:

1. `./utils` как файл;
2. `./utils.js`, `./utils.json`, `./utils.node`;
3. `./utils/` как директорию: `package.json` → поле `main`; иначе `./utils/index.js`.

**В ESM** ничего этого нет. Спецификатор разрешается как URL относительно текущего модуля, **расширение обязательно**, директории не разворачиваются в `index.js`.

```js
import './utils';         // ERR_MODULE_NOT_FOUND
import './utils.js';      // ✅
import './components';    // ERR_UNSUPPORTED_DIR_IMPORT
```

Это самая частая поломка при добавлении `"type": "module"` в существующий проект. Причина решения — производительность и однозначность: перебор расширений означает лишние обращения к ФС и неоднозначность при наличии `utils.js` и `utils.json` рядом.

# Bare-спецификаторы: подъём по `node_modules`

Для `import 'lodash'` из `/home/proj/src/app.js` Node проверяет по порядку:

```
/home/proj/src/node_modules/lodash
/home/proj/node_modules/lodash          ← обычно находится здесь
/home/node_modules/lodash
/node_modules/lodash
```

Первое совпадение выигрывает. Отсюда два практических следствия:

**1. Вложенные `node_modules` создают отдельные экземпляры.** Если `lib-a` требует `shared@1`, а корень — `shared@2`, npm положит `shared@1` внутрь `node_modules/lib-a/node_modules/`. Оба будут загружены, каждый со своим состоянием — см. [[Реестр модулей и singleton-семантика]].

**2. «Фантомные зависимости».** При плоской установке (npm/yarn классические) пакет, который вы не объявляли в `package.json`, может оказаться в корневом `node_modules` как транзитивная зависимость — и ваш `import` его найдёт. Работает до тех пор, пока другая версия не изменит дерево. pnpm с его строгой symlink-структурой такое запрещает — отсюда «на pnpm не собирается».

# Что происходит внутри найденного пакета

Найдя папку пакета, Node читает `package.json`:

1. Есть **`exports`** → используется **только он**. Поля `main`, `module` игнорируются, любой путь вне описанного в `exports` недоступен. См. [[Поле exports]].
2. Нет `exports` → используется `main`; при его отсутствии — `index.js`. См. [[Точки входа пакета — main, module, browser, types]].

Приоритет `exports` абсолютен, и это важнейший практический момент: добавление `exports` в пакет — **breaking change**, если раньше потребители лезли в `dist/` напрямую.

Внутри `exports` выбор ветки определяют [[Условия резолвинга]].

# Определение формата файла

Найденный файл нужно ещё интерпретировать — как ESM или CJS. Решает:

- расширение `.mjs` → всегда ESM;
- расширение `.cjs` → всегда CJS;
- расширение `.js` → по полю `type` **ближайшего вверх по дереву** `package.json`.

Подробно — [[Поле type и расширения mjs cjs]].

# Symlink и монорепы

По умолчанию Node резолвит symlink в **реальный путь**. В монорепе с `npm link`/workspaces пакет физически лежит в `packages/ui`, а в `node_modules` — ссылка. Node приведёт путь к `packages/ui`, и поиск зависимостей пойдёт **оттуда**, а не из места ссылки.

Отсюда классический симптом: библиотека в монорепе «не видит» React, установленный в корне приложения, или видит **другой** его экземпляр. Ключи к решению: `--preserve-symlinks`, `resolve.symlinks` в webpack, `resolve.dedupe` в Vite, корректные `peerDependencies` у библиотеки.

# Чем сборщики отличаются от Node

Воспроизводя алгоритм, сборщики добавляют своё:

**Дополнительные поля.** `module` (ESM-сборка), `browser` (браузерная замена), `jsnext:main` (архаика) — Node их не знает вовсе.

**Условие `browser`.** При сборке для браузера сборщик подставляет условие `browser`, которого в Node нет.

**Алиасы.** `resolve.alias` (webpack), `resolve.alias` (Vite), `paths` (TS) — слой поверх стандартного резолвинга. См. [[Спецификаторы модулей]].

**Мягкость к расширениям.** `resolve.extensions` позволяет писать `./utils` даже в ESM-коде — удобно, но делает код непереносимым в чистый Node.

**Дедупликация.** `resolve.dedupe` в Vite принудительно схлопывает копии пакета к одной — прямое лечение [[Dual package hazard]].

Практический вывод: **то, что собралось, не обязательно запустится в Node, и наоборот**. Если пишете библиотеку — проверяйте обоими способами.

# Инструменты отладки

```bash
# где Node находит пакет
node -e "console.log(require.resolve('lodash'))"
node --input-type=module -e "console.log(import.meta.resolve('lodash'))"

# все копии в дереве
npm ls lodash
npm why lodash          # npm 8+, объясняет, кто притянул

# трассировка резолвинга
vite --debug resolve
```

При разборе «почему подтянулась не та версия» начинайте с `npm ls` — в 90% случаев ответ там.
