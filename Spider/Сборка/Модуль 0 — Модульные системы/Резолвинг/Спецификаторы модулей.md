Спецификатор — строка в `import 'X'`. От её формы зависит **весь алгоритм поиска**, и путаница между формами — источник большинства ошибок резолвинга.

# Три вида

## Относительный

Начинается с `./` или `../`.

```js
import { a } from './utils.js';
import { b } from '../shared/config.js';
```

Разрешается относительно **текущего модуля**. Работает везде одинаково: в браузере, Node, любом сборщике. Самая предсказуемая форма.

## Абсолютный

Начинается с `/` или является полным URL.

```js
import { a } from '/src/utils.js';                    // от корня сервера/ФС
import { b } from 'https://esm.sh/lodash-es';         // полный URL
import { c } from 'file:///home/user/mod.js';         // file URL
```

В браузере `/src/utils.js` — от корня origin. В сборщике этот же путь обычно перехватывается и трактуется от корня проекта — расхождение, о котором стоит помнить.

Импорт по `https://` браузер поддерживает нативно, Node — нет (только через загрузчики). Сборщики по умолчанию оставляют такие импорты как external.

## Bare (голый)

Всё остальное — не начинается ни с `./`, ни с `/`, не является URL.

```js
import { debounce } from 'lodash';        // имя пакета
import { map } from 'rxjs/operators';     // subpath пакета
import { readFile } from 'node:fs';       // встроенный модуль Node
import config from '#config';             // внутренний алиас пакета
```

Самая сложная форма. **Браузер не умеет их резолвить вовсе** — нужны [[Import maps]]. Node ищет по алгоритму `node_modules` (см. [[Резолвинг модулей в Node.js]]). Сборщики повторяют алгоритм Node плюс применяют свои алиасы.

# Ключевое различие: браузер против сборщика

Здесь корень недоразумений. Сборщики годами добавляли «удобства», которых в стандарте нет:

| Спецификатор | Браузер (нативно) | Сборщик |
|---|---|---|
| `'./utils.js'` | ✅ | ✅ |
| `'./utils'` | ❌ 404 | ✅ дописывает расширение |
| `'./folder'` | ❌ 404 | ✅ ищет `folder/index.js` |
| `'lodash'` | ❌ без import map | ✅ ищет в `node_modules` |
| `'@app/ui'` | ❌ | ✅ через alias/paths |

Практическое следствие: **код, написанный «как привычно», не работает в нативном ESM**. Скрипт, отлаженный внутри Vite, при запуске `node script.js` упадёт на отсутствующем расширении.

Обратная сторона: Node в режиме ESM тоже **требует расширения** (в отличие от CJS-режима). Это одна из самых частых поломок при добавлении `"type": "module"` — см. [[Поле type и расширения mjs cjs]].

# Про расширения в TypeScript

Отдельная боль. Вы пишете `.ts`, а в рантайме будет `.js`. Варианты:

```ts
import { a } from './utils';        // без расширения — классика TS
import { a } from './utils.js';     // с .js, хотя файл .ts
```

Второй вариант выглядит странно, но он **корректен** для `moduleResolution: node16/nodenext`: спецификатор описывает выходной файл, а компилятор его не переписывает. TypeScript намеренно не трогает пути при компиляции, поэтому ответственность на вас.

Для `moduleResolution: bundler` (Vite, webpack) расширение можно опускать — сборщик дорезолвит. Выбор режима определяется тем, кто будет исполнять код: Node напрямую → `nodenext` и `.js`; сборщик → `bundler` и без расширения.

# Алиасы: удобство ценой переносимости

```ts
// tsconfig.json
{ "compilerOptions": { "paths": { "@app/*": ["src/app/*"] } } }
```

```js
import { UserService } from '@app/services/user.service';
```

Критично понимать: **`paths` в tsconfig влияет только на проверку типов**. TypeScript не переписывает пути в выходном коде. Чтобы алиас работал в рантайме, его нужно **продублировать в конфиге сборщика**:

```js
// vite.config.ts
resolve: { alias: { '@app': path.resolve(__dirname, 'src/app') } }
```

Рассинхрон этих двух конфигов — классическая ошибка: типы резолвятся, IDE довольна, сборка падает с `Cannot find module '@app/...'`. Или наоборот. Держите их синхронизированными (в Vite для этого есть `vite-tsconfig-paths`, в Jest — `moduleNameMapper`, в webpack — `tsconfig-paths-webpack-plugin`).

Стандартная альтернатива без дублирования — [[Поле imports и внутренние алиасы]] с `#`-префиксом: его понимают и Node, и сборщики, и TypeScript.

# Встроенные модули Node

```js
import { readFile } from 'node:fs';    // явный префикс, предпочтительно
import { readFile } from 'fs';         // работает, но неоднозначно
```

Префикс `node:` устраняет двусмысленность (мог существовать npm-пакет с именем `fs`) и **сигнализирует сборщику**, что это платформенный модуль, а не зависимость. При сборке для браузера сборщик выдаст понятную ошибку вместо попытки найти пакет.

Отдельно: если браузерный бандл требует `fs`, `path`, `crypto` — значит, вы затянули серверный код. Полифилить нужно осознанно и редко; правильный ответ обычно — убрать зависимость. См. [[Диагностика ошибок модульных систем]].

# Как отладить резолвинг

- `node --experimental-import-meta-resolve` + `import.meta.resolve('пакет')` — где именно Node находит модуль;
- `require.resolve('пакет')` в CJS — то же самое;
- `npm ls пакет` — все копии в дереве зависимостей;
- `vite --debug resolve` — трассировка резолвинга в Vite;
- `resolve.symlinks`, `resolve.preserveSymlinks` — если пакет линкуется в монорепе.
